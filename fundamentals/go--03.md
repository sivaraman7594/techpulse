## 7. Generics and Iterators

### Type parameters (Go 1.18+)
<!-- level: intermediate; ref: https://go.dev/doc/tutorial/generics -->
Go 1.18 added generics: functions and types can declare type parameters in square brackets, each constrained by an interface. The compiler checks the body against the constraint once, and callers usually get type arguments inferred from the values they pass.

Before generics, reusable containers and algorithms used `interface{}` (losing type safety and boxing values) or code generation. Generics let you write `Map`, `Filter`, `Max`, typed caches and sets once, with full compile-time checking.

Under the hood, Go uses "GC shape stenciling with dictionaries": one copy of the code is compiled per memory shape (all pointer types share one shape), and a hidden dictionary argument supplies type-specific information. This keeps binaries small but means generic code is sometimes slower than a hand-specialised version, especially when calling methods through a type parameter.

```go
func Map[T, U any](in []T, f func(T) U) []U {
    out := make([]U, 0, len(in))
    for _, v := range in {
        out = append(out, f(v))
    }
    return out
}

func Filter[T any](in []T, keep func(T) bool) []T {
    var out []T
    for _, v := range in {
        if keep(v) {
            out = append(out, v)
        }
    }
    return out
}

names := Map(users, func(u User) string { return u.Name }) // T, U inferred
adults := Filter(users, func(u User) bool { return u.Age >= 18 })
ids := Map[User, int64](users, func(u User) int64 { return u.ID }) // explicit
```

- Pitfall: methods cannot have their own type parameters; only functions and types can. `func (s *Set[T]) Map[U any]()` is illegal.
- Pitfall: generics do not replace interfaces. If you only call methods on a value, an ordinary interface parameter is simpler.
- Interview tip: name the implementation strategy (stenciling by GC shape plus dictionaries) and its performance implication.

### Constraints, type sets and the ~ operator
<!-- level: intermediate; ref: https://go.dev/blog/intro-generics -->
A constraint is an interface that describes a type set: the set of types allowed as type arguments. Besides methods, constraint interfaces can list types with `|`, and `~T` means "any type whose underlying type is T", so user-defined types like `type Cents int64` qualify.

Predeclared and standard constraints:

- `any`: no restriction (but you can only do things every type supports: assign, pass, take address).
- `comparable`: types supporting `==` and `!=`, required for map keys. Since Go 1.20, interfaces satisfy `comparable` even though comparison might panic at runtime.
- `cmp.Ordered` (Go 1.21): integers, floats and strings, supporting `<`.

Interfaces containing type unions can only be used as constraints, not as ordinary variable types.

```go
type Number interface {
    ~int | ~int32 | ~int64 | ~float32 | ~float64
}

func Sum[T Number](xs []T) T {
    var total T
    for _, x := range xs {
        total += x
    }
    return total
}

type Cents int64 // underlying int64: matches ~int64

func MaxBy[T any, K cmp.Ordered](xs []T, key func(T) K) (best T, ok bool) {
    for i, x := range xs {
        if i == 0 || key(x) > key(best) {
            best, ok = x, true
        }
    }
    return
}

// Constraint mixing methods and types
type StringID interface {
    ~string
    Validate() error
}

total := Sum([]Cents{150, 250}) // Cents(400)
```

- Pitfall: without `~`, `int64` would reject `Cents`. Library constraints should almost always use `~`.
- Pitfall: you cannot use a type switch on a type parameter directly; convert to `any` first, which is a code smell in generic code.
- Interview tip: say "constraint = type set", which is the vocabulary of the spec.

### Generic types and generic type aliases
<!-- level: intermediate; ref: https://go.dev/ref/spec#Type_parameter_declarations -->
Types can be parameterised too: `type Stack[T any] struct{ items []T }`. Methods on a generic type use the type's parameters (`func (s *Stack[T]) Push(v T)`) but cannot introduce new ones. To instantiate, write `Stack[int]{}`; inference does not work for composite literals.

Common uses: typed collections (sets, ordered maps, ring buffers), caches, result/option-like containers, typed concurrency helpers (a typed `sync.Pool` wrapper or a typed atomic value), and pagination or API response envelopes.

Go 1.24 fully supports generic type aliases: `type Set[T comparable] = map[T]struct{}` is an alias, not a new type, so it interoperates with plain maps. This matters for refactoring generic APIs across packages.

```go
type Set[T comparable] map[T]struct{}

func NewSet[T comparable](vals ...T) Set[T] {
    s := make(Set[T], len(vals))
    for _, v := range vals {
        s[v] = struct{}{}
    }
    return s
}

func (s Set[T]) Has(v T) bool { _, ok := s[v]; return ok }

type Cache[K comparable, V any] struct {
    mu   sync.Mutex
    data map[K]V
}

func (c *Cache[K, V]) GetOrLoad(k K, load func(K) (V, error)) (V, error) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if v, ok := c.data[k]; ok {
        return v, nil
    }
    v, err := load(k)
    if err == nil {
        if c.data == nil { c.data = make(map[K]V) }
        c.data[k] = v
    }
    return v, err
}

type Page[T any] struct {
    Items []T   `json:"items"`
    Next  string `json:"next,omitempty"`
}
```

- Pitfall: holding the lock while calling `load` serialises all misses; real caches use `singleflight` or per-key locks.
- Interview tip: mention Go 1.24 generic aliases as a recent change.

### When to use generics (and when not)
<!-- level: advanced; ref: https://go.dev/blog/when-generics -->
Generics are a tool, not a style. Guidance from the Go team, condensed:

Use generics when:

- You write the same code for multiple element types: container types, slice and map algorithms, channel helpers (merge, batch), typed wrappers.
- The function operates on the type's shape (slices, maps, channels) rather than its behaviour.
- You would otherwise use `any` and type assertions, losing safety.

Avoid generics when:

- You only call methods on the value. An interface parameter does the same job with simpler code and no instantiation.
- The implementation differs per type; then you need an interface with methods, or separate functions.
- It is speculative. Write concrete code first; generalise when a second or third type appears.

Performance reality: because of GC-shape stenciling, calling a method on a type-parameter value goes through a dictionary and is often not inlined; generic code over pointer types can be slower than the interface version. For numeric hot loops over value types, generics are usually as fast as hand-written code.

```go
// Good: shape-based, type-safe, no interfaces needed
func Batch[T any](in <-chan T, size int) <-chan []T {
    out := make(chan []T)
    go func() {
        defer close(out)
        buf := make([]T, 0, size)
        for v := range in {
            buf = append(buf, v)
            if len(buf) == size {
                out <- buf
                buf = make([]T, 0, size)
            }
        }
        if len(buf) > 0 {
            out <- buf
        }
    }()
    return out
}

// Unnecessary: an interface parameter is simpler
func WriteAll[W io.Writer](w W, b []byte) error { _, err := w.Write(b); return err }
```

- Pitfall: deeply nested constraints and type parameters make APIs hard to read; readability is still the top Go value.
- Interview tip: give one example where you chose an interface over generics and explain why.

### Range-over-func iterators (Go 1.23)
<!-- level: advanced; ref: https://go.dev/blog/range-functions -->
Go 1.23 lets `for range` loop over functions with specific signatures, called push iterators. The `iter` package names them:

- `iter.Seq[V]` is `func(yield func(V) bool)`.
- `iter.Seq2[K, V]` is `func(yield func(K, V) bool)`.

The iterator calls `yield` for each element; `yield` returns false when the loop body executes `break` or `return`, and the iterator must then stop. The compiler rewrites the loop body into the yield function, handling `break`, `continue`, `return` and `defer` correctly.

This gives a standard way to expose sequences from custom collections, paginated APIs or database cursors without allocating a slice. Standard functions now return iterators: `maps.Keys`, `slices.All`, `slices.Values`, `strings.SplitSeq` and `strings.Lines` (Go 1.24). `iter.Pull` converts a push iterator into a pull-style `next()` function when you need to step through two sequences together.

```go
// Iterate a paginated API lazily
func (c *Client) Orders(ctx context.Context) iter.Seq2[Order, error] {
    return func(yield func(Order, error) bool) {
        token := ""
        for {
            page, err := c.fetchPage(ctx, token)
            if err != nil {
                yield(Order{}, err)
                return
            }
            for _, o := range page.Items {
                if !yield(o, nil) {
                    return // caller broke out
                }
            }
            if page.Next == "" {
                return
            }
            token = page.Next
        }
    }
}

for o, err := range client.Orders(ctx) {
    if err != nil { return err }
    if o.Total > 1000 { break } // stops fetching further pages
}

for line := range strings.Lines(text) { fmt.Print(line) } // Go 1.24
```

- Pitfall: calling `yield` again after it returned false panics at runtime. Always check its result.
- Pitfall: iterators are single-pass unless you design them otherwise; document whether a sequence can be ranged twice.
- Interview tip: contrast push iterators (Seq) with pull (`iter.Pull`) and mention that pull needs `stop()` to release resources.

## 8. Goroutines and Channels

### Goroutines and the scheduler (G, M, P)
<!-- level: intermediate; ref: https://go.dev/doc/effective_go#goroutines -->
A goroutine is a function running concurrently, started with the `go` keyword. Goroutines are much cheaper than OS threads: they start with a small stack (a few KB) that grows and shrinks as needed, and creating one costs about a microsecond. Running hundreds of thousands is normal.

The runtime scheduler multiplexes goroutines onto OS threads using three entities:

- G: a goroutine (stack, instruction pointer, state).
- M: an OS thread (machine).
- P: a processor, a scheduling context with a local run queue. The number of Ps equals `GOMAXPROCS`, which bounds how many goroutines execute Go code in parallel.

An M must hold a P to run Go code. Idle Ps steal work from other Ps' queues. When a goroutine blocks in a syscall, its M releases the P so another M can keep running goroutines. Network I/O does not block threads at all: the netpoller (epoll/kqueue/IOCP) parks the goroutine and wakes it when the socket is ready. Since Go 1.14, goroutines are asynchronously preempted, so a tight loop cannot starve others.

```go
func main() {
    results := make(chan string)
    urls := []string{"https://go.dev", "https://pkg.go.dev"}
    for _, u := range urls {
        go func() { // Go 1.22+: u is per-iteration, safe to capture
            resp, err := http.Get(u)
            if err != nil {
                results <- u + ": " + err.Error()
                return
            }
            resp.Body.Close()
            results <- u + ": " + resp.Status
        }()
    }
    for range urls {
        fmt.Println(<-results)
    }
}
```

When `main` returns, the program exits immediately; other goroutines are not waited for. Something (channel, WaitGroup, errgroup) must synchronise.

- Pitfall: "fire and forget" goroutines with no owner leak and outlive requests. Every goroutine needs a clear way to stop.
- Interview tip: explain why blocking network calls are cheap in Go (netpoller) and blocking syscalls/cgo are not.

### Channels: unbuffered and buffered
<!-- level: basic; ref: https://go.dev/tour/concurrency/2 -->
A channel is a typed, goroutine-safe queue used to pass values and synchronise. "Do not communicate by sharing memory; share memory by communicating."

- Unbuffered (`make(chan T)`): a send blocks until a receiver takes the value, and vice versa. It is a rendezvous that both transfers data and synchronises the two goroutines.
- Buffered (`make(chan T, n)`): sends block only when the buffer is full; receives block when it is empty. Buffers decouple producer and consumer speeds and smooth bursts, but do not fix a consumer that is permanently slower.

Directional types `chan<- T` (send-only) and `<-chan T` (receive-only) document and enforce roles in function signatures.

Internally a channel (`hchan`) is a mutex-protected ring buffer plus queues of waiting senders and receivers. When a receiver is already waiting, a sender copies the value directly onto the receiver's stack.

Blocking rules to memorise: send or receive on a nil channel blocks forever; send on a closed channel panics; receive on a closed channel returns the zero value immediately (with `ok == false`).

```go
func producer(n int) <-chan int {
    ch := make(chan int, 16) // buffered: producer can run ahead a bit
    go func() {
        defer close(ch)
        for i := range n {
            ch <- i * i
        }
    }()
    return ch
}

func main() {
    for v := range producer(5) { // ends when channel is closed
        fmt.Println(v)
    }
    done := make(chan struct{}) // signal-only channel
    go func() { defer close(done); time.Sleep(10 * time.Millisecond) }()
    <-done
}
```

- Pitfall: choosing a buffer size to "fix" a deadlock usually hides a design problem.
- Pitfall: channels are slower than a mutex for protecting simple shared state; use them for ownership transfer and signalling.
- Interview tip: list the nil/closed channel behaviours confidently.

### Closing channels and range
<!-- level: intermediate; ref: https://go.dev/ref/spec#Close -->
`close(ch)` signals that no more values will be sent. Receivers drain any buffered values, then get zero values with `ok == false`. `for v := range ch` loops until the channel is closed and drained, which is the standard consumer loop.

Rules of thumb:

- Only the sender closes, never the receiver: a sender writing to a closed channel panics.
- With multiple senders, no single sender can safely close. Use a `sync.WaitGroup` and a separate goroutine that closes after all senders finish.
- Closing is a broadcast: every receiver waiting on the channel wakes up. That makes `close(done)` the classic way to tell many goroutines to stop (context cancellation is built on this).
- You do not need to close a channel for garbage collection; close only to signal.

```go
func fetchAll(ids []int) <-chan Result {
    out := make(chan Result)
    var wg sync.WaitGroup
    for _, id := range ids {
        wg.Add(1)
        go func() {
            defer wg.Done()
            out <- fetch(id)
        }()
    }
    go func() {
        wg.Wait()
        close(out) // closed exactly once, after all senders are done
    }()
    return out
}

for r := range fetchAll([]int{1, 2, 3}) {
    fmt.Println(r)
}

v, ok := <-out // ok == false means closed and drained
```

- Pitfall: closing a channel twice panics. If close can happen from several places, guard it with `sync.Once`.
- Pitfall: a consumer that stops reading early (returns on first error) leaves senders blocked forever: a goroutine leak. Give senders a way out with `select` on a done channel or context.
- Interview tip: "the sender closes" is the answer interviewers want, plus the multi-sender WaitGroup pattern.

### select, timeouts and non-blocking operations
<!-- level: intermediate; ref: https://go.dev/tour/concurrency/5 -->
`select` waits on several channel operations at once and runs whichever case becomes ready first. If several are ready, one is chosen uniformly at random to avoid starvation. A `default` case makes the select non-blocking.

Typical uses:

- Timeouts: `case <-time.After(d)` or a timer.
- Cancellation: `case <-ctx.Done()`.
- Non-blocking send or receive with `default` (drop or skip when busy).
- Merging inputs from several channels.
- Disabling a case dynamically by setting its channel variable to nil (nil channels never become ready).

```go
func worker(ctx context.Context, jobs <-chan Job, results chan<- Result) error {
    ticker := time.NewTicker(30 * time.Second)
    defer ticker.Stop()
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case j, ok := <-jobs:
            if !ok {
                return nil // input closed
            }
            select {
            case results <- process(j):
            case <-ctx.Done():
                return ctx.Err()
            }
        case <-ticker.C:
            slog.Info("worker heartbeat")
        }
    }
}

// Non-blocking publish: drop metrics rather than stall the caller
select {
case metrics <- m:
default:
    dropped.Add(1)
}
```

Timer note: since Go 1.23, timers and tickers that are no longer referenced are garbage collected even if not stopped, and their channels are unbuffered (synchronous), so `Reset`/`Stop` no longer deliver stale values. Calling `Stop` is still good hygiene.

- Pitfall: `time.After` in a hot loop allocated a new timer per iteration that lived until it fired before Go 1.23; reuse a timer in older codebases.
- Pitfall: a `for { select { default: } }` with nothing blocking is a busy loop that burns 100% CPU.
- Interview tip: explain the nil-channel trick for turning off a case after its channel closes.

### Concurrency patterns: pipelines, fan-out, fan-in, worker pools
<!-- level: advanced; ref: https://go.dev/blog/pipelines -->
A pipeline is a series of stages connected by channels: each stage receives values from upstream, processes them and sends downstream. Fan-out means several goroutines read from the same channel to parallelise a slow stage; fan-in merges several channels into one.

A worker pool is fan-out with a fixed number of goroutines, which bounds concurrency: important when each job uses a database connection or calls a rate-limited API. Bounding is the key property; unbounded `go` per item can overwhelm downstream systems.

Every stage must stop when the consumer stops, so all stages take a `context.Context` (or done channel) and select on it when sending.

```go
func pool(ctx context.Context, jobs []Job, workers int) ([]Result, error) {
    in := make(chan Job)
    out := make(chan Result)
    var wg sync.WaitGroup

    for range workers {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range in {
                select {
                case out <- process(j):
                case <-ctx.Done():
                    return
                }
            }
        }()
    }
    go func() { // feeder
        defer close(in)
        for _, j := range jobs {
            select {
            case in <- j:
            case <-ctx.Done():
                return
            }
        }
    }()
    go func() { wg.Wait(); close(out) }()

    var res []Result
    for r := range out {
        res = append(res, r)
    }
    return res, ctx.Err()
}
```

A simpler bounded alternative is a semaphore: a buffered channel of size N acquired before each goroutine starts, or `errgroup.Group.SetLimit(N)`.

- Pitfall: if workers send results on an unbuffered channel and the collector returns early on error, workers block forever. Always pair sends with `ctx.Done()`.
- Pitfall: result order is not preserved; carry an index if order matters.
- Interview tip: be ready to write a worker pool on a whiteboard, including shutdown.

### Goroutine leaks
<!-- level: advanced; ref: https://pkg.go.dev/runtime/pprof -->
A goroutine leak is a goroutine that never exits because it is blocked forever, typically on a channel send or receive, a lock, or a network call without a timeout. Each leaked goroutine holds its stack and everything it references, so leaks show up as slowly rising memory and goroutine counts until the process is OOM-killed.

Common causes:

- Sending on a channel nobody will read (the receiver returned early after an error or timeout).
- Receiving from a channel nobody will close.
- Missing cancellation: a background loop with no `ctx.Done()` case.
- HTTP calls with no timeout, or response bodies that are never closed.
- `time.Ticker` loops started per request and never stopped.

Detection: expose `net/http/pprof` and look at `/debug/pprof/goroutine?debug=1`, which groups goroutines by stack. Thousands of identical stacks blocked on `chan send` point straight at the culprit. Export `runtime.NumGoroutine()` as a metric and alert on growth. In tests, `go.uber.org/goleak` fails tests that leave goroutines behind, and Go 1.25's `testing/synctest` reports goroutines left blocked in a bubble.

```go
// Leaky: if ctx times out first, the goroutine blocks forever on ch <- ...
func queryLeaky(ctx context.Context) (string, error) {
    ch := make(chan string)
    go func() { ch <- slowQuery() }()
    select {
    case v := <-ch:
        return v, nil
    case <-ctx.Done():
        return "", ctx.Err()
    }
}

// Fixed: buffer of 1 lets the goroutine finish and be collected
func query(ctx context.Context) (string, error) {
    ch := make(chan string, 1)
    go func() { ch <- slowQuery() }()
    select {
    case v := <-ch:
        return v, nil
    case <-ctx.Done():
        return "", ctx.Err()
    }
}
```

The fix stops the leak but `slowQuery` still runs to completion; better still, pass `ctx` into it so the work itself is cancelled.

- Interview tip: describe both detection (pprof goroutine profile) and prevention (ownership, context, buffered result channels).

## 9. Synchronisation and Context

### Mutex and RWMutex
<!-- level: intermediate; ref: https://pkg.go.dev/sync#Mutex -->
`sync.Mutex` provides mutual exclusion: only one goroutine can hold it between `Lock` and `Unlock`. `sync.RWMutex` allows many concurrent readers (`RLock`) or one writer (`Lock`). Both have usable zero values and must not be copied after first use.

Go's mutex is not re-entrant: locking it twice in the same goroutine deadlocks. It has a fast path (a single atomic compare-and-swap when uncontended), spins briefly, then parks the goroutine. In starvation mode (a waiter blocked for over 1 ms), ownership is handed directly to waiters in FIFO order to bound tail latency.

Guidelines:

- Keep critical sections short; never do I/O or call unknown callbacks while holding a lock.
- Put the mutex next to the fields it protects and document which fields those are.
- Prefer `defer mu.Unlock()` for correctness, unless profiling shows the critical section must end earlier.
- RWMutex only helps when reads are frequent, long enough to matter, and writes are rare. For tiny critical sections a plain Mutex is often faster because RWMutex has higher overhead.

```go
type RateCounter struct {
    mu     sync.Mutex // protects counts
    counts map[string]int
}

func (r *RateCounter) Hit(key string) int {
    r.mu.Lock()
    defer r.mu.Unlock()
    if r.counts == nil {
        r.counts = make(map[string]int)
    }
    r.counts[key]++
    return r.counts[key]
}

func (r *RateCounter) Snapshot() map[string]int {
    r.mu.Lock()
    defer r.mu.Unlock()
    return maps.Clone(r.counts) // never hand out the guarded map itself
}
```

- Pitfall: returning a reference to guarded data (a map or slice) lets callers bypass the lock.
- Pitfall: lock-order inversion between two mutexes causes deadlocks; always acquire in a consistent global order.
- Pitfall: an RWMutex reader that calls RLock again while a writer is waiting can deadlock, because new readers block behind pending writers.
- Interview tip: say "not re-entrant" and mention `go vet` copylocks.

### WaitGroup and WaitGroup.Go (Go 1.25)
<!-- level: basic; ref: https://pkg.go.dev/sync#WaitGroup -->
A `sync.WaitGroup` waits for a collection of goroutines to finish. The classic pattern calls `Add(1)` before starting each goroutine, `Done()` (usually deferred) when it finishes, and `Wait()` to block until the counter reaches zero.

Go 1.25 added `WaitGroup.Go(f)`, which does the `Add(1)`, starts the goroutine and calls `Done` for you. It removes the two most common bugs: calling `Add` inside the goroutine (racing with `Wait`) and forgetting `Done` on an early return. `go vet` in 1.25 also flags `wg.Add` called inside the new goroutine.

A WaitGroup does not collect errors or cancel siblings; for that, use `errgroup`. It also must not be copied after use, so pass it by pointer.

```go
// Go 1.25+
func resizeAll(paths []string) {
    var wg sync.WaitGroup
    for _, p := range paths {
        wg.Go(func() {
            if err := resize(p); err != nil {
                slog.Error("resize failed", "path", p, "err", err)
            }
        })
    }
    wg.Wait()
}

// Pre-1.25 equivalent
func resizeAllOld(paths []string) {
    var wg sync.WaitGroup
    for _, p := range paths {
        wg.Add(1) // before go, never inside
        go func() {
            defer wg.Done()
            _ = resize(p)
        }()
    }
    wg.Wait()
}
```

- Pitfall: a negative counter (more `Done` than `Add`) panics.
- Pitfall: reusing a WaitGroup for a new batch before the previous `Wait` has returned is a bug.
- Pitfall: unbounded fan-out (`wg.Go` for a million items) can exhaust memory or downstream connections; bound concurrency with a semaphore or `errgroup.SetLimit`.
- Interview tip: mentioning `WaitGroup.Go` shows you track recent releases.

### sync.Once, OnceFunc and OnceValue
<!-- level: intermediate; ref: https://pkg.go.dev/sync#OnceValue -->
`sync.Once` runs a function exactly once, no matter how many goroutines call `Do` concurrently; all callers block until the first call completes. It is the standard tool for lazy initialisation of expensive shared resources: a parsed template set, a database pool, a compiled regex table.

Go 1.21 added convenience wrappers:

- `sync.OnceFunc(f)` returns a function that calls f only once.
- `sync.OnceValue(f)` returns a function that computes and caches a single value.
- `sync.OnceValues(f)` caches a `(value, error)` pair.

If f panics, `Once.Do` treats it as done (later calls do nothing), while the `OnceFunc`/`OnceValue` wrappers re-panic with the same value on every call, which is usually what you want.

```go
var loadRates = sync.OnceValues(func() (map[string]float64, error) {
    data, err := os.ReadFile("rates.json")
    if err != nil {
        return nil, err
    }
    var m map[string]float64
    return m, json.Unmarshal(data, &m)
})

func Convert(amount float64, ccy string) (float64, error) {
    rates, err := loadRates() // first caller loads; others wait, then reuse
    if err != nil {
        return 0, err
    }
    return amount * rates[ccy], nil
}

type Client struct {
    closeOnce sync.Once
    done      chan struct{}
}

func (c *Client) Close() { c.closeOnce.Do(func() { close(c.done) }) } // idempotent
```

- Pitfall: errors are cached too. With `OnceValues`, a transient failure (network blip) is remembered forever; if you need retry, write a mutex-based loader instead.
- Pitfall: calling `Do` recursively on the same Once from inside f deadlocks.
- Interview tip: `Once` uses an atomic fast path, so the steady-state cost is a single atomic load.

### Atomics and the Go memory model
<!-- level: advanced; ref: https://go.dev/ref/mem -->
The Go memory model defines when a read in one goroutine is guaranteed to observe a write in another. The rule is "happens-before": a write is visible to a read only if synchronisation orders them, through channel operations, mutex unlock/lock, `sync.Once`, `WaitGroup`, or atomic operations. Without synchronisation, a program has a data race and Go makes no promises; the compiler and CPU may reorder, cache or tear values.

Since the 2022 revision (Go 1.19), `sync/atomic` operations are sequentially consistent, like C++ `seq_cst` atomics. Go 1.19 also added typed atomics: `atomic.Int64`, `atomic.Uint32`, `atomic.Bool`, `atomic.Pointer[T]`, which are safer than the functions on raw ints (they are aligned correctly even on 32-bit platforms and cannot be accessed non-atomically by mistake).

Use atomics for counters, flags and swapping immutable snapshots (copy-on-write config). Use a mutex when several fields must change together.

```go
type Stats struct {
    requests atomic.Int64
    healthy  atomic.Bool
}

type Config struct{ RateLimit int; Features map[string]bool }

var current atomic.Pointer[Config] // readers never lock

func reload(path string) error {
    cfg, err := parseConfig(path)
    if err != nil {
        return err
    }
    current.Store(cfg) // publish a new immutable snapshot
    return nil
}

func handle() {
    stats.requests.Add(1)
    cfg := current.Load() // consistent snapshot; never mutate it
    _ = cfg.RateLimit
}
```

- Pitfall: two separate atomic operations are not atomic together. `if v.Load() == 0 { v.Store(1) }` races; use `CompareAndSwap`.
- Pitfall: "benign" races on plain ints are not benign in Go; they are undefined behaviour and the race detector will flag them.
- Interview tip: define happens-before and give two ways to establish it.

### The race detector
<!-- level: intermediate; ref: https://go.dev/doc/articles/race_detector -->
A data race happens when two goroutines access the same memory concurrently and at least one access is a write, without synchronisation. Races cause corrupted data, torn reads, crashes and heisenbugs that vanish under a debugger.

Go ships a race detector based on ThreadSanitizer. Build or test with `-race` and the compiler instruments every memory access; at runtime it tracks happens-before relationships with vector clocks and prints both conflicting stacks when it sees a race.

Properties to know:

- It finds races that actually happen during execution, not all possible races. Good test coverage and realistic concurrency are needed.
- No false positives: every report is a real bug.
- Overhead is roughly 2–20x CPU and 5–10x memory, so it is used in CI and staging, not usually in production.
- It requires cgo on most platforms.

```go
// Racy: run `go test -race` and it reports a DATA RACE
func TestCounter(t *testing.T) {
    var n int
    var wg sync.WaitGroup
    for range 100 {
        wg.Go(func() { n++ }) // unsynchronised read-modify-write
    }
    wg.Wait()
    t.Log(n)
}

// Fixed
func TestCounterFixed(t *testing.T) {
    var n atomic.Int64
    var wg sync.WaitGroup
    for range 100 {
        wg.Go(func() { n.Add(1) })
    }
    wg.Wait()
    if n.Load() != 100 {
        t.Fatal(n.Load())
    }
}
```

Run `go test -race ./...` in CI on every change. Combine with `-count=N` or stress tools to shake out rare interleavings.

- Pitfall: "it passes without -race" means nothing for concurrent code.
- Pitfall: races on maps also trigger the runtime's own fatal "concurrent map writes" check, but only sometimes; `-race` is more reliable.
- Interview tip: say it has no false positives but can have false negatives.

### errgroup and structured concurrency
<!-- level: intermediate; ref: https://pkg.go.dev/golang.org/x/sync/errgroup -->
`golang.org/x/sync/errgroup` combines a WaitGroup, first-error capture and context cancellation. `errgroup.WithContext(ctx)` returns a group and a derived context; `g.Go(f)` starts a goroutine; `g.Wait()` waits for all and returns the first non-nil error. When any function returns an error, the derived context is cancelled so siblings can stop early.

`g.SetLimit(n)` bounds the number of active goroutines: `Go` blocks until a slot is free, which turns errgroup into a simple bounded worker pool. `TryGo` starts only if a slot is available.

This is Go's practical form of structured concurrency: goroutines are scoped to a function call, and the function does not return until all of them finish.

```go
func enrichOrders(ctx context.Context, ids []int64) ([]Order, error) {
    g, ctx := errgroup.WithContext(ctx)
    g.SetLimit(8) // at most 8 concurrent DB calls
    out := make([]Order, len(ids))

    for i, id := range ids {
        g.Go(func() error {
            o, err := repo.Get(ctx, id) // honours cancellation
            if err != nil {
                return fmt.Errorf("order %d: %w", id, err)
            }
            out[i] = o // each goroutine writes its own index: no race
            return nil
        })
    }
    if err := g.Wait(); err != nil {
        return nil, err
    }
    return out, nil
}
```

- Pitfall: the derived ctx is cancelled after `Wait` returns, so do not keep using it afterwards.
- Pitfall: functions that ignore ctx keep running after a sibling fails; cancellation is cooperative.
- Pitfall: a panic in a `g.Go` function still crashes the process (newer versions of x/sync propagate it to `Wait`); recover inside if needed.
- Interview tip: prefer errgroup over hand-rolled WaitGroup plus error channel in answers.

### context: cancellation, deadlines and values
<!-- level: intermediate; ref: https://pkg.go.dev/context -->
`context.Context` carries a cancellation signal, an optional deadline and request-scoped values across API boundaries and goroutines. It forms a tree: derived contexts are cancelled when their parent is cancelled.

Constructors: `context.Background()` at the top level; `WithCancel`, `WithTimeout`, `WithDeadline` for cancellation; `WithValue` for request-scoped data. Go 1.20 added `WithCancelCause` and Go 1.21 added `WithTimeoutCause`, `WithDeadlineCause`, `AfterFunc` and `WithoutCancel` (keeps values but detaches cancellation, useful for work that must finish after the request ends).

Conventions:

- Pass ctx as the first parameter, named `ctx`. Never store it in a struct (except for rare long-lived adapters).
- Always call the `cancel` function returned by `With*` (usually `defer cancel()`), or timers and goroutines leak until the parent ends.
- Check `ctx.Done()` in loops and pass ctx to every blocking call (database, HTTP, gRPC).
- `ctx.Err()` is `context.Canceled` or `context.DeadlineExceeded`.
- Use values only for request-scoped metadata (trace IDs, auth principal), not optional function parameters. Use an unexported key type to avoid collisions.

```go
type ctxKey struct{}

func WithUser(ctx context.Context, u *User) context.Context {
    return context.WithValue(ctx, ctxKey{}, u)
}

func UserFrom(ctx context.Context) (*User, bool) {
    u, ok := ctx.Value(ctxKey{}).(*User)
    return u, ok
}

func (s *Service) Report(ctx context.Context, id int64) (*Report, error) {
    ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()
    rows, err := s.db.QueryContext(ctx, `SELECT ... WHERE account=$1`, id)
    if err != nil {
        return nil, fmt.Errorf("report %d: %w", id, err) // may wrap DeadlineExceeded
    }
    defer rows.Close()
    return buildReport(rows)
}
```

- Pitfall: `context.Background()` deep inside request handling discards the client's cancellation and deadline.
- Pitfall: a child timeout longer than the parent's has no effect; the earlier deadline wins.
- Interview tip: explain that cancellation is cooperative: context signals, code must listen.
