## 10. Modules and Tooling

### Modules, go.mod and go.sum
<!-- level: basic; ref: https://go.dev/ref/mod -->
A module is a collection of packages versioned together, defined by a `go.mod` file at its root. Modules replaced GOPATH as the default in Go 1.16. `go mod init example.com/shop` creates go.mod with the module path, which is the import prefix for all its packages.

go.mod contains:

- `module`: the module path.
- `go`: the minimum Go language version the module requires. Since Go 1.21 this is a hard requirement, and it also selects language semantics (for example, per-iteration loop variables apply only to modules declaring `go 1.22` or later).
- `require`: dependencies with minimum versions; `// indirect` marks ones not imported directly.
- `replace`, `exclude`, `retract`, `toolchain`, `tool` (Go 1.24) and `godebug` directives.

go.sum records cryptographic hashes of every module version used, verified against the public checksum database (sum.golang.org), so a tampered or changed dependency is detected. Commit both files.

```bash
go mod init example.com/shop
go get github.com/jackc/pgx/v5@v5.7.1   # add or upgrade a dependency
go get -u ./...                          # upgrade direct and indirect deps
go mod tidy                              # add missing, remove unused
go list -m all                           # full build list
go mod why -m golang.org/x/text          # why is this here?
```

```go
module example.com/shop

go 1.25

require (
    github.com/jackc/pgx/v5 v5.7.1
    golang.org/x/sync v0.10.0
)
```

Major versions 2 and above live at a different import path (`/v2`, `/v5`), the "semantic import versioning" rule. This lets two major versions coexist in one build.

- Pitfall: forgetting `go mod tidy` before committing leaves go.mod and go.sum inconsistent and breaks CI.
- Pitfall: private modules need `GOPRIVATE=github.com/myorg/*` so the go command skips the public proxy and checksum database.
- Interview tip: explain why go.sum is not a lock file in the npm sense (MVS already makes builds reproducible; go.sum is about integrity).

### Minimal version selection and dependency management
<!-- level: advanced; ref: https://go.dev/ref/mod#minimal-version-selection -->
Go resolves dependency versions with Minimal Version Selection (MVS). Each module states the minimum version it needs of each dependency. The go command builds the graph of requirements and, for each module, picks the highest of the minimum versions requested. It never picks a newer version just because one exists.

Consequences:

- Builds are reproducible without a separate lock file: the same go.mod files always produce the same build list.
- Upgrades happen only when you ask (`go get -u`) or a dependency raises its minimum.
- There is no SAT solving and no "dependency hell" search; the algorithm is simple and fast.

Tools for controlling the graph:

- `replace` points a module to a fork or a local directory (only honoured in the main module).
- `exclude` skips a specific bad version.
- `retract` (in a library's own go.mod) tells consumers not to use versions you published by mistake.
- `GOPROXY` (default `https://proxy.golang.org,direct`) serves immutable module zips; companies run Athens or Artifactory as a private proxy.
- `go mod vendor` copies dependencies into `vendor/` for air-gapped builds.

```go
module example.com/payments

go 1.25

require github.com/acme/ledger v1.8.0

// Temporary fix while upstream merges our patch
replace github.com/acme/ledger => github.com/myorg/ledger v1.8.1-fix.1

// Known broken release
exclude github.com/acme/ledger v1.7.3
```

```bash
govulncheck ./...   # reports known vulnerabilities actually reachable from your code
```

- Pitfall: a `replace` to a local path (`=> ../ledger`) committed by accident breaks everyone else's build. Use workspaces for local development instead.
- Pitfall: `go get -u ./...` can pull many minor upgrades at once; upgrade deliberately and run tests.
- Interview tip: contrast MVS with npm/pip "latest compatible" resolution.

### Workspaces, toolchains and the tool directive
<!-- level: intermediate; ref: https://go.dev/doc/toolchain -->
Three features make multi-module and multi-version work manageable.

Workspaces (Go 1.18): a `go.work` file lists several local modules (`go work init ./api ./lib`). Builds inside the workspace use the local copies instead of the versions in go.mod, so you can change a library and its consumer together without `replace` directives. go.work is usually not committed for libraries.

Toolchain management (Go 1.21): the `go` line states the minimum language version and the optional `toolchain` line suggests a specific toolchain. If your installed Go is older than required, the go command downloads the right toolchain automatically (controlled by `GOTOOLCHAIN`, e.g. `GOTOOLCHAIN=local` to forbid downloads). This makes "works on my machine" version mismatches rare.

Tool dependencies (Go 1.24): a `tool` directive in go.mod tracks executables such as code generators and linters, versioned like any other dependency. Run them with `go tool <name>`. It replaces the old `tools.go` blank-import hack.

```bash
go work init ./orders ./shared
go work use ./billing

go get -tool golang.org/x/tools/cmd/stringer   # adds a tool directive (Go 1.24)
go tool stringer -type=Status ./...
```

```go
module example.com/orders

go 1.24.0

toolchain go1.25.3

tool golang.org/x/tools/cmd/stringer
```

- Pitfall: committing go.work in a service repo can make CI build against local paths that do not exist there.
- Pitfall: raising the `go` line forces every consumer of your library onto that version; libraries should lag behind applications.
- Interview tip: mention `GOTOOLCHAIN` when discussing reproducible CI builds.

### Project layout and package design
<!-- level: intermediate; ref: https://go.dev/doc/modules/layout -->
Go does not mandate a layout, and the official guidance is to start simple. A small service can be a single `main` package. As it grows:

- `cmd/<binary>/main.go` for each executable, keeping `main` thin (wiring, config, signal handling).
- `internal/...` for packages that must not be imported from outside the module; the compiler enforces this.
- Top-level packages for anything intentionally public in a library.
- Avoid a catch-all `pkg/` unless you have a reason; it adds a path segment without meaning.

Package design matters more than folders:

- Name packages for what they provide (`order`, `postgres`, `httpapi`), not generic buckets (`utils`, `common`, `models`, `helpers`).
- Avoid stutter: `order.Order` is fine, `order.OrderService` reads as `order.Service` would.
- Keep dependencies flowing one way: domain packages should not import transport or storage packages. Interfaces defined by consumers enable this.
- Prefer fewer, cohesive packages over many tiny ones; circular imports are compile errors and often appear when packages are split along technical layers.

```text
shop/
  go.mod
  cmd/
    api/main.go        // wires config, db, http server
    worker/main.go
  internal/
    order/             // domain types + business rules
      order.go
      service.go
    postgres/          // implements order.Repository
      orders.go
    httpapi/           // handlers, depends on order
      handlers.go
```

- Pitfall: copying a sprawling "standard layout" template into a 500-line project adds ceremony and import churn.
- Pitfall: putting all types in a `models` package couples everything to everything.
- Interview tip: talk about dependency direction and the `internal` rule, not folder names.

### gofmt, go vet and static analysis
<!-- level: basic; ref: https://pkg.go.dev/cmd/vet -->
Go's toolchain bakes in code quality checks that every Go developer is expected to use.

- `gofmt` (and `go fmt`) formats code in the one canonical style. There are no style debates in Go; editors run it on save. `goimports` additionally adds and removes imports.
- `go vet` runs analyzers that catch likely bugs which still compile: wrong `Printf` verbs, copying locks, unkeyed struct literals from other packages, unreachable code, misuse of `errors.As`, bad struct tags, loop-variable capture issues in old code, `wg.Add` inside goroutines (1.25), and test-function mistakes. `go test` runs a subset of vet automatically.
- `staticcheck` is the de facto extra linter (unused code, deprecated APIs, simplifications, subtle bugs).
- `golangci-lint` aggregates dozens of linters (errcheck, gosec, revive, staticcheck) with one config and caching; most teams run it in CI.
- `govulncheck` scans for known vulnerabilities in code paths you actually call.
- `gopls` is the language server powering editor features and also offers modernisation fixes (such as replacing loops with `slices.Contains`).

```bash
gofmt -l .                 # list unformatted files (fails CI if any)
go vet ./...
staticcheck ./...
golangci-lint run ./...
govulncheck ./...
go test -race -count=1 ./...
```

```go
func report(name string, n int) {
    fmt.Printf("%d items for %d\n", name, n) // go vet: Printf format %d has arg name of wrong type string
}
```

- Pitfall: enabling every golangci-lint linter at once produces noise and gets ignored; start with a curated set.
- Pitfall: suppressing vet warnings instead of fixing them; vet has very few false positives.
- Interview tip: describe a CI pipeline: gofmt check, vet, staticcheck/golangci-lint, race-enabled tests, govulncheck.

## 11. Testing and Benchmarks

### Table-driven tests and subtests
<!-- level: basic; ref: https://pkg.go.dev/testing -->
Go's testing is built into the toolchain. Test files end in `_test.go`; test functions are `func TestXxx(t *testing.T)`. `go test ./...` compiles and runs them. There is no assertion library in the standard library: you compare values and call `t.Errorf` (continue) or `t.Fatalf` (stop this test).

Table-driven tests list cases as a slice of structs and loop over them. Combined with `t.Run`, each case becomes a named subtest that can be run alone (`go test -run 'TestParse/negative'`) and reported separately. `t.Parallel()` marks tests or subtests that can run concurrently with others.

Test files can be in the same package (white-box, access to unexported identifiers) or `package foo_test` (black-box, only the public API).

```go
func TestParseAmount(t *testing.T) {
    tests := []struct {
        name    string
        in      string
        want    int64
        wantErr bool
    }{
        {"whole", "12", 1200, false},
        {"cents", "12.34", 1234, false},
        {"negative", "-1.00", 0, true},
        {"garbage", "abc", 0, true},
    }
    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            t.Parallel() // safe: Go 1.22 loop var semantics
            got, err := ParseAmount(tc.in)
            if (err != nil) != tc.wantErr {
                t.Fatalf("ParseAmount(%q) err = %v, wantErr %v", tc.in, err, tc.wantErr)
            }
            if got != tc.want {
                t.Errorf("ParseAmount(%q) = %d, want %d", tc.in, got, tc.want)
            }
        })
    }
}
```

Good failure messages state the input, the got value and the want value, so failures are understandable without reading the test.

- Pitfall: before Go 1.22, `t.Parallel()` subtests captured the shared loop variable and all tested the last case; old code used `tc := tc`.
- Pitfall: `t.Fatal` must be called from the test goroutine, not from goroutines the test starts.
- Interview tip: mention `go-cmp` (`cmp.Diff`) for readable diffs of structs.

### Test helpers, fixtures and cleanup
<!-- level: intermediate; ref: https://pkg.go.dev/testing#T.Cleanup -->
The `testing` package offers several features that keep tests tidy:

- `t.Helper()` marks a function as a helper so failure line numbers point to the caller, not inside the helper.
- `t.Cleanup(f)` registers teardown that runs after the test and its subtests, in LIFO order, even if the test fails. It replaces `defer` chains in setup helpers.
- `t.TempDir()` creates a directory deleted automatically.
- `t.Setenv(k, v)` sets an environment variable for the test duration (not allowed with `t.Parallel`).
- `t.Context()` (Go 1.24) returns a context cancelled just before cleanup runs.
- `t.Chdir` (Go 1.24) changes directory for the test.
- `testdata/` directories are ignored by the go tool and conventionally hold fixtures and golden files.
- `TestMain(m *testing.M)` runs package-level setup, such as starting a database container once.

```go
func newTestDB(t *testing.T) *sql.DB {
    t.Helper()
    db, err := sql.Open("pgx", os.Getenv("TEST_DATABASE_URL"))
    if err != nil {
        t.Fatalf("open db: %v", err)
    }
    t.Cleanup(func() { db.Close() })
    return db
}

func TestExportCSV(t *testing.T) {
    db := newTestDB(t)
    dir := t.TempDir()
    out := filepath.Join(dir, "orders.csv")

    if err := ExportCSV(t.Context(), db, out); err != nil {
        t.Fatal(err)
    }
    got, _ := os.ReadFile(out)
    want, _ := os.ReadFile("testdata/orders.golden.csv")
    if !bytes.Equal(got, want) {
        t.Errorf("csv mismatch:\n got: %s\nwant: %s", got, want)
    }
}
```

Use build tags (`//go:build integration`) or `testing.Short()` to separate slow integration tests from fast unit tests.

- Pitfall: tests sharing global state (package variables, a shared DB schema) break when run with `t.Parallel` or `-shuffle=on`.
- Interview tip: describe golden files with an `-update` flag to regenerate expected output.

### Testing HTTP code with httptest
<!-- level: intermediate; ref: https://pkg.go.dev/net/http/httptest -->
`net/http/httptest` makes HTTP code testable without real network ports or external services.

- `httptest.NewRecorder()` returns a `ResponseRecorder` implementing `http.ResponseWriter`. Call a handler directly with it and inspect the status, headers and body. Fast and in-process.
- `httptest.NewRequest(method, target, body)` builds a server-side request suitable for passing to a handler.
- `httptest.NewServer(handler)` starts a real server on a loopback port; use it to test HTTP clients against a fake upstream, including timeouts and malformed responses. `NewTLSServer` does the same with TLS.

Testing handlers through the router (your `ServeMux`) rather than calling the handler function directly also verifies routes, methods and path parameters.

```go
func TestGetOrder(t *testing.T) {
    store := &fakeStore{orders: map[string]Order{"42": {ID: "42", Total: 990}}}
    mux := NewRouter(store) // registers "GET /orders/{id}"

    req := httptest.NewRequest(http.MethodGet, "/orders/42", nil)
    rec := httptest.NewRecorder()
    mux.ServeHTTP(rec, req)

    if rec.Code != http.StatusOK {
        t.Fatalf("status = %d, body = %s", rec.Code, rec.Body)
    }
    var got Order
    if err := json.NewDecoder(rec.Body).Decode(&got); err != nil {
        t.Fatal(err)
    }
    if got.Total != 990 {
        t.Errorf("total = %d", got.Total)
    }
}

func TestClientTimeout(t *testing.T) {
    slow := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        time.Sleep(200 * time.Millisecond)
    }))
    defer slow.Close()

    c := NewPaymentsClient(slow.URL, 50*time.Millisecond)
    if _, err := c.Charge(t.Context(), 100); !errors.Is(err, context.DeadlineExceeded) {
        t.Fatalf("want timeout, got %v", err)
    }
}
```

- Pitfall: the sleeping handler above makes the test slow; prefer blocking on a channel or `synctest` for time-based tests.
- Interview tip: say you test clients against `httptest.NewServer` rather than mocking `http.Client`.

### Benchmarks and testing.B.Loop (Go 1.24)
<!-- level: intermediate; ref: https://pkg.go.dev/testing#B.Loop -->
Benchmarks are functions `func BenchmarkXxx(b *testing.B)` run with `go test -bench=. -benchmem`. The framework runs the body enough times to get a stable measurement and reports ns/op, and with `-benchmem` bytes/op and allocs/op.

Go 1.24 added `b.Loop()`, now the preferred style. `for b.Loop() { ... }` runs the body the right number of times, automatically excludes setup before the loop from timing, runs the benchmark function only once (instead of once per calibration round), and prevents the compiler from optimising away calls inside the loop. The older style `for i := 0; i < b.N; i++` required `b.ResetTimer()` and sink variables to avoid dead-code elimination.

Benchmark results are noisy. Run several times (`-count=10`) and compare versions with `benchstat`, which reports deltas with statistical significance.

```go
func BenchmarkJoinBuilder(b *testing.B) {
    parts := make([]string, 100)
    for i := range parts {
        parts[i] = strconv.Itoa(i)
    }
    for b.Loop() { // Go 1.24+: setup above is not timed
        var sb strings.Builder
        for _, p := range parts {
            sb.WriteString(p)
        }
        _ = sb.String()
    }
}

func BenchmarkEncode(b *testing.B) {
    for _, size := range []int{10, 1000} {
        b.Run(fmt.Sprint(size), func(b *testing.B) {
            data := makeOrders(size)
            b.ReportAllocs()
            for b.Loop() {
                _, _ = json.Marshal(data)
            }
        })
    }
}
```

```bash
go test -bench=Encode -benchmem -count=10 > old.txt
# change code
go test -bench=Encode -benchmem -count=10 > new.txt
benchstat old.txt new.txt
```

- Pitfall: benchmarking on a laptop with thermal throttling or other load gives misleading numbers.
- Pitfall: micro-benchmarks can mislead about real workloads; confirm with profiles from production-like runs.
- Interview tip: mention `-cpuprofile` on benchmarks to see where the time goes.

### Fuzzing (Go 1.18+)
<!-- level: advanced; ref: https://go.dev/doc/security/fuzz/ -->
Native fuzzing, added in Go 1.18, automatically generates inputs to find crashes, panics and broken invariants. A fuzz test is `func FuzzXxx(f *testing.F)`. You add seed inputs with `f.Add`, then call `f.Fuzz` with a function taking `*testing.T` plus parameters of supported types (strings, byte slices, integers, floats, bools).

`go test` runs only the seeds and stored corpus, so fuzz tests act as normal regression tests in CI. `go test -fuzz=FuzzXxx` runs the coverage-guided fuzzing engine, which mutates inputs and keeps those reaching new code paths. When it finds a failure, it writes the input to `testdata/fuzz/FuzzXxx/` so the failure becomes a permanent regression test.

Good fuzz targets are parsers, decoders, serialisation round-trips, validation and anything handling untrusted input. Since you do not know the expected output for random input, assert properties: no panic, decode(encode(x)) == x, output is valid, two implementations agree.

```go
func FuzzRoundTrip(f *testing.F) {
    f.Add("hello", int64(42))
    f.Add("", int64(-1))
    f.Fuzz(func(t *testing.T, name string, amount int64) {
        in := Payment{Name: name, Amount: amount}
        data, err := in.MarshalBinary()
        if err != nil {
            t.Skip() // input not representable; not a bug
        }
        var out Payment
        if err := out.UnmarshalBinary(data); err != nil {
            t.Fatalf("unmarshal of our own output failed: %v", err)
        }
        if out != in {
            t.Fatalf("round trip mismatch: %+v != %+v", in, out)
        }
    })
}
```

```bash
go test -fuzz=FuzzRoundTrip -fuzztime=60s ./payment
```

- Pitfall: fuzz functions must be deterministic and fast; network calls or global state make findings unreproducible.
- Pitfall: only one fuzz target per package can run with `-fuzz` at a time.
- Interview tip: describe the "properties, not outputs" approach.

### Testing concurrent and time-dependent code with testing/synctest (Go 1.25)
<!-- level: advanced; ref: https://pkg.go.dev/testing/synctest -->
Code involving timeouts, tickers, retries with backoff and goroutine coordination is notoriously hard to test: real sleeps make tests slow, and short sleeps make them flaky. Go 1.24 introduced `testing/synctest` as an experiment, and Go 1.25 made it generally available.

`synctest.Test(t, func(t *testing.T) { ... })` runs the function in an isolated "bubble". Inside, goroutines started by the test belong to the bubble, and the bubble has a fake clock starting at a fixed time. Time advances only when every goroutine in the bubble is durably blocked (on channels, timers, sync.WaitGroup, or `time.Sleep`), and then it jumps instantly to the next timer. `synctest.Wait()` blocks until all other bubble goroutines are durably blocked, giving a deterministic point to make assertions.

So a test of a 30-second timeout runs in microseconds and never flakes.

```go
func TestRetryBackoff(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        calls := 0
        op := func() error { calls++; return errors.New("unavailable") }

        start := time.Now()
        err := Retry(t.Context(), 3, time.Second, op) // sleeps 1s, 2s between attempts
        elapsed := time.Since(start)                  // fake clock

        if err == nil || calls != 3 {
            t.Fatalf("calls=%d err=%v", calls, err)
        }
        if elapsed != 3*time.Second {
            t.Fatalf("elapsed = %v, want 3s", elapsed)
        }
    })
}
```

Limitations: goroutines blocked on real I/O (network sockets, files, syscalls) are not "durably blocked", so use in-memory fakes such as `net.Pipe`. Mutex waits are not durable blocking either.

- Pitfall: the Go 1.24 experimental `synctest.Run` API is deprecated in favour of `synctest.Test`.
- Interview tip: this is a strong answer to "how do you test timeout logic without sleeping".
