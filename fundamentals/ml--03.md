## 5. Evaluating Models

### Confusion matrix, precision, recall and F1
<!-- level: basic; ref: https://scikit-learn.org/stable/modules/model_evaluation.html#classification-metrics -->
For classification, the confusion matrix counts four outcomes: true positives (TP), false positives (FP), true negatives (TN) and false negatives (FN). Every common metric is derived from it.

- Accuracy = (TP + TN) / all. Misleading when classes are imbalanced.
- Precision = TP / (TP + FP): of the items flagged positive, how many really are? Matters when false alarms are costly (spam filters deleting real mail, fraud blocks annoying customers).
- Recall (sensitivity) = TP / (TP + FN): of the real positives, how many did we catch? Matters when misses are costly (cancer screening, safety defects).
- F1 = harmonic mean of precision and recall, high only when both are high. F-beta weights recall beta times as much as precision.
- Specificity = TN / (TN + FP), common in medicine.

For multi-class problems, average per-class metrics: macro (each class equal, highlights minority classes), weighted (by support) or micro (pooled counts).

```python
from sklearn.metrics import confusion_matrix, classification_report, fbeta_score

y_pred = (model.predict_proba(X_val)[:, 1] >= 0.5).astype(int)
tn, fp, fn, tp = confusion_matrix(y_val, y_pred).ravel()
print(f"precision={tp/(tp+fp):.2f} recall={tp/(tp+fn):.2f}")
print(classification_report(y_val, y_pred, digits=3))
print(fbeta_score(y_val, y_pred, beta=2))      # recall-weighted
```

Precision and recall trade off through the decision threshold: lowering it catches more positives (recall up) but flags more negatives (precision down). Pick the operating point from the business cost of each error.

#### Interview tip
- Give a concrete example: "For fraud with a manual review team of fixed capacity, I optimise precision within the top N alerts; for a medical triage screen, I fix a minimum recall and maximise precision under it."

### ROC-AUC and PR-AUC
<!-- level: intermediate; ref: https://scikit-learn.org/stable/modules/model_evaluation.html#receiver-operating-characteristic-roc -->
Threshold-independent metrics summarise performance across all possible thresholds, which is useful for comparing models before choosing an operating point.

- The ROC curve plots true positive rate (recall) against false positive rate as the threshold moves. ROC-AUC is the area under it: the probability that a randomly chosen positive is scored higher than a randomly chosen negative. 0.5 is random ranking, 1.0 is perfect.
- The precision-recall (PR) curve plots precision against recall. PR-AUC, usually computed as average precision, focuses on the positive class.

Why the distinction matters: with heavy imbalance (say 0.5% positives), the false positive rate stays tiny even when the model produces many false alarms, because negatives are so numerous. ROC-AUC can look excellent (0.97) while precision at useful recall levels is poor. PR-AUC exposes this; its baseline equals the positive rate rather than 0.5.

```python
from sklearn.metrics import roc_auc_score, average_precision_score, precision_recall_curve

scores = model.predict_proba(X_val)[:, 1]
print("ROC-AUC:", roc_auc_score(y_val, scores))
print("PR-AUC :", average_precision_score(y_val, scores), "baseline:", y_val.mean())

precision, recall, thresholds = precision_recall_curve(y_val, scores)
ok = precision[:-1] >= 0.80
best = thresholds[ok][recall[:-1][ok].argmax()] if ok.any() else None   # max recall at precision >= 0.8
```

Both metrics assess ranking quality only; they say nothing about calibration or the chosen threshold.

#### Pitfalls
- Comparing PR-AUC across datasets with different positive rates is misleading because the baseline differs.
- A high AUC overall can hide poor performance in the region you actually operate in; inspect the curve or partial metrics like recall at a fixed precision.

### Decision thresholds and probability calibration
<!-- level: intermediate; ref: https://scikit-learn.org/stable/modules/calibration.html -->
Classifiers output scores; decisions need thresholds. The default 0.5 is rarely right. Choose thresholds on validation data from costs and constraints, such as "maximise expected profit" or "at least 90% recall".

Calibration is a separate property: a model is well calibrated if among cases predicted at 0.8, about 80% are actually positive. Calibration matters when probabilities feed further calculations: expected loss, pricing, combining models, or showing risk scores to people.

Many models are miscalibrated: Naive Bayes and boosted trees tend toward overconfidence, random forests avoid extremes, and class weighting or resampling distorts probabilities. Fix with post-hoc calibration on held-out data:

- Platt scaling (sigmoid): fits a logistic curve; good with small data.
- Isotonic regression: flexible monotonic mapping; needs more data.

```python
from sklearn.calibration import CalibratedClassifierCV, calibration_curve
from sklearn.metrics import brier_score_loss
from sklearn.model_selection import TunedThresholdClassifierCV

calibrated = CalibratedClassifierCV(base_model, method="isotonic", cv=5).fit(X_train, y_train)
proba = calibrated.predict_proba(X_val)[:, 1]
print("Brier score:", brier_score_loss(y_val, proba))      # lower is better
frac_pos, mean_pred = calibration_curve(y_val, proba, n_bins=10)   # reliability diagram data

tuned = TunedThresholdClassifierCV(base_model, scoring="balanced_accuracy").fit(X_train, y_train)
print(tuned.best_threshold_)        # scikit-learn 1.5+
```

#### Pitfalls
- Calibrating on the training data overfits; use cross-validation or a separate calibration set.
- When the positive rate changes in production (prior shift), calibration drifts; monitor predicted vs observed rates.

### Regression metrics
<!-- level: basic; ref: https://scikit-learn.org/stable/modules/model_evaluation.html#regression-metrics -->
Regression metrics measure the gap between predicted and actual numbers. Each emphasises different errors, so choose according to how errors cost money or trust.

- MAE (mean absolute error): average absolute error in the target's units. Easy to explain ("off by 120 rupees on average"), robust to outliers.
- RMSE (root mean squared error): penalises large errors more heavily; appropriate when big misses are disproportionately harmful.
- MAPE (mean absolute percentage error): relative error, intuitive for business, but explodes near zero actuals and penalises over- and under-prediction asymmetrically.
- R-squared: fraction of variance explained compared with predicting the mean. Can be negative for models worse than the mean; not comparable across datasets.
- Quantile (pinball) loss: evaluates quantile forecasts, such as the 90th percentile demand used for inventory buffers.

```python
from sklearn.metrics import (mean_absolute_error, root_mean_squared_error,
                             mean_absolute_percentage_error, r2_score, mean_pinball_loss)

y_pred = reg.predict(X_test)
print("MAE ", mean_absolute_error(y_test, y_pred))
print("RMSE", root_mean_squared_error(y_test, y_pred))     # scikit-learn 1.4+
print("MAPE", mean_absolute_percentage_error(y_test, y_pred))
print("R2  ", r2_score(y_test, y_pred))

residuals = y_test - y_pred
print(residuals.groupby(X_test["region"]).mean())           # bias by segment
```

Always look beyond one number: plot residuals against predictions and key features to find systematic bias (under-predicting large orders, one region consistently off). Compare with naive baselines, such as last week's value for forecasting.

#### Pitfalls
- Reporting only R-squared hides absolute error size that stakeholders care about.
- Optimising MSE yields mean predictions; if the business needs the median or a high quantile, train and evaluate with the matching loss.

### Baselines, error analysis and statistical confidence
<!-- level: intermediate; ref: https://scikit-learn.org/stable/modules/model_evaluation.html#dummy-estimators -->
A metric is meaningless without a reference. Always build baselines first:

- Trivial: predict the majority class or the mean (`DummyClassifier`, `DummyRegressor`).
- Heuristic: the existing business rule or "same as last week".
- Simple model: logistic or linear regression on obvious features.

If a complex model barely beats these, the added cost and risk may not be worth it.

Error analysis turns metrics into improvements. Slice performance by segment (region, device, customer type, input length), read misclassified examples, and categorise failure causes (label noise, missing feature, rare case). This tells you whether to collect data, fix labels or change the model.

Statistical confidence prevents chasing noise. With a 2,000-example test set, a 0.5-point accuracy difference is usually within random variation. Use bootstrap confidence intervals, paired tests on the same examples (McNemar's test for classifiers), or repeated cross-validation.

```python
from sklearn.dummy import DummyClassifier
import numpy as np

base = DummyClassifier(strategy="most_frequent").fit(X_train, y_train)
print("baseline:", base.score(X_test, y_test))

rng = np.random.default_rng(0)
a_correct = (model_a.predict(X_test) == y_test).to_numpy()
b_correct = (model_b.predict(X_test) == y_test).to_numpy()
diffs = []
for _ in range(2000):
    idx = rng.integers(0, len(y_test), len(y_test))
    diffs.append(a_correct[idx].mean() - b_correct[idx].mean())
print("95% CI of A-B:", np.percentile(diffs, [2.5, 97.5]))
```

#### Interview tip
- Interviewers value "I compared against the current rule-based system and showed a confidence interval" over "my model got 94%".

### Hyperparameter tuning
<!-- level: intermediate; ref: https://scikit-learn.org/stable/modules/grid_search.html -->
Hyperparameters are settings chosen before training (tree depth, learning rate, regularisation strength), unlike parameters learned from data. Tuning searches for values that maximise validation performance.

Methods:

- Grid search: tries every combination. Simple but wasteful as the number of hyperparameters grows.
- Random search: samples combinations; usually finds good settings faster because only a few hyperparameters matter much.
- Successive halving / Hyperband: start many configurations with small budgets (few epochs or data) and keep only the best for larger budgets.
- Bayesian optimisation (Optuna, scikit-optimize): builds a model of which settings look promising and samples there, efficient for expensive training.

```python
from scipy.stats import loguniform, randint
from sklearn.model_selection import RandomizedSearchCV, StratifiedKFold
from sklearn.ensemble import HistGradientBoostingClassifier

search = RandomizedSearchCV(
    HistGradientBoostingClassifier(early_stopping=True, random_state=0),
    param_distributions={
        "learning_rate": loguniform(0.01, 0.3),
        "max_leaf_nodes": randint(15, 127),
        "min_samples_leaf": randint(10, 200),
        "l2_regularization": loguniform(1e-3, 10),
    },
    n_iter=40, scoring="average_precision",
    cv=StratifiedKFold(5, shuffle=True, random_state=0), n_jobs=-1, random_state=0)
search.fit(X_train, y_train)
print(search.best_params_, search.best_score_)
```

Search continuous parameters like learning rates on a log scale. Keep the test set out of tuning entirely, and report the final score on it once.

#### Pitfalls
- Tuning extensively on a small validation set overfits it; the gain disappears on the test set. Use cross-validation or nested CV.
- Tuning rarely fixes bad data or features; expect small gains compared with better features or labels.

## 6. Generalisation and Feature Engineering

### Bias, variance and overfitting
<!-- level: basic; ref: https://scikit-learn.org/stable/modules/learning_curve.html -->
A model's error on new data comes from three sources: bias (systematic error from overly simple assumptions), variance (sensitivity to the particular training sample) and irreducible noise in the data.

- Underfitting (high bias): poor performance on both training and validation data. The model is too simple or features are weak.
- Overfitting (high variance): excellent training performance but much worse validation performance. The model memorised noise and quirks.

Increasing model complexity lowers bias but raises variance; the goal is the sweet spot. Modern deep networks complicate the classic U-shaped picture (very large models can generalise well when combined with lots of data and implicit regularisation), but the diagnostic approach is the same.

Learning curves diagnose which problem you have by plotting training and validation scores as training size grows:

- Both low and close together: high bias. Add features or use a more flexible model.
- Large gap between them: high variance. Get more data, regularise or simplify.

```python
from sklearn.model_selection import learning_curve
import numpy as np

sizes, train_scores, val_scores = learning_curve(
    model, X, y, cv=5, train_sizes=np.linspace(0.1, 1.0, 6), scoring="roc_auc", n_jobs=-1)
for n, tr, va in zip(sizes, train_scores.mean(1), val_scores.mean(1)):
    print(f"{n:6d} train={tr:.3f} val={va:.3f} gap={tr - va:.3f}")
```

Remedies for overfitting: more or cleaner data, regularisation, simpler models, early stopping, data augmentation, dropout, ensembling. Remedies for underfitting: richer features, more expressive models, less regularisation, longer training.

#### Interview tip
- Describe overfitting with the gap between training and validation metrics, and name the learning-curve test to decide whether more data will help.

### Regularisation: L1, L2 and elastic net
<!-- level: intermediate; ref: https://scikit-learn.org/stable/modules/linear_model.html#ridge-regression-and-classification -->
Regularisation adds a penalty on model complexity to the training objective, discouraging solutions that fit noise.

- L2 (Ridge, weight decay): adds the sum of squared weights. Shrinks all weights smoothly toward zero, spreads weight across correlated features and stabilises solutions. Rarely makes weights exactly zero.
- L1 (Lasso): adds the sum of absolute weights. Drives many weights exactly to zero, performing automatic feature selection, useful when you suspect few features matter.
- Elastic net: a mix of both, keeping L1's sparsity while handling groups of correlated features more stably.

The strength is a hyperparameter (`alpha` in Ridge/Lasso, `C = 1/strength` in logistic regression and SVMs) chosen by cross-validation. Features must be scaled, otherwise the penalty treats features unequally.

Other forms of regularisation follow the same idea of constraining models: tree depth limits and minimum leaf sizes, dropout and weight decay in neural networks, early stopping, data augmentation, and label smoothing.

```python
from sklearn.linear_model import RidgeCV, LassoCV, ElasticNetCV
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
import numpy as np

lasso = make_pipeline(StandardScaler(), LassoCV(cv=5, random_state=0)).fit(X_train, y_train)
kept = np.array(feature_names)[lasso[-1].coef_ != 0]
print(f"Lasso kept {len(kept)} of {len(feature_names)} features")

ridge = make_pipeline(StandardScaler(), RidgeCV(alphas=np.logspace(-3, 3, 13))).fit(X_train, y_train)
enet = make_pipeline(StandardScaler(), ElasticNetCV(l1_ratio=[0.2, 0.5, 0.8], cv=5)).fit(X_train, y_train)
```

#### Pitfalls
- With strongly correlated features, Lasso picks one somewhat arbitrarily; do not read its selection as "the others are irrelevant".
- Regularisation biases coefficients toward zero, so penalised coefficients are not unbiased effect estimates.

### Feature engineering
<!-- level: intermediate; ref: https://developers.google.com/machine-learning/crash-course/numerical-data -->
Feature engineering transforms raw data into inputs that make patterns easy for a model to learn. On tabular problems it often matters more than algorithm choice.

Common techniques:

- Numeric transforms: log for skewed values, ratios (debt to income), differences, binning when relationships are step-like.
- Date and time: day of week, hour, month, holidays, time since last event, cyclical encoding with sine and cosine for hour-of-day.
- Aggregations: per-entity statistics over time windows (orders in the last 7, 30 and 90 days; average basket size), computed strictly with data before the prediction time.
- Interactions: price times quantity, category crossed with region; tree models find many interactions themselves, linear models need them explicitly.
- Text: length, keyword flags, TF-IDF or embeddings.
- Domain knowledge: the best features usually come from talking to experts (for fraud: "shipping address differs from billing", "new device").

```python
import numpy as np
import pandas as pd

df["order_hour_sin"] = np.sin(2 * np.pi * df.order_ts.dt.hour / 24)
df["order_hour_cos"] = np.cos(2 * np.pi * df.order_ts.dt.hour / 24)
df["is_weekend"] = df.order_ts.dt.dayofweek >= 5
df["amount_log"] = np.log1p(df.amount)

df = df.sort_values("order_ts")
df["orders_prev_30d"] = (df.set_index("order_ts")
                           .groupby("customer_id")["order_id"]
                           .transform(lambda s: s.rolling("30D", closed="left").count())
                           .to_numpy())              # excludes the current order: no leakage
```

Deep learning reduces manual engineering for images, audio and text by learning representations, but tabular and event data still benefit greatly from thoughtful features.

#### Pitfalls
- Aggregates that include the current or future events leak the label.
- Features computed differently in training (batch SQL) and serving (application code) cause training-serving skew; share one implementation or use a feature store.

### Feature selection and importance
<!-- level: intermediate; ref: https://scikit-learn.org/stable/modules/permutation_importance.html -->
Feature selection keeps the features that help and removes the rest, which can reduce overfitting, speed up training and serving, cut data costs and simplify explanations. Feature importance tells you which features a model relies on.

Selection methods:

- Filter methods: rank features by a statistic independent of the model (mutual information, correlation, chi-squared). Fast but ignore interactions.
- Wrapper methods: search subsets by training models, such as recursive feature elimination (RFE). Accurate but expensive.
- Embedded methods: selection happens during training, such as L1 regularisation or tree-based importance thresholds.

Importance methods:

- Impurity-based importance in trees: fast but biased toward high-cardinality features and computed on training data.
- Permutation importance: shuffle one feature on validation data and measure how much the score drops. Model-agnostic and measures real dependence on held-out data.
- SHAP values: per-prediction contributions that also aggregate into global importance.

```python
from sklearn.inspection import permutation_importance
from sklearn.feature_selection import SelectFromModel, mutual_info_classif

result = permutation_importance(model, X_val, y_val, scoring="average_precision",
                                n_repeats=10, random_state=0, n_jobs=-1)
order = result.importances_mean.argsort()[::-1]
for i in order[:10]:
    print(f"{feature_names[i]:<25} {result.importances_mean[i]:.4f} +/- {result.importances_std[i]:.4f}")

mi = mutual_info_classif(X_train, y_train, random_state=0)
```

#### Pitfalls
- Correlated features share importance: permuting one barely hurts because the other compensates, so both look unimportant. Group correlated features before permuting.
- Selecting features using the full dataset before cross-validation leaks information; do selection inside the pipeline.
- Importance shows what the model uses, not what causes the outcome.

### Pipelines and ColumnTransformer
<!-- level: intermediate; ref: https://scikit-learn.org/stable/modules/compose.html -->
A scikit-learn `Pipeline` chains preprocessing steps and a final estimator into a single object with `fit` and `predict`. `ColumnTransformer` applies different preprocessing to different column groups. Together they are the safest way to build tabular models.

Why they matter:

- Leakage prevention: every step is fitted only on the training portion in each cross-validation fold.
- Reproducibility: the exact same transformations run in training and inference.
- Deployment: one serialised artifact contains preprocessing and model, reducing training-serving skew.
- Tuning: hyperparameters of any step can be searched together (`step__param`).

```python
from sklearn.compose import ColumnTransformer, make_column_selector
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import GridSearchCV
import joblib

numeric = Pipeline([("impute", SimpleImputer(strategy="median")), ("scale", StandardScaler())])
categorical = Pipeline([("impute", SimpleImputer(strategy="most_frequent")),
                        ("onehot", OneHotEncoder(handle_unknown="ignore"))])

pre = ColumnTransformer([
    ("num", numeric, make_column_selector(dtype_include="number")),
    ("cat", categorical, make_column_selector(dtype_include=["object", "category"])),
])
pipe = Pipeline([("pre", pre), ("clf", LogisticRegression(max_iter=2000))])

search = GridSearchCV(pipe, {"clf__C": [0.1, 1, 10]}, cv=5, scoring="roc_auc").fit(X_train, y_train)
joblib.dump(search.best_estimator_, "churn_model.joblib")     # one deployable artifact
```

Custom logic fits in via `FunctionTransformer` or your own class implementing `fit`/`transform`.

#### Pitfalls
- Pickled/joblib artifacts are tied to library versions; pin scikit-learn in serving and record versions with the model.
- Never load model files from untrusted sources: unpickling can execute arbitrary code.
