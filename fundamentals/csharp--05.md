## 9. Asynchronous programming
### Tasks and the task-based asynchronous pattern
<!-- level: basic; ref: https://learn.microsoft.com/dotnet/standard/asynchronous-programming-patterns/task-based-asynchronous-pattern-tap -->
A `Task` represents an operation that will complete in the future; `Task<T>` also carries a result. Tasks unify many kinds of work: I/O that completes when the OS signals it, CPU work on the thread pool, timers, or composite operations.

The Task-based Asynchronous Pattern (TAP) is the convention every modern .NET API follows:
- Async methods return `Task`, `Task<T>`, `ValueTask` or `ValueTask<T>` and end with `Async`.
- They accept a `CancellationToken` as the last parameter when cancellation makes sense.
- They may report progress via `IProgress<T>`.
- Argument validation errors are thrown synchronously; operational failures are stored in the returned task.

There are two very different kinds of async work:
- I/O-bound (HTTP calls, database queries, file reads): no thread is consumed while waiting. The OS completes the operation and the continuation resumes on a thread-pool thread. This is where async gives scalability.
- CPU-bound (image resizing, hashing big files): something must run the code. `Task.Run` offloads it to the thread pool, keeping a UI thread responsive.

```csharp
public async Task<WeatherReport> GetReportAsync(string city, CancellationToken ct)
{
    var json = await _http.GetStringAsync($"/weather/{city}", ct);   // I/O-bound
    var report = await Task.Run(() => Analyze(json), ct);             // CPU-bound offload
    return report;
}

Task<int> done = Task.FromResult(42);           // already-completed task
Task delay = Task.Delay(TimeSpan.FromSeconds(1), ct);
Task<string> winner = await Task.WhenAny(primary, fallback);
```

- Pitfall: wrapping synchronous I/O in `Task.Run` in a server just moves the blocking to another thread pool thread; it does not add scalability.
- Interview tip: "there is no thread" waiting for true async I/O; the thread returns to the pool.

### How async/await works under the hood
<!-- level: advanced; ref: https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/task-asynchronous-programming-model -->
The `async` keyword makes the compiler rewrite your method into a state machine struct. Every `await` becomes a potential suspension point, and local variables that live across awaits become fields of the state machine.

What happens at `await task`:
1. The awaiter checks `IsCompleted`. If the task already finished, execution continues synchronously with no suspension (the fast path).
2. If not, the state machine records its current state, registers a continuation with the awaiter, and returns to the caller. The first time this happens, the state machine is boxed to the heap so it can outlive the stack frame.
3. When the task completes, the continuation calls `MoveNext()` on the state machine, which jumps to the saved state and resumes after the `await`.
4. Where it resumes depends on the captured context: the UI thread in WinForms/WPF, or any thread-pool thread in ASP.NET Core and console apps.

```csharp
// What you write
public async Task<int> CountWordsAsync(string path)
{
    string text = await File.ReadAllTextAsync(path);    // suspension point
    return text.Split(' ').Length;
}

// Roughly what the compiler generates (simplified)
// struct <CountWordsAsync>d__0 : IAsyncStateMachine
// {
//     int state; AsyncTaskMethodBuilder<int> builder; string path;
//     TaskAwaiter<string> awaiter;
//     void MoveNext() { /* switch(state) ... awaiter.OnCompleted(MoveNext) ... */ }
// }
```

Exceptions thrown inside the method are captured into the returned task and rethrown when it is awaited, which is why a fault surfaces at the `await`, not the call.

.NET 10 continues work on "runtime async", moving more of this machinery into the runtime itself, but the observable behaviour of `await` stays the same.

- Pitfall: an `async` method runs synchronously until its first incomplete await; heavy work before that blocks the caller.
- Interview tip: describe async as "continuation-passing generated by the compiler", not as "runs on another thread".

### SynchronizationContext and ConfigureAwait
<!-- level: advanced; ref: https://learn.microsoft.com/dotnet/api/system.threading.tasks.task.configureawait -->
When you `await`, the continuation by default tries to resume in the context that was current before the await. That context is `SynchronizationContext.Current` if set, otherwise the current `TaskScheduler`.

- UI frameworks (WinForms, WPF, MAUI) install a context that marshals back to the single UI thread, so after `await` you can safely update controls.
- Classic ASP.NET (System.Web) had a request context.
- ASP.NET Core, console apps and worker services have no `SynchronizationContext`; continuations run on any thread-pool thread.

`ConfigureAwait(false)` tells the awaiter not to capture the context. The continuation then runs wherever the task completed, typically a pool thread.

```csharp
// Library code: does not need the caller's context
public async Task<Customer> LoadAsync(int id, CancellationToken ct)
{
    var json = await _http.GetStringAsync($"customers/{id}", ct).ConfigureAwait(false);
    return JsonSerializer.Deserialize<Customer>(json)!;
}

// UI code: must come back to the UI thread
private async void SaveButton_Click(object sender, EventArgs e)
{
    statusLabel.Text = "Saving...";
    await _service.SaveAsync(model);          // no ConfigureAwait(false) here
    statusLabel.Text = "Saved";               // runs on UI thread
}

// .NET 8+: more control
await task.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
```

Guidance:
- General-purpose libraries that might be used from UI apps should use `ConfigureAwait(false)` on every await; it avoids deadlocks for callers who block and saves a context switch.
- Application code in ASP.NET Core does not need it, since there is no context.

- Pitfall: `ConfigureAwait(false)` only affects that one await; if the task was already complete, execution continues on the original thread anyway.
- Interview tip: explain how capturing the UI context plus `.Result` on the UI thread produces a deadlock.

### Cancellation with CancellationToken
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/standard/threading/cancellation-in-managed-threads -->
.NET uses cooperative cancellation. A `CancellationTokenSource` (CTS) owns cancellation; it hands out `CancellationToken` values that code can observe. Cancelling the source sets the token, and well-behaved code stops promptly by throwing `OperationCanceledException`.

Why it matters: without cancellation, abandoned work (a closed browser tab, a shutdown request, a timed-out client) keeps burning CPU, database connections and money.

```csharp
public async Task<IReadOnlyList<Product>> SearchAsync(string term, CancellationToken ct)
{
    var results = new List<Product>();
    await foreach (var page in _api.GetPagesAsync(term, ct))     // pass it down
    {
        ct.ThrowIfCancellationRequested();                         // check in CPU loops
        results.AddRange(page.Items);
    }
    return results;
}

// Timeout combined with an outer token (for example the HTTP request's token)
using var cts = CancellationTokenSource.CreateLinkedTokenSource(requestAborted);
cts.CancelAfter(TimeSpan.FromSeconds(5));
try
{
    var items = await SearchAsync("shoes", cts.Token);
}
catch (OperationCanceledException) when (!requestAborted.IsCancellationRequested)
{
    // our own 5-second timeout fired, not the caller
    return Results.StatusCode(StatusCodes.Status504GatewayTimeout);
}

// Run cleanup when cancelled
using var reg = ct.Register(() => connection.Abort());
```

Rules:
- Accept a `CancellationToken` in every async API and pass it to every call you make.
- Dispose `CancellationTokenSource` instances you create (especially with timers).
- Treat `OperationCanceledException` as a normal outcome, not an error to alert on.

- Pitfall: passing `CancellationToken.None` (or nothing) deep in the call chain makes the whole operation uncancellable.
- Interview tip: cancellation is a request, not a kill; code must check the token to stop.

### ValueTask and avoiding async allocations
<!-- level: advanced; ref: https://learn.microsoft.com/dotnet/api/system.threading.tasks.valuetask-1 -->
`Task<T>` is a class, so every async method that completes asynchronously, or returns a result not cached by the runtime, allocates. For most code this is irrelevant. For extremely hot paths that usually complete synchronously, such as reading from an in-memory buffer or a cache hit, the allocation shows up in profiles.

`ValueTask<T>` is a struct that can wrap either a result directly (no allocation), a `Task<T>`, or an `IValueTaskSource<T>` that the implementer can pool and reuse. Stream APIs like `Stream.ReadAsync(Memory<byte>)` and channel readers use it.

```csharp
public sealed class PriceCache(IPriceApi api)
{
    private readonly ConcurrentDictionary<string, decimal> _cache = new();

    public ValueTask<decimal> GetAsync(string sku, CancellationToken ct)
    {
        if (_cache.TryGetValue(sku, out var price))
            return ValueTask.FromResult(price);           // sync path: no allocation
        return new ValueTask<decimal>(LoadAsync(sku, ct)); // async path wraps a Task
    }

    private async Task<decimal> LoadAsync(string sku, CancellationToken ct)
    {
        var p = await api.FetchAsync(sku, ct);
        _cache[sku] = p;
        return p;
    }
}
```

Strict usage rules, because a `ValueTask` may be backed by a reused object:
- Await it exactly once.
- Do not await it concurrently from multiple places.
- Do not call `.Result` before it has completed.
- If you need any of the above, call `.AsTask()` once and use that.

- Pitfall: switching every method to `ValueTask` "for performance" adds risk and can even be slower when results are usually asynchronous.
- Interview tip: the runtime already caches completed tasks for common values (`true`, `false`, small integers), so `Task<bool>` often does not allocate either.

### Async streams with IAsyncEnumerable
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/generate-consume-asynchronous-stream -->
`IAsyncEnumerable<T>` (C# 8) combines iterators with async: a method can `await` between items and `yield return` each one as it becomes available. Consumers use `await foreach`. This is the natural shape for paged APIs, database cursors, message streams, and streaming responses from a server.

```csharp
public async IAsyncEnumerable<Order> GetAllOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    string? continuation = null;
    do
    {
        var page = await _api.GetOrdersPageAsync(continuation, ct);
        foreach (var order in page.Items)
            yield return order;                 // consumer can start processing immediately
        continuation = page.NextToken;
    } while (continuation is not null);
}

await foreach (var order in GetAllOrdersAsync().WithCancellation(ct))
{
    await ExportAsync(order, ct);
}

// LINQ over async streams is built into .NET 10 (System.Linq.AsyncEnumerable)
var bigOnes = await GetAllOrdersAsync(ct)
    .Where(o => o.Total > 1000)
    .Take(50)
    .ToListAsync(ct);
```

Benefits over returning `Task<List<T>>`: memory stays flat no matter how many items there are, the first item arrives quickly, and consumers can stop early. ASP.NET Core and System.Text.Json can stream an `IAsyncEnumerable<T>` straight into a JSON array response. EF Core exposes queries as async streams with `AsAsyncEnumerable()`.

- Pitfall: `[EnumeratorCancellation]` is needed so that a token passed through `WithCancellation` reaches your method.
- Pitfall: holding a database connection open while doing slow work per item can exhaust the connection pool.
- Interview tip: before .NET 10, async LINQ operators came from the community `System.Linq.Async` package.

### Common async pitfalls: async void, sync-over-async, fire-and-forget
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/async-scenarios -->
Most production async bugs come from a handful of mistakes.

- `async void`: the caller cannot await it or catch its exceptions. An exception escapes to the synchronization context or thread pool and usually crashes the process. Only event handlers should be `async void`.
- Sync-over-async: `.Result`, `.Wait()` or `.GetAwaiter().GetResult()` block a thread while waiting. In UI apps this can deadlock; in servers it causes thread-pool starvation under load.
- Fire-and-forget: calling an async method without awaiting it. Exceptions disappear (or surface as unobserved task exceptions), and work may be cut off when the request or process ends.
- Forgetting to await inside `using`: the resource is disposed while the operation is still running.
- Lazy `async` lambdas passed to APIs that expect `Action` (for example `List.ForEach` or `Parallel.ForEach`) become `async void`.

```csharp
// Bad
public async void SendWelcome(User u) => await _mail.SendAsync(u.Email);   // crash risk
var user = _repo.GetAsync(id).Result;                                       // blocking
_ = _audit.WriteAsync(evt);                                                 // lost errors
items.ForEach(async i => await SaveAsync(i));                               // async void lambdas

// Good
public Task SendWelcomeAsync(User u, CancellationToken ct) => _mail.SendAsync(u.Email, ct);
var user2 = await _repo.GetAsync(id, ct);
await _queue.EnqueueAsync(evt, ct);              // hand off to a durable background worker
foreach (var i in items) await SaveAsync(i, ct);
```

Returning a task directly without `async`/`await` (eliding) is fine for simple pass-through methods, but inside `using` or `try` blocks keep the `await` so disposal and exception handling happen at the right time.

- Interview tip: name the analyzers that catch these (for example VSTHRD rules from Microsoft.VisualStudio.Threading.Analyzers, and CA2012 for misuse of ValueTask).

## 10. Threads, synchronisation and parallelism
### Threads and the thread pool
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/standard/threading/the-managed-thread-pool -->
A thread is an OS-scheduled execution path with its own stack. Creating one is expensive (memory for the stack, kernel objects, scheduling), so .NET maintains a shared thread pool: a set of worker threads that execute queued work items such as task continuations, timer callbacks and `Task.Run` delegates.

The pool's "hill climbing" algorithm adjusts the number of threads to maximise throughput. It starts with a minimum equal to the number of CPU cores and, when all threads are busy and work is queued, injects extra threads slowly (roughly one or two per second beyond the minimum). This is deliberate: more threads than cores usually slows CPU-bound work.

Thread-pool starvation happens when pool threads block (on `.Result`, `Thread.Sleep`, synchronous I/O or locks). Queued work, including the very continuations that would unblock them, waits for new threads that arrive slowly. Symptoms: latency climbing to seconds while CPU is low and the "ThreadPool Queue Length" counter grows.

```csharp
ThreadPool.GetMinThreads(out int worker, out int io);
Console.WriteLine($"min worker={worker}, io={io}");

// Long-running dedicated work: avoid tying up a pool thread forever
var t = new Thread(ProcessHardwareEvents) { IsBackground = true, Name = "hw-reader" };
t.Start();

// Or with tasks
_ = Task.Factory.StartNew(Loop, TaskCreationOptions.LongRunning);
```

```bash
dotnet-counters monitor -n MyApi --counters System.Runtime
# threadpool-thread-count, threadpool-queue-length, threadpool-completed-items-count
```

- Pitfall: raising `ThreadPool.SetMinThreads` hides starvation instead of fixing the blocking code; use it only as a temporary mitigation.
- Interview tip: background threads (`IsBackground = true`) do not keep the process alive; foreground threads do.

### lock, Monitor and the .NET 9 Lock type
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/csharp/language-reference/statements/lock -->
When multiple threads read and write shared state, you need mutual exclusion to keep the state consistent. The `lock` statement ensures only one thread at a time executes a block for a given lock object.

Traditionally `lock (obj)` compiles to `Monitor.Enter` / `Monitor.Exit` inside `try/finally`, using the object's header to track ownership. .NET 9 added `System.Threading.Lock`, a dedicated lock type. When the C# 13 compiler sees `lock` on a `Lock` instance, it uses the new type's faster `EnterScope()` API instead of `Monitor`.

```csharp
public sealed class BankAccount
{
    private readonly Lock _sync = new();        // .NET 9 / C# 13
    private decimal _balance;
    private readonly List<string> _history = [];

    public bool TryWithdraw(decimal amount)
    {
        lock (_sync)
        {
            if (_balance < amount) return false;   // check and act atomically
            _balance -= amount;
            _history.Add($"-{amount}");
            return true;
        }
    }
}
```

Rules for correct locking:
- Lock on a private, dedicated, read-only object; never on `this`, a `Type` or a string, which outside code could also lock.
- Keep critical sections short; never `await` inside a `lock` (the compiler forbids it) or call unknown code while holding it.
- Acquire multiple locks in a consistent global order to avoid deadlocks.
- `Monitor` locks are re-entrant: the same thread can enter again.

For read-heavy data, `ReaderWriterLockSlim` allows many concurrent readers. For async code, use `SemaphoreSlim` instead of `lock`.

- Pitfall: locking only the writes and not the reads still allows torn or stale reads of multi-field state.
- Interview tip: a deadlock needs four conditions (mutual exclusion, hold-and-wait, no preemption, circular wait); lock ordering breaks the circular wait.

### Interlocked, volatile and the memory model
<!-- level: advanced; ref: https://learn.microsoft.com/dotnet/api/system.threading.interlocked -->
Modern CPUs and compilers reorder memory operations and cache values in registers. Without synchronisation, one thread may not see another thread's writes, or may see them in a different order. The .NET memory model defines what is guaranteed; locks, `Interlocked` and `Volatile` provide the necessary memory barriers.

`Interlocked` offers lock-free atomic operations on a single variable:
- `Increment`, `Decrement`, `Add` for counters.
- `Exchange` to swap in a new value and get the old one.
- `CompareExchange` (compare-and-swap, CAS) as the building block for lock-free algorithms.

```csharp
private long _requests;
public void OnRequest() => Interlocked.Increment(ref _requests);

// Lock-free "set once"
private ConnectionInfo? _info;
public ConnectionInfo GetInfo()
{
    var existing = Volatile.Read(ref _info);
    if (existing is not null) return existing;
    var created = ConnectionInfo.Load();
    return Interlocked.CompareExchange(ref _info, created, null) ?? created;
}

// CAS loop to keep a running maximum
private int _max;
public void Observe(int value)
{
    int current;
    do
    {
        current = Volatile.Read(ref _max);
        if (value <= current) return;
    } while (Interlocked.CompareExchange(ref _max, value, current) != current);
}
```

`Volatile.Read` / `Volatile.Write` (or the `volatile` keyword) prevent certain reorderings and caching, making a flag written by one thread visible to another. They do not make compound operations like `x++` atomic.

- Pitfall: hand-written lock-free code is notoriously hard to get right; prefer `lock`, `Lazy<T>` or concurrent collections unless profiling demands more.
- Pitfall: reading a 64-bit `long` on a 32-bit process is not atomic; use `Interlocked.Read`.
- Interview tip: `Lazy<T>` with the default thread-safety mode is the simplest correct way to initialise a shared value once.

### SemaphoreSlim and async-friendly coordination
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/api/system.threading.semaphoreslim -->
`lock` cannot be held across `await`, and blocking primitives (`Mutex`, `ManualResetEvent`) tie up threads. For async code the standard tool is `SemaphoreSlim`, which supports `await WaitAsync()`.

A semaphore with a count of 1 acts as an async mutex; a larger count limits concurrency, for example "at most 5 calls to this rate-limited API at a time".

```csharp
public sealed class TokenProvider(IAuthClient auth, TimeProvider clock)
{
    private readonly SemaphoreSlim _gate = new(1, 1);
    private AccessToken? _token;

    public async Task<string> GetAsync(CancellationToken ct)
    {
        if (_token is { } t && t.ExpiresAt > clock.GetUtcNow().AddMinutes(1))
            return t.Value;                           // fast path without the lock

        await _gate.WaitAsync(ct);
        try
        {
            if (_token is { } t2 && t2.ExpiresAt > clock.GetUtcNow().AddMinutes(1))
                return t2.Value;                      // another caller refreshed it
            _token = await auth.RequestTokenAsync(ct);
            return _token.Value;
        }
        finally
        {
            _gate.Release();
        }
    }
}

// Limit concurrency
var throttle = new SemaphoreSlim(5);
var tasks = urls.Select(async url =>
{
    await throttle.WaitAsync(ct);
    try { return await http.GetStringAsync(url, ct); }
    finally { throttle.Release(); }
});
var pages = await Task.WhenAll(tasks);
```

Other coordination types: `TaskCompletionSource<T>` to create a task you complete manually (bridging callbacks to async), `CountdownEvent`, `Barrier`, and `PeriodicTimer` (.NET 6) for async periodic loops.

- Pitfall: always `Release` in `finally`, and never release more times than you waited, or the count grows and the limit stops working.
- Pitfall: `SemaphoreSlim` is not re-entrant; awaiting it twice in the same flow deadlocks.
- Interview tip: create `TaskCompletionSource` with `TaskCreationOptions.RunContinuationsAsynchronously` to avoid running awaiters inline on the completing thread.

### Concurrent collections and System.Threading.Channels
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/core/extensions/channels -->
Ordinary collections are not safe for concurrent writes. `System.Collections.Concurrent` provides thread-safe alternatives with fine-grained locking or lock-free internals:

- `ConcurrentDictionary<TKey,TValue>`: `GetOrAdd`, `AddOrUpdate`, `TryRemove`.
- `ConcurrentQueue<T>`, `ConcurrentStack<T>`, `ConcurrentBag<T>`.
- `BlockingCollection<T>`: older blocking producer/consumer wrapper.

For producer/consumer pipelines in async code, `System.Threading.Channels` is the modern choice. A channel is an async queue with a writer and a reader. Bounded channels apply backpressure: when full, `WriteAsync` waits, so a fast producer cannot exhaust memory.

```csharp
var channel = Channel.CreateBounded<ImageJob>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = false,
    SingleWriter = true,
});

// Producer
async Task ProduceAsync(CancellationToken ct)
{
    await foreach (var job in source.ReadJobsAsync(ct))
        await channel.Writer.WriteAsync(job, ct);   // waits if 100 items queued
    channel.Writer.Complete();
}

// Several consumers
async Task ConsumeAsync(CancellationToken ct)
{
    await foreach (var job in channel.Reader.ReadAllAsync(ct))
        await ResizeAsync(job, ct);
}

await Task.WhenAll(ProduceAsync(ct), ConsumeAsync(ct), ConsumeAsync(ct), ConsumeAsync(ct));

var counts = new ConcurrentDictionary<string, int>();
counts.AddOrUpdate("errors", 1, (_, old) => old + 1);
```

- Pitfall: the value factory in `ConcurrentDictionary.GetOrAdd` may run more than once under contention; wrap in `Lazy<T>` if creation must happen once.
- Pitfall: unbounded channels or queues hide a slow consumer until the process runs out of memory.
- Interview tip: channels give in-process decoupling only; work is lost on crash, so use a durable broker for critical messages.

### Data parallelism: Parallel and PLINQ
<!-- level: intermediate; ref: https://learn.microsoft.com/dotnet/standard/parallel-programming/task-parallel-library-tpl -->
When you have a large amount of independent CPU-bound work, the Task Parallel Library spreads it across cores.

- `Parallel.For` / `Parallel.ForEach`: partition a collection and run the body on multiple threads, blocking until done.
- `Parallel.ForEachAsync` (.NET 6): async-aware, with `MaxDegreeOfParallelism`; ideal for many I/O calls with a concurrency limit.
- PLINQ (`.AsParallel()`): parallel LINQ queries, with ordering and aggregation support.

```csharp
// CPU-bound: hash thousands of files
var hashes = new ConcurrentDictionary<string, string>();
Parallel.ForEach(files, new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount },
    file =>
    {
        using var stream = File.OpenRead(file);
        hashes[file] = Convert.ToHexString(SHA256.HashData(stream));
    });

// I/O-bound with a concurrency cap
await Parallel.ForEachAsync(customerIds,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (id, token) =>
    {
        var profile = await crm.GetProfileAsync(id, token);
        await store.SaveAsync(profile, token);
    });

// PLINQ
var primes = Enumerable.Range(2, 5_000_000).AsParallel()
    .Where(IsPrime)
    .Count();
```

Parallelism only helps when work per item outweighs the coordination overhead, and when items are truly independent. Shared mutable state inside the body needs synchronisation, which can erase the gains.

- Pitfall: `Parallel.ForEach` with an async lambda creates `async void` delegates; it returns before the work finishes. Use `Parallel.ForEachAsync`.
- Pitfall: running CPU-heavy parallel loops inside a web request starves other requests of threads.
- Interview tip: Amdahl's law says the serial part of a program caps the possible speedup, no matter how many cores you add.
