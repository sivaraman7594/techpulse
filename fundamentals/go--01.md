## 1. Getting Started and Core Syntax

### What Go is and why it exists
<!-- level: basic; ref: https://go.dev/doc/faq -->
Go is a statically typed, compiled language created at Google in 2007 and released as open source in 2009. It was designed for large codebases and networked services: fast compilation, a small language you can hold in your head, built-in concurrency, and a single static binary at the end.

Key design choices worth knowing:

- Compiled to native machine code with a garbage-collected runtime linked into every binary. There is no VM, so startup is fast and deployment is "copy one file".
- Composition over inheritance: there are no classes, only structs, methods and interfaces satisfied implicitly.
- Concurrency in the language: goroutines and channels are keywords and built-in types, not a library.
- Tooling is part of the language: `go build`, `go test`, `go vet`, `gofmt`, `go mod` ship with the toolchain, so every project looks and builds the same way.
- Backward compatibility: the Go 1 compatibility promise means code written for Go 1.0 still compiles; changes in behaviour are gated by the `go` line in go.mod.

```go
package main

import "fmt"

func main() {
    fmt.Println("hello, gopher")
}
```

Run with `go run .`, build with `go build -o app .`, and cross-compile with `GOOS=linux GOARCH=arm64 go build`.

- Interview tip: when asked "why Go?", talk about operational simplicity (static binaries, fast builds, predictable performance) and readability for teams, not just "it is fast".
- Pitfall: Go deliberately omits features (exceptions, inheritance, operator overloading). Fighting that by emulating Java patterns produces awkward code.

### Packages, imports and visibility
<!-- level: basic; ref: https://go.dev/doc/code -->
Every Go file starts with a `package` clause. A package is a directory of `.go` files compiled together; all files in a directory must share the same package name (test files may use the `_test` suffix). The package named `main` with a `func main()` produces an executable; any other name produces a library.

Visibility is decided by the first letter of an identifier. `Upper` names are exported (public outside the package); `lower` names are package-private. There are no `public`/`private` keywords and no file-level privacy: everything in a package can see everything else in that package.

Imports use the full module path. The compiler refuses unused imports and unused local variables, which keeps code tidy but surprises newcomers.

```go
package inventory

import (
    "errors"
    "fmt"

    "example.com/shop/internal/money" // only importable inside example.com/shop
)

var ErrOutOfStock = errors.New("out of stock") // exported

type item struct{ sku string; qty int }        // unexported

func Describe(p money.Price) string { return fmt.Sprint(p) }
```

A directory named `internal` restricts imports to code rooted at the parent of `internal`, which is the main tool for hiding implementation packages inside a module. Each package can have `init()` functions that run once, after package-level variables are initialised and after all imported packages have initialised.

- Pitfall: import cycles are compile errors. They usually signal that a shared type belongs in a lower-level package.
- Pitfall: heavy logic in `init()` makes tests and startup order hard to reason about; prefer explicit constructors.
- Interview tip: blank imports (`import _ "net/http/pprof"`) exist only to run a package's `init` side effects.

### Variables, constants and iota
<!-- level: basic; ref: https://go.dev/blog/constants -->
Go has two ways to declare variables. `var x int = 5` works anywhere, including at package level; the short form `x := 5` works only inside functions and infers the type. Every variable that is declared but not assigned holds its type's zero value, so there is no "uninitialised" state.

Constants are evaluated at compile time and can be untyped. An untyped constant such as `const big = 1 << 62` has arbitrary precision until it is used, at which point it takes on (and must fit) the required type. This is why `time.Second * 2` works without conversions.

`iota` is a counter that resets to 0 in each `const` block and increments per line. It is the idiomatic way to build enumerations and bit flags.

```go
type Level int

const (
    Debug Level = iota // 0
    Info               // 1
    Warn               // 2
    Error              // 3
)

type Perm uint8

const (
    Read Perm = 1 << iota // 1
    Write                 // 2
    Exec                  // 4
)

func main() {
    count, name := 3, "orders" // multiple short declaration
    var ratio float64          // zero value 0.0
    _ = ratio
    fmt.Println(count, name, Warn, Read|Write)
}
```

- Pitfall: `:=` inside an inner scope creates a new variable that shadows the outer one. A classic bug is `err := ...` inside an `if` block leaving the outer `err` nil. `go vet -vettool` shadow analyzers can catch it.
- Pitfall: Go has no real enums; nothing stops `Level(42)`. Validate at boundaries and give the type a `String()` method (or use `stringer`).
- Interview tip: `:=` requires at least one new variable on the left; the others are simply assigned.

### Control flow: if, for, switch
<!-- level: basic; ref: https://go.dev/ref/spec -->
Go has exactly one loop keyword, `for`, which covers C-style loops, while loops, infinite loops and `range` iteration. `if` and `switch` can start with a short statement whose variables are scoped to the block, which keeps error handling tight.

`switch` does not fall through by default (use the explicit `fallthrough` keyword if you must), cases can list several values, and a tagless `switch` is a clean replacement for if/else chains.

Since Go 1.22, `for i := range 10` ranges over an integer, and each loop iteration gets a fresh copy of the loop variable (see the loop-variable concept). Since Go 1.23, `range` also accepts iterator functions.

```go
for i := 0; i < 3; i++ { fmt.Println(i) }   // classic
for n > 0 { n /= 2 }                         // while
for i := range 5 { fmt.Println(i) }          // Go 1.22+: 0..4

for idx, v := range []string{"a", "b"} { fmt.Println(idx, v) }

if v, err := strconv.Atoi(s); err != nil {
    return fmt.Errorf("parse %q: %w", s, err)
} else if v < 0 {
    return errors.New("negative")
}

switch {
case temp < 0:
    fmt.Println("freezing")
case temp < 25, humid:
    fmt.Println("mild")
default:
    fmt.Println("hot")
}
```

Labels let `break` and `continue` target an outer loop, which matters inside `select` or `switch` within a `for`: a bare `break` there only exits the `select`/`switch`.

- Pitfall: `break` inside `select` in a `for` loop does not stop the loop. Use a labelled break or `return`.
- Interview tip: there is no ternary operator and no `while` keyword; know how to express both.

### Functions, multiple returns and closures
<!-- level: basic; ref: https://go.dev/doc/effective_go#functions -->
Functions are first-class values: they can be assigned to variables, passed as arguments, and returned. A function can return several values, which is how Go reports errors (`value, err`). Results can be named; named results are pre-initialised to zero values and are visible to deferred functions, which is handy for annotating errors.

Variadic parameters (`...T`) receive a slice. To pass an existing slice, spread it with `s...`.

A closure is a function literal that captures variables from the enclosing scope by reference. The captured variable lives as long as the closure does, so the compiler may move it to the heap (escape analysis).

```go
func divmod(a, b int) (q, r int, err error) {
    if b == 0 {
        return 0, 0, errors.New("division by zero")
    }
    return a / b, a % b, nil
}

func sum(nums ...int) int {
    total := 0
    for _, n := range nums { total += n }
    return total
}

func counter() func() int {
    n := 0
    return func() int { n++; return n } // captures n
}

func main() {
    next := counter()
    next(); fmt.Println(next())          // 2
    fmt.Println(sum([]int{1, 2, 3}...))  // 6
}
```

Arguments are always passed by value. Passing a slice, map, channel, pointer or function copies a small header or pointer, so the callee can still mutate shared underlying data.

- Pitfall: bare `return` with named results in long functions hurts readability; use it sparingly.
- Pitfall: Go has no default parameter values or overloading. Use option structs or functional options.
- Interview tip: "Go is pass-by-value, always" is the precise answer; then explain reference-like types.

### defer, panic and recover
<!-- level: intermediate; ref: https://go.dev/blog/defer-panic-and-recover -->
`defer` schedules a call to run when the surrounding function returns, whether normally or by panic. Deferred calls run in LIFO order. Arguments to a deferred call are evaluated immediately, at the `defer` statement, not when it runs. Since Go 1.14, open-coded defers made `defer` nearly free in most functions, so use it freely for cleanup.

`panic` stops normal execution, runs deferred calls up the stack, and crashes the program if nothing recovers. `recover`, called directly inside a deferred function, stops the panic and returns the panic value. It only works in the same goroutine that panicked.

```go
func copyFile(dst, src string) (err error) {
    in, err := os.Open(src)
    if err != nil { return err }
    defer in.Close()

    out, err := os.Create(dst)
    if err != nil { return err }
    defer func() {
        if cerr := out.Close(); cerr != nil && err == nil {
            err = cerr // surface the close error via named result
        }
    }()
    _, err = io.Copy(out, in)
    return err
}

func safeHandle(job func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("job panicked: %v", r)
        }
    }()
    job()
    return nil
}
```

Use panic for programmer errors and impossible states (nil map write, index out of range, broken invariants), not for expected failures like "file not found". net/http recovers panics per request, but a panic in a goroutine you start yourself will crash the whole process.

- Pitfall: `defer` inside a loop delays every cleanup until the function returns, which can exhaust file handles. Wrap the loop body in a function.
- Pitfall: `defer f.Close()` on a written file ignores the close error, which may hide a failed flush.
- Interview tip: know that `recover()` returns nil when called outside a deferred function.

## 2. Types and Values

### Basic types and zero values
<!-- level: basic; ref: https://go.dev/ref/spec#The_zero_value -->
Go's built-in types are booleans, numeric types (`int`, `int8`…`int64`, `uint`…`uint64`, `uintptr`, `float32`, `float64`, `complex64`, `complex128`), `string`, plus the aliases `byte` (`uint8`) and `rune` (`int32`). `int` and `uint` are 32 or 64 bits depending on the platform; on all mainstream 64-bit targets they are 64 bits.

Every type has a zero value: `0`, `false`, `""`, and `nil` for pointers, slices, maps, channels, functions and interfaces. Struct zero values have every field zeroed. Idiomatic Go designs types so the zero value is useful: a zero `sync.Mutex` is unlocked and ready, a zero `bytes.Buffer` is an empty buffer, and a nil slice can be appended to.

Integer overflow wraps silently (two's complement) and there is no implicit conversion between numeric types, not even `int32` to `int64`.

```go
var (
    count  int       // 0
    active bool      // false
    name   string    // ""
    tags   []string  // nil, len 0, append works
    lookup map[string]int // nil: reads ok, writes panic
)

type Counter struct {
    mu sync.Mutex
    n  map[string]int
}

func (c *Counter) Inc(k string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if c.n == nil { c.n = make(map[string]int) } // lazy init keeps zero value usable
    c.n[k]++
}
```

- Pitfall: `var x uint8 = 255; x++` gives 0 with no error. Use `math/bits` helpers or explicit checks for money and counters that must not wrap.
- Pitfall: floating point equality (`0.1+0.2 == 0.3` is false). Use integer cents for money.
- Interview tip: "make the zero value useful" is a Go proverb; mention it when discussing API design.

### Strings, bytes, runes and UTF-8
<!-- level: basic; ref: https://go.dev/blog/strings -->
A Go string is an immutable sequence of bytes, internally a two-word header (pointer, length). It usually holds UTF-8 text but nothing enforces that. `len(s)` returns bytes, not characters, and `s[i]` returns a byte.

A `rune` is an `int32` holding a Unicode code point. Ranging over a string decodes UTF-8 and yields `(byteIndex, rune)` pairs; invalid bytes come back as `U+FFFD`. Converting `[]rune(s)` gives code points, and `utf8.RuneCountInString` counts them without allocating.

Because strings are immutable, `s += x` in a loop allocates a new string each time (quadratic). Use `strings.Builder`, which grows a byte buffer and converts it to a string without copying at the end. Converting between `string` and `[]byte` normally copies, though the compiler optimises some cases (map lookups with `m[string(b)]`, comparisons).

```go
s := "héllo, 世界"
fmt.Println(len(s))                    // 14 bytes
fmt.Println(utf8.RuneCountInString(s)) // 9 runes

for i, r := range s {
    fmt.Printf("%d:%c ", i, r) // byte offsets jump on multi-byte runes
}

var b strings.Builder
for i := range 3 {
    fmt.Fprintf(&b, "row-%d;", i)
}
out := b.String()
_ = out
```

- Pitfall: slicing `s[:5]` can cut a multi-byte character in half. Slice on rune boundaries when truncating user text.
- Pitfall: a "character" a user sees (grapheme cluster, e.g. emoji with skin tone) can be several runes; Go's standard library does not segment graphemes.
- Pitfall: a small substring keeps the whole original backing array alive; use `strings.Clone` (Go 1.20) to detach it.
- Interview tip: explain the difference between byte, rune and grapheme concisely.

### Type conversions, type definitions and aliases
<!-- level: intermediate; ref: https://go.dev/ref/spec#Type_declarations -->
Go never converts between types implicitly. You write `float64(n)`, `int64(x)`, `string(rune)` or `[]byte(s)` explicitly. Numeric conversions truncate or wrap; float-to-int conversion truncates toward zero.

A type definition `type Celsius float64` creates a new, distinct named type with the same underlying type. You cannot mix `Celsius` and `float64` without conversion, which lets the compiler catch unit mistakes, and you can attach methods to the new type. Methods of the original type are not inherited.

A type alias `type MyInt = int` creates a second name for the same type, with no distinction at all. Aliases exist mainly for gradual refactoring (moving a type between packages) and, since Go 1.24, can be generic: `type Set[T comparable] = map[T]struct{}`.

```go
type Celsius float64
type Fahrenheit float64

func (c Celsius) ToF() Fahrenheit { return Fahrenheit(c*9/5 + 32) }

type UserID int64 // distinct: cannot pass an OrderID by mistake
type OrderID int64

func load(id UserID) {}

func main() {
    var o OrderID = 7
    // load(o)          // compile error
    load(UserID(o))     // explicit conversion required
    fmt.Println(Celsius(100).ToF())

    s := string(rune(65)) // "A"
    // string(65) compiles but go vet flags it: it means rune, not "65"
    fmt.Println(s, strconv.Itoa(65))
}
```

- Pitfall: `string(i)` on an integer produces a character, not decimal text. Use `strconv.Itoa`.
- Pitfall: converting a large `int64` to `int32` silently wraps; check ranges first.
- Interview tip: distinguish "defined type" (new type, can have methods) from "alias" (same type) clearly.

### Pointers
<!-- level: basic; ref: https://go.dev/tour/moretypes/1 -->
A pointer `*T` holds the address of a `T`. `&x` takes an address and `*p` dereferences. Go has no pointer arithmetic (outside `unsafe`), so pointers are safe references, and the garbage collector keeps the target alive as long as any pointer refers to it.

It is legal and common to return a pointer to a local variable: escape analysis notices that it outlives the function and allocates it on the heap. `new(T)` allocates a zeroed `T` and returns `*T`; composite literals like `&Config{}` are more common. From Go 1.26, `new` also accepts an expression, e.g. `new(30)` gives an `*int` pointing to 30, which is convenient for optional fields.

Field access auto-dereferences: `p.Name` works whether `p` is a struct or a pointer to one.

When to use pointers:

- To let a function mutate the caller's value.
- To avoid copying large structs.
- To express "optional" (nil means absent), common in JSON PATCH-style APIs.
- Because the type contains something that must not be copied, such as a `sync.Mutex`.

```go
type Account struct {
    ID      int
    Balance int64
}

func deposit(a *Account, amt int64) { a.Balance += amt }

func newAccount(id int) *Account {
    a := Account{ID: id} // escapes to heap, totally fine
    return &a
}

type Patch struct {
    Email *string `json:"email,omitempty"` // nil = not provided
}
```

- Pitfall: dereferencing a nil pointer panics. Check before use, or design so nil is impossible.
- Pitfall: pointers everywhere increase GC work and hurt cache locality; small structs are often faster passed by value.
- Interview tip: Go has pointers but not references in the C++ sense; everything is a value, some values are addresses.

### Arrays
<!-- level: basic; ref: https://go.dev/ref/spec#Array_types -->
An array has a fixed length that is part of its type: `[4]int` and `[5]int` are different, incompatible types. Arrays are values, so assigning or passing one copies every element. This makes them rarely used directly in application code, but they are the storage underneath every slice and are handy for fixed-size data such as hashes, keys and small buffers.

Arrays are comparable with `==` if their element type is comparable, so they can be map keys, unlike slices. The length can be inferred with `[...]`.

```go
var digest [32]byte = sha256.Sum256([]byte("payload"))

seen := map[[32]byte]bool{} // arrays work as map keys
seen[digest] = true

grid := [...]string{"x", "o", "x"} // len 3 inferred
copyOf := grid                     // full copy
copyOf[0] = "o"
fmt.Println(grid[0], copyOf[0])    // x o

s := digest[:8] // slicing an array gives a slice that shares its memory
fmt.Printf("%x\n", s)
```

Small arrays can live entirely on the stack and avoid heap allocation, which is why performance-sensitive code sometimes uses `var buf [64]byte` and then slices it with `buf[:0]`.

- Pitfall: passing a large array (say `[1<<20]byte`) by value copies a megabyte each call; pass a pointer or a slice.
- Pitfall: ranging over an array with `for i, v := range arr` iterates over a copy of the array when `arr` is a value, so modifications during the loop are not seen.
- Interview tip: know that you can convert a slice to an array (Go 1.20) with `[4]byte(s)`, which panics if the slice is shorter.

## 3. Slices and Maps

### Slice internals: pointer, length, capacity
<!-- level: intermediate; ref: https://go.dev/blog/slices-intro -->
A slice is a small descriptor of three words: a pointer to an element of a backing array, a length, and a capacity. `len` is how many elements you can index; `cap` is how many exist from the pointer to the end of the backing array. Slicing `s[a:b]` creates a new header pointing into the same array, so no data is copied.

Because the header is copied when passed to a function, the callee can modify elements (shared array) but cannot change the caller's length; that is why `append` returns a new slice that you must assign.

A nil slice (`var s []int`) has a nil pointer and zero len/cap. An empty slice (`[]int{}`) has a non-nil pointer. Both behave the same for `len`, `range` and `append`, but they encode differently in JSON (`null` vs `[]`) and compare differently to nil.

```go
arr := [6]int{0, 1, 2, 3, 4, 5}
s := arr[1:4]               // [1 2 3], len 3, cap 5
fmt.Println(len(s), cap(s))
s[0] = 99                   // modifies arr[1]
fmt.Println(arr)            // [0 99 2 3 4 5]

buf := make([]byte, 0, 4096) // len 0, cap 4096: pre-sized

func zeroFirst(x []int) { x[0] = 0 }          // visible to caller
func grow(x []int)      { x = append(x, 1) }  // not visible to caller
```

Use `make([]T, 0, n)` when you know roughly how many elements will be appended; it avoids repeated growth and copying.

- Pitfall: returning `nil` vs `[]T{}` matters for JSON APIs. Decide deliberately.
- Interview tip: draw the three-word header when explaining slices; interviewers love it.

### append and slice growth
<!-- level: intermediate; ref: https://pkg.go.dev/builtin#append -->
`append(s, x...)` writes into the existing backing array if there is spare capacity; otherwise it allocates a bigger array, copies the old elements, and returns a header pointing to the new array. The old array is left untouched (and garbage once unreferenced).

The growth policy is a runtime detail, but as of recent versions: small slices roughly double; beyond 256 elements, growth transitions smoothly toward about 1.25x, and the final size is rounded up to a malloc size class. Amortised, append is O(1).

```go
var ids []int
for i := range 10 {
    ids = append(ids, i)
    fmt.Println(len(ids), cap(ids)) // caps jump: 1 2 4 4 8 8 8 8 16 16
}

// Pre-size when length is known: one allocation
users := make([]User, 0, len(rows))
for _, r := range rows {
    users = append(users, toUser(r))
}

// Appending one slice to another
all := append(slices.Clone(a), b...) // avoid mutating a's backing array
```

Built-ins and helpers worth knowing: `copy(dst, src)` copies min(len) elements and handles overlap; `clear(s)` (Go 1.21) zeroes elements; `slices.Grow` (Go 1.21) reserves capacity; `slices.Clip` drops unused capacity.

- Pitfall: forgetting to assign the result (`append(s, x)` alone) is a compile error only because the result is unused; but `t := append(s, x)` while still using `s` leads to aliasing bugs (next concept).
- Pitfall: appending inside a loop that also reads by index from the same slice is fine, but taking `&s[i]` and then appending may leave your pointer referring to the old array.
- Interview tip: say "amortised constant time, because capacity grows geometrically".

### Slice aliasing and the full slice expression
<!-- level: advanced; ref: https://go.dev/ref/spec#Slice_expressions -->
Two slices that share a backing array see each other's writes, and `append` on one can overwrite elements that the other considers its own. This is the single most common slice bug in production Go code.

The scenario: you take a sub-slice `a := base[:2]` while `base` has more capacity. Appending to `a` writes into `base[2]` instead of allocating, silently changing data that another part of the program owns.

The full (three-index) slice expression `s[low:high:max]` sets the capacity to `max-low`. With `cap == len`, the next append is forced to allocate a new array, breaking the aliasing.

```go
base := []int{1, 2, 3, 4}
a := base[:2]          // len 2, cap 4
a = append(a, 99)      // writes into base[2]!
fmt.Println(base)      // [1 2 99 4]

base = []int{1, 2, 3, 4}
b := base[:2:2]        // len 2, cap 2
b = append(b, 99)      // must allocate
fmt.Println(base)      // [1 2 3 4] untouched

// Returning an internal slice safely
func (q *Queue) Snapshot() []Job {
    return slices.Clone(q.items) // caller cannot corrupt q.items
}
```

A related memory issue: a tiny sub-slice of a huge slice keeps the whole backing array reachable. If you keep only a few elements of a large read, copy them out.

- Pitfall: functions that both receive a slice and append to it should document whether they may write into the caller's spare capacity.
- Pitfall: when removing elements with `slices.Delete` (Go 1.21), since Go 1.22 the vacated tail elements are zeroed, so stale references in other aliases can see zero values.
- Interview tip: show the `[:len:len]` trick; it signals real-world experience.

### Maps: usage and internals
<!-- level: intermediate; ref: https://go.dev/blog/maps -->
A map is a hash table from comparable keys to values. Keys can be any type that supports `==`: numbers, strings, pointers, channels, arrays and structs of comparable fields, and interfaces (panicking at runtime if the dynamic type is not comparable). Slices, maps and functions cannot be keys.

A map value is a pointer to a runtime structure, so passing a map to a function shares it. The zero value is nil: reading returns zero values, but writing panics. Create maps with `make(map[K]V, hint)` or a literal.

Lookups return the zero value for missing keys; use the comma-ok form to distinguish "absent" from "present with zero value".

Internals: since Go 1.24 the runtime uses a Swiss-table design (groups of 8 slots with a control word of hash fragments, probed with SIMD-like bit tricks), replacing the older bucket-and-overflow-chain implementation. It gives faster lookups and lower memory for large maps. Maps grow incrementally but never shrink; deleting all entries leaves the memory allocated.

```go
stock := map[string]int{"apple": 5}
stock["pear"] += 3                 // missing key reads 0, then writes 3

if qty, ok := stock["kiwi"]; !ok {
    fmt.Println("no kiwi", qty)    // qty is 0
}
delete(stock, "apple")             // no-op if absent

type key struct{ tenant, sku string } // composite key
prices := make(map[key]float64, 1000)
prices[key{"acme", "A1"}] = 9.99

set := map[string]struct{}{}       // zero-byte values: idiomatic set
set["x"] = struct{}{}
```

- Pitfall: you cannot take the address of a map element (`&m[k]` is illegal) because entries move when the map grows. Store pointers or reassign the whole struct.
- Pitfall: a long-lived map that once held millions of keys keeps that memory; rebuild it to release memory.
- Interview tip: mention Swiss tables (Go 1.24) to show you follow the runtime.

### Map iteration order and concurrent access
<!-- level: intermediate; ref: https://go.dev/doc/faq#atomic_maps -->
Map iteration order is unspecified, and the runtime deliberately randomises the starting point on every `range` so programs cannot accidentally depend on it. If you need sorted output, collect the keys and sort them, or since Go 1.23 use `slices.Sorted(maps.Keys(m))`.

Adding entries during iteration may or may not produce them in the same loop; deleting entries not yet reached means they will not be produced. Both are allowed but rarely a good idea.

Maps are not safe for concurrent use when at least one goroutine writes. The runtime detects many unsynchronised accesses and kills the process with "fatal error: concurrent map writes" (or "concurrent map read and map write"). This is a fatal error, not a panic, so `recover` cannot catch it.

Options for concurrent maps:

- A `map` protected by `sync.Mutex` or `sync.RWMutex`: the default choice.
- `sync.Map`: optimised for keys written once and read many times, or disjoint key sets per goroutine. It is untyped (`any`) and usually slower for general workloads.
- Sharding: N maps each with its own lock, keyed by hash, for very high contention.

```go
type Cache struct {
    mu sync.RWMutex
    m  map[string][]byte
}

func (c *Cache) Get(k string) ([]byte, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.m[k]
    return v, ok
}

func (c *Cache) Set(k string, v []byte) {
    c.mu.Lock()
    c.m[k] = v
    c.mu.Unlock()
}

keys := slices.Sorted(maps.Keys(c.m)) // Go 1.23+, deterministic order
```

- Pitfall: tests that compare map-derived output (JSON is fine, `encoding/json` sorts map keys) but custom printing loops produce flaky results.
- Interview tip: say "fatal error, not recoverable" for concurrent map writes.

### The slices, maps and cmp packages
<!-- level: basic; ref: https://pkg.go.dev/slices -->
Go 1.21 added generic standard-library packages that replaced a lot of hand-written loops and `sort.Slice` calls. Go 1.23 extended them with iterator-based functions.

slices highlights:

- `slices.Contains`, `Index`, `IndexFunc`, `Equal`, `Max`, `Min`.
- `slices.Sort`, `SortFunc`, `SortStableFunc`, `BinarySearch`.
- `slices.Insert`, `Delete`, `Compact`, `Reverse`, `Clone`, `Grow`, `Clip`.
- Go 1.23: `slices.All`, `Values`, `Collect`, `Sorted`, `Chunk` (1.23) working with `iter.Seq`.

maps highlights: `maps.Clone`, `Copy`, `DeleteFunc`, `Equal`, and (Go 1.23) `Keys`/`Values`/`All` returning iterators.

cmp provides `cmp.Compare`, `cmp.Less` and `cmp.Or` (Go 1.22), which returns its first non-zero argument and is perfect for multi-key sorts and defaults. Go 1.21 also added built-in `min`, `max` and `clear`.

```go
type Order struct {
    Customer string
    Total    float64
}

slices.SortFunc(orders, func(a, b Order) int {
    return cmp.Or(
        cmp.Compare(a.Customer, b.Customer),
        cmp.Compare(b.Total, a.Total), // descending
    )
})

big := slices.IndexFunc(orders, func(o Order) bool { return o.Total > 1000 })
port := cmp.Or(os.Getenv("PORT"), "8080") // default value

for chunk := range slices.Chunk(ids, 500) { // batch DB writes, Go 1.23
```

- Pitfall: `slices.Sort` is not stable; use `SortStableFunc` when equal elements must keep their order.
- Pitfall: `slices.Compact` only removes adjacent duplicates; sort first.
- Interview tip: preferring these packages over hand-rolled loops shows you write modern Go.
