## 4. Structs and Methods

### Structs, literals and struct tags
<!-- level: basic; ref: https://go.dev/ref/spec#Struct_types -->
A struct groups named fields into a single value. Structs are value types: assignment copies every field. Two structs are comparable with `==` if all their fields are comparable, which makes small structs good map keys.

Composite literals create values. Always use field names (`User{ID: 1}`) rather than positional literals for structs from other packages; `go vet` warns about unkeyed literals because adding a field would break them.

Struct tags are string metadata attached to fields and read via reflection. They drive `encoding/json`, `encoding/xml`, database mappers and validators. The format is a space-separated list of `key:"value"` pairs.

Field order affects memory layout: the compiler inserts padding to align fields, so ordering from largest to smallest alignment can shrink a struct. The empty struct `struct{}` takes zero bytes, which is why it is used for sets and signal-only channels.

```go
type User struct {
    ID        int64     `json:"id" db:"id"`
    Email     string    `json:"email"`
    Password  string    `json:"-"`                  // never serialised
    Nickname  string    `json:"nickname,omitempty"` // omit if ""
    CreatedAt time.Time `json:"created_at,omitzero"` // Go 1.24: omit zero time
}

u := User{ID: 1, Email: "a@b.com"}
p := &User{Email: "c@d.com"} // pointer to new struct
p.Nickname = "cd"            // auto-dereference

// Anonymous struct: handy for one-off JSON payloads and table tests
resp := struct {
    OK    bool   `json:"ok"`
    Error string `json:"error,omitempty"`
}{OK: true}
_ = resp
```

- Pitfall: `omitempty` does not consider a zero `time.Time` or zero struct "empty"; Go 1.24's `omitzero` fixes that (and uses an `IsZero` method if present).
- Pitfall: tags are only checked at runtime. A typo like `json:"email "` silently misbehaves; `go vet` catches malformed tags.
- Interview tip: mention that unexported fields are invisible to `encoding/json`.

### Embedding and composition
<!-- level: intermediate; ref: https://go.dev/doc/effective_go#embedding -->
Go has no inheritance. Instead, a struct can embed another type by listing it without a field name. The embedded type's fields and methods are promoted, so you can call them on the outer struct as if they were its own. This is composition with syntactic sugar: the outer type has a field named after the embedded type, and promoted calls are rewritten to go through it.

Embedding also affects interfaces: if the embedded type's methods satisfy an interface, the outer type does too. Interfaces can embed other interfaces to compose them (`io.ReadWriter` embeds `io.Reader` and `io.Writer`).

If the outer type defines a method with the same name, it shadows the promoted one; the embedded method is still reachable explicitly. If two embedded types at the same depth provide the same name, using it is an ambiguity compile error.

```go
type Logger struct{ prefix string }

func (l Logger) Logf(format string, args ...any) {
    log.Printf(l.prefix+format, args...)
}

type OrderService struct {
    Logger            // embedded: OrderService gets Logf
    repo   *OrderRepo
}

func (s *OrderService) Place(o Order) error {
    s.Logf("placing order %d", o.ID) // promoted
    return s.repo.Save(o)
}

// Decorating an interface by embedding it
type countingWriter struct {
    io.Writer
    n int
}

func (c *countingWriter) Write(p []byte) (int, error) {
    n, err := c.Writer.Write(p) // explicit call to embedded
    c.n += n
    return n, err
}
```

- Pitfall: embedding is not subtyping. A function taking `Logger` will not accept `OrderService`.
- Pitfall: embedding a `sync.Mutex` exports `Lock`/`Unlock` on your type if the struct is exported; usually use a named field `mu sync.Mutex` instead.
- Pitfall: embedding an interface in a struct and not setting it gives a nil field; calling an unimplemented method panics.
- Interview tip: describe it as "delegation the compiler writes for you".

### Methods: value vs pointer receivers
<!-- level: basic; ref: https://go.dev/doc/faq#methods_on_values_or_pointers -->
A method is a function with a receiver. Methods can be declared on any named type defined in the same package, not just structs (`type Celsius float64` can have methods).

A value receiver `func (t T) M()` gets a copy; changes do not affect the caller. A pointer receiver `func (t *T) M()` gets the address, so it can mutate the original and avoids copying.

Choose a pointer receiver when:

- The method mutates the receiver.
- The struct is large, so copying is costly.
- The struct contains fields that must not be copied (`sync.Mutex`, `bytes.Buffer` you are writing to).
- For consistency: if any method needs a pointer receiver, make them all pointer receivers.

Value receivers suit small immutable types like `time.Time`, points or money amounts.

Go automatically takes the address or dereferences when calling: `v.PtrMethod()` works on an addressable variable `v`, and `p.ValueMethod()` works on a pointer. Map elements are not addressable, so `m[k].PtrMethod()` fails to compile.

```go
type Cart struct {
    Items []Item
    total int64
}

func (c *Cart) Add(it Item) { // mutates
    c.Items = append(c.Items, it)
    c.total += it.Price
}

func (c *Cart) Total() int64 { return c.total } // pointer for consistency

type Money int64

func (m Money) String() string { return fmt.Sprintf("%d.%02d", m/100, m%100) }

var cart Cart
cart.Add(Item{Price: 250}) // Go takes &cart automatically
```

- Pitfall: a value-receiver method that "updates" a field silently updates a copy. Linters such as staticcheck flag some of these.
- Pitfall: `go vet` copylocks warns when a struct containing a mutex is passed by value.
- Interview tip: tie the answer to method sets, the next concept.

### Method sets and interface satisfaction
<!-- level: intermediate; ref: https://go.dev/ref/spec#Method_sets -->
The method set of a type decides which interfaces it satisfies. The rule:

- The method set of `T` contains methods with value receivers.
- The method set of `*T` contains methods with value receivers and pointer receivers.

So if `Save` has a pointer receiver, a `*Repo` implements `Saver`, but a `Repo` value does not. The reason: an interface holding a value stores a copy, and that copy is not addressable, so calling a pointer method on it could only mutate the hidden copy, which would be surprising. Go simply forbids it.

This explains a common compile error: "Repo does not implement Saver (method Save has pointer receiver)".

```go
type Saver interface{ Save() error }

type Repo struct{ path string }

func (r *Repo) Save() error { return os.WriteFile(r.path, nil, 0o644) }

var _ Saver = (*Repo)(nil) // compile-time assertion: *Repo implements Saver
// var _ Saver = Repo{}    // compile error

func persist(s Saver) error { return s.Save() }

func main() {
    r := Repo{path: "/tmp/x"}
    _ = persist(&r) // OK
    // persist(r)   // compile error
}
```

The `var _ Iface = (*T)(nil)` line is an idiomatic zero-cost check that a type keeps implementing an interface as code evolves.

- Pitfall: the automatic `&` that lets you call `r.Save()` on a variable does not apply to interface satisfaction. Know the difference between "callable" and "in the method set".
- Interview tip: be ready to explain why the rule exists (addressability of values stored in interfaces), not just state it.

### Constructors and functional options
<!-- level: intermediate; ref: https://go.dev/doc/effective_go#composite_literals -->
Go has no constructors. By convention, a package exposes `NewThing(...) *Thing` (or `New` if the package has one main type) that validates inputs and sets defaults. When the zero value is usable, no constructor is needed at all.

As configuration grows, long parameter lists become unreadable. Two idioms handle optional settings:

- A config struct: `NewServer(Config{Addr: ":80", ReadTimeout: 5*time.Second})`. Simple, self-documenting, zero values mean defaults.
- Functional options: variadic functions that mutate a private options struct. They keep the call site short, allow defaults, validation and future additions without breaking callers. Widely used in gRPC and cloud SDKs.

```go
type Server struct {
    addr    string
    timeout time.Duration
    logger  *slog.Logger
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithLogger(l *slog.Logger) Option   { return func(s *Server) { s.logger = l } }

func NewServer(addr string, opts ...Option) (*Server, error) {
    if addr == "" {
        return nil, errors.New("addr required")
    }
    s := &Server{addr: addr, timeout: 30 * time.Second, logger: slog.Default()}
    for _, o := range opts {
        o(s)
    }
    return s, nil
}

srv, err := NewServer(":8080", WithTimeout(5*time.Second))
```

- Pitfall: functional options are overkill for two or three settings; a config struct is easier to read and to document.
- Pitfall: returning an interface from a constructor ("accept interfaces, return structs" is the guideline) hides useful methods and complicates evolution.
- Interview tip: quote "accept interfaces, return concrete types" and explain why.

## 5. Interfaces

### Implicit interfaces and small interface design
<!-- level: basic; ref: https://go.dev/doc/effective_go#interfaces -->
An interface type lists method signatures. Any type that has those methods satisfies the interface automatically; there is no `implements` keyword. This structural typing decouples packages: a consumer can define the interface it needs, and existing types from other packages satisfy it without knowing about it.

Idiomatic Go interfaces are small, often one method, named with an "-er" suffix: `io.Reader`, `io.Writer`, `fmt.Stringer`, `http.Handler`, `sort.Interface`. Small interfaces are easy to implement, fake in tests and compose.

The guideline "define interfaces where they are used, not where they are implemented" means a `service` package declares `type UserStore interface { Get(ctx, id) (User, error) }` with just the methods it calls, and the `postgres` package returns a concrete `*Store` type.

```go
// In package billing: only what billing needs
type InvoiceSender interface {
    Send(ctx context.Context, inv Invoice) error
}

type Biller struct{ sender InvoiceSender }

// In tests: a trivial fake satisfies it implicitly
type fakeSender struct{ sent []Invoice }

func (f *fakeSender) Send(_ context.Context, inv Invoice) error {
    f.sent = append(f.sent, inv)
    return nil
}

// Composition of standard interfaces
func checksum(r io.Reader) (string, error) {
    h := sha256.New() // hash.Hash is an io.Writer
    if _, err := io.Copy(h, r); err != nil {
        return "", err
    }
    return hex.EncodeToString(h.Sum(nil)), nil
}
```

`checksum` works with files, network connections, HTTP bodies, gzip readers and `strings.Reader` alike: that is the payoff of tiny interfaces.

- Pitfall: creating an interface for every struct "for mocking" before there is a second implementation adds indirection with no benefit.
- Pitfall: very large interfaces (20 methods) are hard to fake and couple consumers to everything.
- Interview tip: "the bigger the interface, the weaker the abstraction" is a Go proverb worth quoting.

### Interface values internals and the nil-interface trap
<!-- level: advanced; ref: https://go.dev/doc/faq#nil_error -->
At runtime an interface value is two words. For non-empty interfaces (an `iface`), the first word points to an itab containing the dynamic type and a table of method pointers; the second points to (or, for pointer-shaped values, holds) the data. For the empty interface `any` (an `eface`), the first word is just the type descriptor. Method calls through an interface load the function pointer from the itab, which is an indirect call that usually cannot be inlined.

An interface is nil only if both words are nil. If you store a nil `*MyError` in an `error`, the type word is set, so `err != nil` is true. This is the most famous Go gotcha.

Storing a non-pointer value in an interface generally copies it to the heap (small integers and some constants are special-cased), which is why boxing in hot paths causes allocations.

```go
type MyError struct{ Code int }

func (e *MyError) Error() string { return fmt.Sprint("code ", e.Code) }

func validate(ok bool) error {
    var e *MyError // nil pointer
    if !ok {
        e = &MyError{Code: 400}
    }
    return e // BUG: returns non-nil interface holding nil pointer
}

func validateFixed(ok bool) error {
    if !ok {
        return &MyError{Code: 400}
    }
    return nil // untyped nil: both words nil
}

func main() {
    fmt.Println(validate(true) != nil)      // true (!)
    fmt.Println(validateFixed(true) != nil) // false
}
```

- Pitfall: functions should return the `error` interface, not a concrete pointer error type, to avoid this trap.
- Pitfall: comparing two interfaces whose dynamic types are not comparable (e.g. holding slices) panics at runtime.
- Interview tip: draw the (type, value) pair and explain why `(*MyError)(nil)` inside an error is non-nil.

### Type assertions and type switches
<!-- level: intermediate; ref: https://go.dev/tour/methods/15 -->
A type assertion `x.(T)` extracts the concrete value from an interface. If `T` is a concrete type, it checks that the dynamic type is exactly `T`; if `T` is an interface, it checks that the dynamic type implements `T`. The single-result form panics on failure; the comma-ok form returns false instead.

A type switch branches on the dynamic type. In each case, the variable has that case's type; in a multi-type case or `default`, it keeps the interface type.

Asserting to an interface is how optional behaviour is discovered at runtime, a pattern used throughout the standard library: `io.Copy` checks whether the source implements `io.WriterTo` or the destination implements `io.ReaderFrom` to use a faster path.

```go
func describe(v any) string {
    switch x := v.(type) {
    case nil:
        return "nil"
    case int, int64:
        return fmt.Sprintf("integer %v", x) // x is any here
    case string:
        return "string of len " + strconv.Itoa(len(x))
    case fmt.Stringer:
        return "stringer: " + x.String()
    case error:
        return "error: " + x.Error()
    default:
        return fmt.Sprintf("other %T", x)
    }
}

// Optional interface upgrade
type Flusher interface{ Flush() error }

func finish(w io.Writer) error {
    if f, ok := w.(Flusher); ok {
        return f.Flush()
    }
    return nil
}
```

- Pitfall: for errors, never type-assert directly on a returned error; wrapped errors will not match. Use `errors.As`.
- Pitfall: case order matters in type switches when cases are interfaces; the first match wins.
- Pitfall: heavy use of `any` plus type switches often means generics or a proper interface would be cleaner.
- Interview tip: mention optional-interface upgrades like `http.Flusher` and `io.WriterTo`.

### The empty interface, any, and reflection basics
<!-- level: intermediate; ref: https://go.dev/blog/laws-of-reflection -->
`interface{}` has no methods, so every type satisfies it. Since Go 1.18, `any` is a predeclared alias for `interface{}`. It is used where values of arbitrary type must flow through: `fmt.Println(args ...any)`, JSON decoding into `map[string]any`, context values, and generic containers before generics existed.

Using `any` gives up compile-time type checking, so you must recover types with assertions at runtime. Prefer generics or specific interfaces when the set of types is known.

Reflection (`reflect` package) inspects types and values at runtime: `reflect.TypeOf(v)` and `reflect.ValueOf(v)`. It powers `encoding/json`, `fmt`, ORMs and validators. The three laws: reflection goes from interface value to reflection object, back again with `Interface()`, and to modify a value through reflection it must be settable (you must reflect on a pointer).

```go
type Config struct {
    Host string `env:"HOST"`
    Port int    `env:"PORT"`
}

func loadEnv(dst any) error {
    v := reflect.ValueOf(dst)
    if v.Kind() != reflect.Pointer || v.Elem().Kind() != reflect.Struct {
        return errors.New("need pointer to struct")
    }
    v = v.Elem()
    t := v.Type()
    for i := range t.NumField() {
        key := t.Field(i).Tag.Get("env")
        raw, ok := os.LookupEnv(key)
        if !ok { continue }
        switch f := v.Field(i); f.Kind() {
        case reflect.String:
            f.SetString(raw)
        case reflect.Int:
            n, err := strconv.Atoi(raw)
            if err != nil { return fmt.Errorf("%s: %w", key, err) }
            f.SetInt(int64(n))
        }
    }
    return nil
}
```

- Pitfall: reflection is slow (allocations, no inlining) and panics on misuse; keep it at the edges (config, serialisation), never in hot loops.
- Pitfall: JSON numbers decoded into `any` become `float64`, losing precision for large IDs; use `json.Decoder.UseNumber`.
- Interview tip: "clear is better than clever; reflection is never clear" is another Go proverb.

### Standard interfaces you must know
<!-- level: basic; ref: https://pkg.go.dev/io -->
A handful of standard interfaces glue the ecosystem together. Implementing them lets your types plug into hundreds of library functions.

- `fmt.Stringer`: `String() string`, used by `%v` and `Println`.
- `error`: `Error() string`.
- `io.Reader`: `Read(p []byte) (n int, err error)`. Reads up to `len(p)` bytes; may return n > 0 together with `io.EOF`. Callers must process the n bytes before checking err.
- `io.Writer`: `Write(p []byte) (n int, err error)`. Must return a non-nil error if n < len(p).
- `io.Closer`, and combinations `io.ReadCloser`, `io.ReadWriter`.
- `sort.Interface` (`Len`, `Less`, `Swap`), largely replaced by `slices.SortFunc`.
- `http.Handler`: `ServeHTTP(ResponseWriter, *Request)`.
- `json.Marshaler` / `json.Unmarshaler` and `encoding.TextMarshaler` for custom encoding.
- `context.Context` itself is an interface.

```go
type Temperature float64

func (t Temperature) String() string { return fmt.Sprintf("%.1f°C", float64(t)) }

// A Reader that upper-cases another reader (streaming, constant memory)
type upperReader struct{ r io.Reader }

func (u upperReader) Read(p []byte) (int, error) {
    n, err := u.r.Read(p)
    copy(p[:n], bytes.ToUpper(p[:n]))
    return n, err
}

func main() {
    fmt.Println(Temperature(21.5)) // 21.5°C
    io.Copy(os.Stdout, upperReader{strings.NewReader("hello\n")})
}
```

Streaming through `io.Reader`/`io.Writer` chains (file to gzip to hash to network) keeps memory flat regardless of payload size.

- Pitfall: calling `String()` on the value inside `String()` via `fmt.Sprintf("%v", t)` recurses forever; convert to the underlying type first, as above.
- Pitfall: ignoring the `n` returned with `io.EOF` drops the final chunk of data.
- Interview tip: be able to write a correct `io.Reader` loop from memory.

## 6. Error Handling

### Errors are values
<!-- level: basic; ref: https://go.dev/blog/error-handling-and-go -->
Go has no exceptions for ordinary failures. A function that can fail returns an `error` as its last result, and the caller checks it immediately. `error` is just an interface with one method, `Error() string`, so errors are ordinary values you can store, compare, wrap and pass around.

The explicit `if err != nil` style is verbose but makes every failure path visible in the code and in reviews. The convention is: handle the error, or return it with added context; do not do both (logging and returning causes duplicate log lines up the stack).

Create simple errors with `errors.New` or `fmt.Errorf`. When a function returns an error, the other results should generally be treated as invalid unless documented otherwise (`io.Reader` is a notable exception).

```go
func loadConfig(path string) (*Config, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return nil, fmt.Errorf("load config %s: %w", path, err)
    }
    var cfg Config
    if err := json.Unmarshal(data, &cfg); err != nil {
        return nil, fmt.Errorf("parse config %s: %w", path, err)
    }
    if cfg.Port == 0 {
        return nil, errors.New("config: port is required")
    }
    return &cfg, nil
}

func main() {
    cfg, err := loadConfig("app.json")
    if err != nil {
        log.Fatal(err) // load config app.json: open app.json: no such file or directory
    }
    _ = cfg
}
```

Error strings are lower-case and without trailing punctuation, because they get concatenated into chains like the one above.

- Pitfall: `_ = doThing()` or ignoring the error result hides failures; linters like errcheck catch it.
- Pitfall: returning `err` without context produces messages like "EOF" with no clue where it came from.
- Interview tip: argue the trade-off: verbosity in exchange for explicit, local control flow.

### Wrapping with %w, errors.Is and errors.As
<!-- level: intermediate; ref: https://go.dev/blog/go1.13-errors -->
Since Go 1.13, an error can wrap another error. `fmt.Errorf("...: %w", err)` produces an error whose `Unwrap()` method returns the original. This builds a chain: context at each layer, original cause at the bottom.

You inspect chains with two functions:

- `errors.Is(err, target)` walks the chain and reports whether any error equals `target` (or has an `Is` method that says so). Use it for sentinel errors.
- `errors.As(err, &target)` walks the chain looking for an error assignable to the target's type and, if found, sets it. Use it for error types carrying data.

Go 1.20 allowed multiple `%w` verbs in one `Errorf` and `Unwrap() []error`, so a chain can become a tree; `Is` and `As` search it depth-first.

```go
var ErrNotFound = errors.New("not found")

type ValidationError struct{ Field string }

func (e *ValidationError) Error() string { return "invalid " + e.Field }

func getUser(id int) (*User, error) {
    if id <= 0 {
        return nil, &ValidationError{Field: "id"}
    }
    return nil, fmt.Errorf("getUser %d: %w", id, ErrNotFound)
}

func handler(w http.ResponseWriter, id int) {
    _, err := getUser(id)
    var ve *ValidationError
    switch {
    case errors.Is(err, ErrNotFound):
        http.Error(w, "no such user", http.StatusNotFound)
    case errors.As(err, &ve):
        http.Error(w, ve.Error(), http.StatusBadRequest)
    case err != nil:
        http.Error(w, "internal error", http.StatusInternalServerError)
    }
}
```

Wrapping makes the wrapped error part of your API: callers may start depending on `errors.Is(err, sql.ErrNoRows)`. Use `%v` instead of `%w` when you deliberately want to hide the cause.

- Pitfall: `err == ErrNotFound` fails once anyone wraps the error; always use `errors.Is`.
- Pitfall: passing a non-pointer to `errors.As` panics; the second argument must be a pointer to an interface or to a type implementing error.
- Interview tip: Go 1.26 adds generic `errors.AsType[T]`, which returns the match directly; mention it if the team is on a recent toolchain.

### Sentinel errors vs custom error types
<!-- level: intermediate; ref: https://pkg.go.dev/errors -->
There are three common ways to let callers react to specific failures:

1. Sentinel errors: exported package variables like `io.EOF`, `sql.ErrNoRows`, `fs.ErrNotExist`. Callers check with `errors.Is`. Simple, but they carry no data and become part of your public API forever.
2. Custom error types: structs implementing `error`, like `*fs.PathError` or `*net.OpError`. They carry structured data (path, operation, status code). Callers use `errors.As`.
3. Behaviour checks: callers ask "is this temporary/retryable?" through an interface (`interface{ Timeout() bool }`), without depending on concrete types. This keeps coupling lowest.

A custom type can also implement `Is(target error) bool` to match a sentinel, giving callers both styles.

```go
var ErrConflict = errors.New("conflict")

type HTTPError struct {
    Status int
    Body   string
}

func (e *HTTPError) Error() string { return fmt.Sprintf("http %d: %s", e.Status, e.Body) }

func (e *HTTPError) Is(target error) bool {
    return target == ErrConflict && e.Status == http.StatusConflict
}

func (e *HTTPError) Temporary() bool { return e.Status >= 500 || e.Status == 429 }

func shouldRetry(err error) bool {
    var t interface{ Temporary() bool }
    return errors.As(err, &t) && t.Temporary()
}

err := fmt.Errorf("create order: %w", &HTTPError{Status: 409})
fmt.Println(errors.Is(err, ErrConflict), shouldRetry(err)) // true false
```

- Pitfall: comparing error strings (`strings.Contains(err.Error(), "timeout")`) is fragile and breaks on message changes or localisation.
- Pitfall: exporting dozens of sentinels locks you into supporting them; export only those callers genuinely need.
- Interview tip: frame the choice as "how much does the caller need to know, and how much coupling am I willing to accept".

### errors.Join and aggregating failures
<!-- level: intermediate; ref: https://pkg.go.dev/errors#Join -->
Sometimes several independent operations fail and you want to report all of them: validating many fields, closing several resources, or running cleanup steps. Go 1.20 added `errors.Join(errs...)`, which returns an error wrapping all non-nil arguments (or nil if all are nil). Its message joins each error's text with newlines, and `errors.Is`/`errors.As` search every branch.

This replaced ad-hoc multi-error libraries for most uses. It pairs well with `defer` to combine a function's main error with a close error.

```go
func validate(u User) error {
    var errs []error
    if u.Email == "" {
        errs = append(errs, errors.New("email is required"))
    }
    if u.Age < 0 {
        errs = append(errs, fmt.Errorf("age %d: %w", u.Age, ErrOutOfRange))
    }
    return errors.Join(errs...) // nil when errs is empty
}

func writeReport(path string, data []byte) (err error) {
    f, err := os.Create(path)
    if err != nil {
        return err
    }
    defer func() { err = errors.Join(err, f.Close()) }()
    _, err = f.Write(data)
    return err
}

func main() {
    err := validate(User{Age: -1})
    fmt.Println(err)                           // both messages, newline-separated
    fmt.Println(errors.Is(err, ErrOutOfRange)) // true
}
```

For concurrent work where you want the first error and cancellation of the rest, use `errgroup` instead; `Join` is for collecting everything.

- Pitfall: the newline-separated message can break single-line log formats; with structured logging, log the individual errors or replace newlines.
- Pitfall: `errors.Join` with a single non-nil error still wraps it, so the result is not `==` to the original. Use `errors.Is`.
- Interview tip: know both the 1.20 multi-`%w` support and `errors.Join`.

### Error handling strategy in applications
<!-- level: advanced; ref: https://go.dev/doc/effective_go#errors -->
Individual `if err != nil` checks are easy; a consistent strategy across a service is what separates senior Go code. A practical approach:

1. Low-level code returns errors with context (`fmt.Errorf("query orders for %d: %w", id, err)`), never logs them.
2. Domain code translates infrastructure errors into domain meaning: `sql.ErrNoRows` becomes `ErrOrderNotFound`, so HTTP handlers do not import database packages.
3. The boundary (HTTP handler, gRPC interceptor, job runner) decides the outcome once: map known errors to status codes, log unexpected ones with request context, and return a safe message to the client.
4. Panics are reserved for bugs and recovered only at boundaries (middleware), where they are logged with a stack trace and turned into 500s.

```go
var ErrOrderNotFound = errors.New("order not found")

func (r *Repo) Get(ctx context.Context, id int64) (Order, error) {
    var o Order
    err := r.db.QueryRowContext(ctx, `SELECT id,total FROM orders WHERE id=$1`, id).
        Scan(&o.ID, &o.Total)
    if errors.Is(err, sql.ErrNoRows) {
        return Order{}, ErrOrderNotFound
    }
    if err != nil {
        return Order{}, fmt.Errorf("get order %d: %w", id, err)
    }
    return o, nil
}

func writeErr(w http.ResponseWriter, r *http.Request, err error) {
    switch {
    case errors.Is(err, ErrOrderNotFound):
        http.Error(w, "not found", http.StatusNotFound)
    case errors.Is(err, context.Canceled):
        // client went away; nothing useful to send
    default:
        slog.ErrorContext(r.Context(), "request failed", "err", err, "path", r.URL.Path)
        http.Error(w, "internal error", http.StatusInternalServerError)
    }
}
```

- Pitfall: leaking internal error text (SQL, file paths) to API clients is a security issue.
- Pitfall: logging at every layer floods logs with the same failure five times.
- Interview tip: describe "handle once" and "translate at layer boundaries"; it shows production experience.
