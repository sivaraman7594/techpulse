## 12. Building HTTP Services

### net/http handlers and ServeMux routing (Go 1.22 patterns)
<!-- level: basic; ref: https://go.dev/blog/routing-enhancements -->
The standard library's `net/http` is production-grade: it powers many large services without any framework. A handler is anything implementing `ServeHTTP(http.ResponseWriter, *http.Request)`; `http.HandlerFunc` adapts an ordinary function. Each request runs in its own goroutine, so handlers must be safe for concurrent use.

Go 1.22 greatly improved `http.ServeMux`:

- Method matching: `"GET /orders/{id}"`. Wrong methods get an automatic 405 with an `Allow` header.
- Path wildcards: `{id}` matches one segment, read with `r.PathValue("id")`; `{path...}` matches the remainder.
- `{$}` matches only the exact path (`"/{$}"` is the root only).
- Precedence by specificity: the most specific pattern wins regardless of registration order, and conflicting patterns panic at registration.
- Host-specific patterns: `"api.example.com/..."`.

For many services this removes the need for third-party routers. Patterns behave according to the module's `go` version (GODEBUG `httpmuxgo121` restores the old behaviour).

```go
func NewRouter(s *OrderService) http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /orders/{id}", s.getOrder)
    mux.HandleFunc("POST /orders", s.createOrder)
    mux.HandleFunc("GET /files/{path...}", s.serveFile)
    mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("ok"))
    })
    return mux
}

func (s *OrderService) getOrder(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")
    o, err := s.repo.Get(r.Context(), id)
    if errors.Is(err, ErrNotFound) {
        http.Error(w, "not found", http.StatusNotFound)
        return
    }
    if err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(o)
}
```

- Pitfall: headers must be set before `WriteHeader` or the first `Write`; afterwards changes are ignored.
- Pitfall: forgetting `return` after `http.Error` continues executing and writes a second response ("superfluous WriteHeader" log).
- Pitfall: using `http.DefaultServeMux` (via `http.HandleFunc`) exposes anything imported packages register, such as pprof.
- Interview tip: mention that 1.22 routing removed the main reason to adopt gorilla/mux or chi.

### Middleware
<!-- level: intermediate; ref: https://pkg.go.dev/net/http#Handler -->
Middleware in Go is just a function that takes an `http.Handler` and returns a new one wrapping it. This simple shape composes cleanly and needs no framework. Middleware typically handles cross-cutting concerns: logging, metrics, panic recovery, authentication, request IDs, CORS, timeouts, compression and rate limiting.

To capture the status code for logging, wrap the `ResponseWriter`. Since Go 1.20, `http.ResponseController` lets handlers reach `Flush`, `Hijack` and per-request deadlines through wrappers, provided the wrapper implements `Unwrap() http.ResponseWriter`.

Order matters: the outermost middleware runs first on the way in and last on the way out. Recovery should be outermost so it catches panics from everything else.

```go
type statusRecorder struct {
    http.ResponseWriter
    status int
}

func (r *statusRecorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}

func (r *statusRecorder) Unwrap() http.ResponseWriter { return r.ResponseWriter }

func Logging(log *slog.Logger, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
        next.ServeHTTP(rec, r)
        log.InfoContext(r.Context(), "request",
            "method", r.Method, "path", r.URL.Path,
            "status", rec.status, "dur", time.Since(start))
    })
}

func Recover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if v := recover(); v != nil {
                slog.Error("panic", "value", v, "stack", string(debug.Stack()))
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

handler := Recover(Logging(slog.Default(), NewRouter(svc)))
```

- Pitfall: wrapping `ResponseWriter` without `Unwrap` hides `http.Flusher`, breaking streaming and server-sent events.
- Pitfall: `http.ErrAbortHandler` panics are intentional; re-panic them instead of logging an error.
- Interview tip: show the signature `func(http.Handler) http.Handler` and explain composition order.

### JSON encoding and decoding
<!-- level: basic; ref: https://pkg.go.dev/encoding/json -->
`encoding/json` maps Go values to JSON using reflection and struct tags. `json.Marshal`/`Unmarshal` work on byte slices; `json.NewEncoder(w).Encode` and `json.NewDecoder(r).Decode` stream to and from `io.Writer`/`io.Reader`, which is the natural fit for HTTP bodies.

Rules worth memorising:

- Only exported fields are encoded. Tags rename (`json:"name"`), skip (`json:"-"`), or omit empty values (`omitempty`); Go 1.24 added `omitzero`.
- Unmarshal ignores unknown fields by default and matches field names case-insensitively.
- Numbers decoded into `any` become `float64`; use `Decoder.UseNumber` or concrete types for big integers.
- `[]byte` encodes as base64; nil slices encode as `null`, empty slices as `[]`.
- Custom behaviour comes from implementing `MarshalJSON`/`UnmarshalJSON` or `encoding.TextMarshaler`.

For untrusted input, limit the body size with `http.MaxBytesReader` and consider `DisallowUnknownFields` to catch client typos.

Go 1.25 ships an experimental `encoding/json/v2` (enabled with `GOEXPERIMENT=jsonv2`) with better performance and stricter, more configurable semantics; v1 remains the stable default.

```go
type CreateOrder struct {
    CustomerID string  `json:"customer_id"`
    Items      []Item  `json:"items"`
    Note       *string `json:"note,omitempty"` // distinguishes absent from ""
}

func (s *Server) create(w http.ResponseWriter, r *http.Request) {
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MiB cap
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()

    var req CreateOrder
    if err := dec.Decode(&req); err != nil {
        http.Error(w, "bad json: "+err.Error(), http.StatusBadRequest)
        return
    }
    if req.CustomerID == "" || len(req.Items) == 0 {
        http.Error(w, "customer_id and items required", http.StatusUnprocessableEntity)
        return
    }
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode(map[string]string{"status": "created"})
}
```

- Pitfall: `Decoder.Decode` reads one JSON value; trailing garbage is not an error unless you check for more input.
- Interview tip: explain pointer fields for PATCH semantics.

### Server timeouts and graceful shutdown
<!-- level: advanced; ref: https://pkg.go.dev/net/http#Server -->
`http.ListenAndServe(addr, h)` uses a server with no timeouts. In production that lets slow or malicious clients hold connections and goroutines forever (Slowloris). Always build an explicit `http.Server`:

- `ReadHeaderTimeout`: time to read request headers; the most important single setting.
- `ReadTimeout`: time to read the whole request including body.
- `WriteTimeout`: time from end of header read to end of response write; careful with streaming endpoints.
- `IdleTimeout`: how long keep-alive connections wait for the next request.
- `MaxHeaderBytes`.

Graceful shutdown: on SIGTERM (Kubernetes sends it before killing a pod), call `srv.Shutdown(ctx)`. It closes listeners, waits for in-flight requests to complete, and closes idle connections, returning when done or when ctx expires. `ListenAndServe` then returns `http.ErrServerClosed`, which is not a failure.

```go
func main() {
    srv := &http.Server{
        Addr:              ":8080",
        Handler:           NewRouter(svc),
        ReadHeaderTimeout: 5 * time.Second,
        ReadTimeout:       15 * time.Second,
        WriteTimeout:      30 * time.Second,
        IdleTimeout:       120 * time.Second,
    }

    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Fatalf("listen: %v", err)
        }
    }()

    <-ctx.Done() // signal received
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil {
        slog.Error("forced shutdown", "err", err)
    }
    // then close DB pools, flush telemetry
}
```

Handlers can use `http.ResponseController(w).SetWriteDeadline` (Go 1.20) to extend deadlines for specific long downloads.

- Pitfall: `Shutdown` does not wait for hijacked connections (WebSockets) or background goroutines; track them yourself (`RegisterOnShutdown`).
- Pitfall: Kubernetes keeps routing traffic for a moment after SIGTERM; fail the readiness probe first and pause briefly before shutting down.
- Interview tip: name ReadHeaderTimeout and Slowloris explicitly.

### HTTP clients, connection reuse and timeouts
<!-- level: intermediate; ref: https://pkg.go.dev/net/http#Client -->
`http.Client` is safe for concurrent use and should be created once and reused. Its `Transport` (`http.Transport`) maintains a pool of keep-alive connections per host; reusing it avoids TCP and TLS handshakes on every request.

`http.DefaultClient` has no timeout, so a hung server can block a goroutine forever. Set timeouts:

- `Client.Timeout`: total time limit for the request including reading the body.
- Per-request deadlines via `http.NewRequestWithContext(ctx, ...)`, which integrate with request cancellation.
- Transport-level limits: `TLSHandshakeTimeout`, `ResponseHeaderTimeout`, `IdleConnTimeout`, and `MaxIdleConnsPerHost` (default 2, too low for high-throughput calls to one host).

For connections to be reused, you must read the response body to EOF and close it. Closing without draining may discard the connection.

```go
var payments = &http.Client{
    Timeout: 10 * time.Second,
    Transport: &http.Transport{
        MaxIdleConns:          100,
        MaxIdleConnsPerHost:   50,
        IdleConnTimeout:       90 * time.Second,
        TLSHandshakeTimeout:   5 * time.Second,
        ResponseHeaderTimeout: 5 * time.Second,
    },
}

func charge(ctx context.Context, body []byte) (*Receipt, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodPost,
        "https://payments.internal/charge", bytes.NewReader(body))
    if err != nil {
        return nil, err
    }
    req.Header.Set("Content-Type", "application/json")
    resp, err := payments.Do(req)
    if err != nil {
        return nil, fmt.Errorf("charge: %w", err)
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        io.Copy(io.Discard, io.LimitReader(resp.Body, 64<<10)) // drain for reuse
        return nil, fmt.Errorf("charge: status %d", resp.StatusCode)
    }
    var rc Receipt
    return &rc, json.NewDecoder(resp.Body).Decode(&rc)
}
```

- Pitfall: creating a new `http.Client` and `Transport` per request leaks connections and file descriptors.
- Pitfall: a non-2xx status is not an error from `Do`; you must check `StatusCode`.
- Pitfall: retrying non-idempotent POSTs blindly can double-charge; use idempotency keys.
- Interview tip: mention MaxIdleConnsPerHost when discussing connection churn and TIME_WAIT exhaustion.

### Structured logging with log/slog (Go 1.21)
<!-- level: basic; ref: https://pkg.go.dev/log/slog -->
Go 1.21 added `log/slog`, a structured logging package in the standard library. Logs are records with a time, level, message and key-value attributes, rendered by a `Handler`: `slog.NewTextHandler` (key=value) or `slog.NewJSONHandler` for log aggregation systems. Third-party backends (zap, zerolog adapters, OpenTelemetry) plug in as handlers.

Key features:

- Levels: Debug, Info, Warn, Error, with a configurable minimum (`slog.LevelVar` allows changing it at runtime).
- `logger.With(attrs...)` returns a child logger that adds attributes to every record, such as service name or request ID.
- `slog.Group` nests attributes.
- `*Context` variants (`InfoContext`) pass ctx to handlers so they can extract trace IDs.
- `LogValuer` lets types control how they are logged, for example redacting secrets.
- `slog.SetDefault` also routes the old `log` package output through slog.

Prefer alternating key-value pairs for brevity or `slog.Attr` constructors (`slog.Int`, `slog.String`) for performance and vet checking.

```go
func main() {
    level := new(slog.LevelVar) // Info by default
    h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level})
    log := slog.New(h).With("service", "orders", "version", buildVersion)
    slog.SetDefault(log)

    log.Info("starting", "addr", ":8080")
    reqLog := log.With("request_id", "r-123")
    reqLog.Warn("slow query", slog.Duration("took", 1200*time.Millisecond), slog.Int("rows", 5400))
}

type Token string

func (Token) LogValue() slog.Value { return slog.StringValue("REDACTED") }
```

Output: `{"time":"...","level":"WARN","msg":"slow query","service":"orders","version":"1.4.2","request_id":"r-123","took":1200000000,"rows":5400}`

- Pitfall: odd numbers of key-value arguments produce a `!BADKEY` attribute; `go vet` checks slog calls.
- Pitfall: building expensive attribute values when the level is disabled wastes CPU; check `log.Enabled(ctx, level)` or use `LogValuer` for lazy evaluation.
- Interview tip: explain why structured logs beat printf-style logs for querying in production.

## 13. Performance, Memory and the Runtime

### Stack vs heap and escape analysis
<!-- level: advanced; ref: https://go.dev/doc/faq#stack_or_heap -->
Go does not let you choose where a variable lives; the compiler decides. Each goroutine has its own growable stack, and stack allocation is essentially free: memory is reclaimed when the function returns, with no garbage collector involvement. Heap allocation costs more and creates GC work.

Escape analysis is the compile-time pass that proves whether a value can stay on the stack. A value escapes to the heap when it might outlive the function or its size is unknown. Common causes:

- Returning a pointer to a local variable.
- Storing a pointer in a heap object, global, or a value sent on a channel.
- Assigning a non-pointer value to an interface (boxing) when the compiler cannot prove it does not escape, e.g. passing to `fmt.Println`.
- Closures capturing variables that outlive the call.
- Slices with non-constant size from `make([]T, n)` (large or unknown sizes go to the heap).

Inspect decisions with `go build -gcflags=-m` (add `-m=2` for reasons). Goroutine stacks start at a few KB and are grown by copying to a larger stack when needed, which is why pointers into stacks are safe to update.

```go
type Point struct{ X, Y int }

func sumPoints(n int) int {
    p := Point{1, 2} // stays on stack
    return p.X * n
}

func newPoint() *Point {
    p := Point{1, 2}
    return &p // moved to heap: &p escapes
}

func logIt(v int) {
    fmt.Println(v) // v boxed into interface; may allocate
}
```

```bash
go build -gcflags='-m' ./internal/geo
# ./geo.go:9:2: moved to heap: p
```

- Pitfall: "use pointers to avoid copying" can make things slower by forcing heap allocation; measure.
- Pitfall: escape decisions change between compiler versions; do not rely on them without benchmarks.
- Interview tip: connect escape analysis to GC pressure: fewer heap allocations means less GC CPU.

### The garbage collector and GOGC
<!-- level: advanced; ref: https://go.dev/doc/gc-guide -->
Go uses a concurrent, non-moving, tri-color mark-and-sweep garbage collector optimised for low latency. Most work happens concurrently with your goroutines; stop-the-world pauses are typically well under a millisecond. Write barriers, enabled during marking, keep the concurrent marking correct when goroutines modify pointers.

Tri-color marking: objects start white; roots (stacks, globals) are grey; the collector scans grey objects, marking their referents grey and turning themselves black. When no grey objects remain, white objects are garbage and are swept.

Pacing: `GOGC` (default 100) sets how much the heap may grow relative to the live heap after the last collection before the next cycle starts. With 100 MB live, the next GC triggers around 200 MB. Higher GOGC means fewer collections (less CPU) but more memory; `GOGC=off` disables GC (dangerous without a memory limit). Goroutines that allocate heavily during a cycle are drafted into "GC assist" work, which shows up as latency.

GC cost is roughly proportional to the live heap and number of pointers, and frequency is proportional to allocation rate. So the two levers are: allocate less, and keep fewer pointer-heavy live objects.

Go 1.25 shipped the experimental "Green Tea" collector (`GOEXPERIMENT=greenteagc`), which scans memory in page-sized spans for better locality and reduces GC CPU for many workloads; it became the default in Go 1.26.

```bash
GODEBUG=gctrace=1 ./server
# gc 42 @12.3s 2%: 0.05+3.1+0.02 ms clock, ... 180->184->95 MB, 190 MB goal, 8 P
```

```go
var m runtime.MemStats
runtime.ReadMemStats(&m) // stops the world briefly; prefer runtime/metrics
fmt.Println(m.HeapAlloc, m.NumGC)
```

- Pitfall: calling `runtime.GC()` manually is almost never helpful in servers.
- Pitfall: huge maps or slices of pointers (`[]*Item`) are expensive to scan; slices of values or pointer-free structs are cheaper.
- Interview tip: explain the GOGC trade-off as "CPU vs memory".

### GOMEMLIMIT and memory tuning in containers
<!-- level: advanced; ref: https://go.dev/doc/gc-guide#Memory_limit -->
Go 1.19 added a soft memory limit, set with the `GOMEMLIMIT` environment variable (e.g. `GOMEMLIMIT=900MiB`) or `debug.SetMemoryLimit`. When total Go runtime memory approaches the limit, the GC runs more often regardless of GOGC, and the scavenger returns memory to the OS more aggressively.

Why it matters: in containers, the kernel OOM-kills a process that exceeds its cgroup limit. With only GOGC, a service with 600 MB live heap and GOGC=100 can try to grow to 1.2 GB and be killed in a 1 GB container. A memory limit tells the GC about the ceiling.

Common configurations:

- Set GOMEMLIMIT to about 80–90% of the container limit, leaving headroom for non-Go memory (cgo, thread stacks, mmap'd files).
- For services with a steady live heap, `GOGC=off` plus GOMEMLIMIT makes the GC run only when needed, saving CPU. Risky if live heap can approach the limit.

Death spirals: if the live heap itself exceeds the limit, the GC would run constantly. The runtime caps GC CPU at about 50% in that situation, so the process slows down rather than freezing, but it may still OOM eventually.

```go
// Usually set via env in the Deployment spec; programmatic equivalent:
import "runtime/debug"

func init() {
    if os.Getenv("GOMEMLIMIT") == "" {
        debug.SetMemoryLimit(900 << 20) // 900 MiB
    }
}
```

```yaml
resources:
  limits:
    memory: 1Gi
env:
  - name: GOMEMLIMIT
    value: "900MiB"
```

Monitor `/gc/heap/live:bytes` and `/memory/classes/total:bytes` from `runtime/metrics`, plus container RSS.

- Pitfall: the limit is soft; it cannot save you from a genuine leak.
- Pitfall: RSS can stay above the heap for a while because freed memory is returned to the OS lazily.
- Interview tip: this is a frequent question for Kubernetes-hosted Go services.

### Profiling with pprof
<!-- level: advanced; ref: https://go.dev/blog/pprof -->
pprof is Go's built-in profiler. Profiles are sampled, cheap enough for production, and analysed with `go tool pprof`.

Profile types:

- CPU: samples stacks 100 times per second while code runs; shows where CPU time goes.
- Heap: sampled allocations; view `inuse_space` (what is live now, for leaks) or `alloc_space` (total allocated, for GC pressure).
- Goroutine: stacks of all goroutines; the first stop for leaks and deadlocks.
- Block and mutex: where goroutines wait on channels/locks, and lock contention. Disabled by default; enable with `runtime.SetBlockProfileRate` and `runtime.SetMutexProfileFraction`.

Collect from services by importing `net/http/pprof` on an internal-only port, from tests with `go test -cpuprofile cpu.out -memprofile mem.out`, or programmatically with `runtime/pprof`. Continuous profiling platforms collect pprof data from fleets.

```go
import _ "net/http/pprof" // registers /debug/pprof/* on DefaultServeMux

func main() {
    go func() {
        // internal admin port only, never public
        log.Println(http.ListenAndServe("localhost:6060", nil))
    }()
    runApp()
}
```

```bash
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/profile?seconds=30
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/heap
curl -s 'localhost:6060/debug/pprof/goroutine?debug=1' | head -50
go tool pprof -diff_base=before.pb.gz after.pb.gz   # compare two heap profiles
```

In the web UI, the flame graph shows inclusive cost by stack; `top` lists flat cost by function; `list FuncName` annotates source lines.

- Pitfall: exposing pprof on a public port leaks internals and allows expensive profiling requests.
- Pitfall: a CPU profile of an idle service shows nothing useful; capture during the problem.
- Interview tip: say which profile you would use for "high CPU", "growing memory", "high latency but low CPU" (block/mutex or trace).

### Execution tracing and the flight recorder
<!-- level: advanced; ref: https://pkg.go.dev/runtime/trace -->
Profiles aggregate; the execution tracer records a timeline of events: goroutine creation, blocking and unblocking, syscalls, network waits, GC phases, processor (P) activity and user-defined regions. It answers latency questions profiles cannot, such as "why did this request take 300 ms while CPU was idle?" (waiting on a lock, starved of a P, GC assist, scheduler delay).

Collect a trace with `go test -trace trace.out`, `/debug/pprof/trace?seconds=5`, or `trace.Start(w)`. View it with `go tool trace trace.out`. Since Go 1.21–1.22, the tracer's overhead dropped to a few percent and traces became scalable, making production use realistic.

Annotate application work with `trace.NewTask`, `trace.WithRegion` and `trace.Log` so the trace viewer groups events by request.

Go 1.25 added `trace.FlightRecorder`: it keeps the last few seconds of trace data in an in-memory ring buffer, and you write it out only when something interesting happens (a slow request, a timeout). This captures rare latency spikes without tracing continuously to disk.

```go
fr := trace.NewFlightRecorder(trace.FlightRecorderConfig{
    MinAge:   10 * time.Second,
    MaxBytes: 16 << 20,
})
if err := fr.Start(); err != nil {
    log.Fatal(err)
}

func handle(w http.ResponseWriter, r *http.Request) {
    start := time.Now()
    ctx, task := trace.NewTask(r.Context(), "checkout")
    defer task.End()
    process(ctx)
    if time.Since(start) > 500*time.Millisecond {
        f, _ := os.Create(fmt.Sprintf("/tmp/slow-%d.trace", time.Now().Unix()))
        fr.WriteTo(f) // snapshot of the recent past
        f.Close()
    }
}
```

- Pitfall: traces are large; record seconds, not minutes.
- Pitfall: the flight recorder snapshot should be rate-limited so a burst of slow requests does not write hundreds of files.
- Interview tip: contrast "profile tells you where time is spent; trace tells you when and why goroutines were not running".

### Reducing allocations and sync.Pool
<!-- level: advanced; ref: https://pkg.go.dev/sync#Pool -->
In allocation-heavy services, GC CPU and assist latency are often the main costs. Reducing allocations in hot paths is the most effective tuning. Find them with a heap profile using `alloc_space`/`alloc_objects`, or `-benchmem` in benchmarks.

Techniques:

- Preallocate slices and maps when the size is known (`make([]T, 0, n)`, `make(map[K]V, n)`).
- Reuse buffers: `buf = buf[:0]` keeps capacity; `strings.Builder` and `bytes.Buffer` with `Grow`.
- Avoid boxing values into interfaces in hot loops (logging with `any` arguments, `fmt.Sprintf` for simple concatenation; use `strconv.AppendInt`).
- Avoid converting between `[]byte` and `string` repeatedly.
- Prefer value types and pointer-free structs to reduce GC scanning.
- Stream with `io.Reader`/`io.Writer` instead of reading whole payloads into memory.

`sync.Pool` caches temporary objects for reuse across goroutines. Each P has a local cache, so Get/Put are fast. Pools are cleared gradually across GC cycles (a victim cache keeps items for one extra cycle), so they suit short-lived, frequently allocated objects like buffers and encoders, not connection pools.

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func renderJSON(w io.Writer, v any) error {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()
    defer func() {
        if buf.Cap() <= 64<<10 { // do not keep huge buffers alive
            bufPool.Put(buf)
        }
    }()
    if err := json.NewEncoder(buf).Encode(v); err != nil {
        return err
    }
    _, err := w.Write(buf.Bytes())
    return err
}
```

- Pitfall: using an object after `Put` (or putting it while still referenced) causes data corruption across requests.
- Pitfall: pooling objects of wildly varying sizes keeps memory high; cap what you return to the pool.
- Pitfall: putting non-pointer values in a Pool allocates on every Put due to interface boxing.
- Interview tip: always say "profile first", then name two or three concrete techniques.

### Profile-guided optimisation (PGO)
<!-- level: advanced; ref: https://go.dev/doc/pgo -->
Profile-guided optimisation feeds a CPU profile from real workloads back into the compiler so it optimises the hot paths. It was previewed in Go 1.20 and became generally available in Go 1.21.

How it works: place a representative CPU profile named `default.pgo` in the main package's directory. `go build` uses it automatically (`-pgo=auto` is the default). The compiler then inlines more aggressively at hot call sites and devirtualises hot interface method calls (adding a fast path that calls the concrete method directly when the profile shows one dominant type). Typical gains are 2–14% CPU for real services, with modestly larger binaries and builds.

Workflow:

1. Build and deploy without PGO.
2. Collect CPU profiles from production (for example 30 seconds from several instances) and merge them with `go tool pprof -proto a.pprof b.pprof > default.pgo`.
3. Commit `default.pgo` to the main package directory and rebuild.
4. Refresh the profile periodically. PGO is designed to be robust to stale profiles: code changes simply reduce the benefit for changed functions; correctness is never affected.

```bash
curl -o cpu1.pprof 'http://svc-a:6060/debug/pprof/profile?seconds=30'
curl -o cpu2.pprof 'http://svc-b:6060/debug/pprof/profile?seconds=30'
go tool pprof -proto cpu1.pprof cpu2.pprof > cmd/api/default.pgo
go build -o api ./cmd/api        # picks up default.pgo automatically
go version -m api | grep pgo     # confirm: -pgo=.../default.pgo
```

- Pitfall: profiles from benchmarks or unrepresentative traffic optimise the wrong paths.
- Pitfall: PGO is per main package; a library's default.pgo is ignored when built as a dependency.
- Interview tip: mention devirtualisation, since it explains why interface-heavy code benefits.

### GOMAXPROCS and containers (Go 1.25)
<!-- level: intermediate; ref: https://go.dev/doc/go1.25 -->
`GOMAXPROCS` sets the number of Ps, which bounds how many goroutines run Go code simultaneously. Historically the default was the number of logical CPUs on the machine, ignoring container CPU limits. A pod limited to 2 CPUs on a 64-core node would run with GOMAXPROCS=64, causing the kernel's CFS quota to throttle the process: bursts of parallel work exhaust the quota early in each 100 ms period and then all threads stall, producing tail-latency spikes. Teams used `go.uber.org/automaxprocs` to fix it.

Go 1.25 made the default container-aware on Linux: the runtime considers the cgroup CPU limit and sets GOMAXPROCS to it (rounded up, minimum 2 when the limit is lower but the machine has more CPUs). It also periodically re-checks CPU limits and logical CPU counts and adjusts GOMAXPROCS if they change. These behaviours apply when the module's go version is 1.25 or later, and are disabled if you set GOMAXPROCS explicitly; GODEBUG settings `containermaxprocs=0` and `updatemaxprocs=0` turn them off.

CPU requests (as opposed to limits) are not considered, because they do not throttle.

```go
func main() {
    // Go 1.25+: already reflects the container CPU limit
    slog.Info("runtime", "gomaxprocs", runtime.GOMAXPROCS(0), "numcpu", runtime.NumCPU())
}
```

```yaml
resources:
  requests:
    cpu: "1"
  limits:
    cpu: "2"      # Go 1.25+ picks GOMAXPROCS=2 automatically
```

- Pitfall: on Go 1.24 and earlier, forgetting automaxprocs in containers with CPU limits is a classic source of p99 latency spikes.
- Pitfall: setting GOMAXPROCS very low on I/O-heavy services is rarely harmful, but too low for CPU-bound work wastes allotted CPU.
- Interview tip: explain CFS throttling, not just "set GOMAXPROCS".

### weak pointers, unique and finalisers (Go 1.23–1.24)
<!-- level: advanced; ref: https://pkg.go.dev/weak -->
Recent releases added runtime primitives for memory-sensitive data structures.

`unique` (Go 1.23) interns comparable values: `unique.Make(v)` returns a `unique.Handle[T]`; two handles are equal if and only if the values are equal, and comparing handles is a cheap pointer comparison. Interned values are deduplicated across the program and freed when no handles remain. Useful for repeated strings like label names, hostnames or IP zone strings (the `net/netip` package uses it).

`weak` (Go 1.24) provides `weak.Pointer[T]`: a reference that does not keep its target alive. `weak.Make(p)` creates one; `wp.Value()` returns the original pointer or nil if it was collected. This enables caches that do not prevent garbage collection and canonicalisation maps.

`runtime.AddCleanup` (Go 1.24) attaches a cleanup function that runs after an object becomes unreachable. It improves on `runtime.SetFinalizer`: multiple cleanups per object, no resurrection of the object, and it works with interior pointers. Cleanups are a safety net (for example, releasing a C resource if the user forgot `Close`), not a substitute for explicit cleanup, because when or whether they run is not guaranteed.

```go
type Blob struct{ data []byte }

type BlobCache struct {
    mu sync.Mutex
    m  map[string]weak.Pointer[Blob]
}

func (c *BlobCache) Get(key string, load func() *Blob) *Blob {
    c.mu.Lock()
    defer c.mu.Unlock()
    if wp, ok := c.m[key]; ok {
        if b := wp.Value(); b != nil {
            return b // still alive somewhere
        }
    }
    b := load()
    c.m[key] = weak.Make(b)
    runtime.AddCleanup(b, func(k string) { // remove stale entry later
        c.mu.Lock()
        defer c.mu.Unlock()
        if wp, ok := c.m[k]; ok && wp.Value() == nil {
            delete(c.m, k)
        }
    }, key)
    return b
}

host := unique.Make("api.internal.example.com") // deduplicated handle
```

- Pitfall: the cleanup function must not reference the object itself, or it never becomes unreachable.
- Interview tip: these are niche; know they exist and when a weak cache beats an LRU.
