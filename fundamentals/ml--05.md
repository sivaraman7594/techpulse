## 9. Adapting Models and Retrieval

### Fine-tuning versus prompting versus RAG
<!-- level: intermediate; ref: https://platform.openai.com/docs/guides/optimizing-llm-accuracy -->
Three levers adapt an LLM to your task. Prompting changes instructions and examples; it is cheapest and fastest to iterate. Retrieval-augmented generation injects external, current or private knowledge at request time. Fine-tuning changes the weights so the model internalises a style, format or narrow skill.

Rule of thumb: use RAG when the problem is missing or changing knowledge; use fine-tuning when the problem is behaviour, such as consistent tone, strict output format, or a small model that must imitate a larger one; try prompting first for both. Fine-tuning is poor at teaching large volumes of facts reliably and the knowledge goes stale, while RAG cannot change how the model reasons or writes.

```text
Knowledge gap or changing facts  -> RAG
Style / format / latency / cost  -> fine-tune (often a smaller model)
Unknown                           -> prompt + evaluation set first
```

Pitfalls:
- Fine-tuning before building an evaluation set, so you cannot tell if it helped.
- Fine-tuning on facts that change monthly.

Interview tip: the strongest answers combine them: RAG for knowledge, fine-tuning for format, prompting for glue.

### Parameter-efficient fine-tuning (LoRA)
<!-- level: advanced; ref: https://huggingface.co/docs/peft/index -->
Full fine-tuning updates every weight and needs optimizer state several times the model size. LoRA (low-rank adaptation) freezes the base weights and learns, for selected matrices, a pair of small matrices A and B whose product is a low-rank update added to the original weight. Only A and B are trained, often well under 1% of the parameters, and they can be saved as a small adapter and swapped per task or merged into the base model for inference. QLoRA additionally quantises the frozen base to 4-bit to fit larger models on one GPU.

```python
from peft import LoraConfig, get_peft_model
cfg = LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"], lora_dropout=0.05)
model = get_peft_model(base_model, cfg)
model.print_trainable_parameters()
```

Pitfalls:
- Training data quality dominates; a few thousand clean examples beat many noisy ones.
- Overfitting small datasets with too many epochs.
- Evaluating only on training-like prompts and missing regressions in general ability.

Interview tip: explain rank r as the capacity versus cost knob and why adapters make multi-tenant serving cheaper.

### Preference tuning: RLHF and DPO
<!-- level: advanced; ref: https://arxiv.org/abs/2305.18290 -->
After supervised fine-tuning, models are aligned with human preferences using comparisons: for a prompt, annotators say which of two responses is better. In RLHF, a reward model is trained on these comparisons and the language model is then optimised against it with a reinforcement learning algorithm such as PPO, with a KL penalty that keeps it close to the original model. Direct Preference Optimisation (DPO) skips the explicit reward model and RL loop: it optimises a simple classification-style loss directly on preferred versus rejected pairs, which is simpler and more stable.

```json
{"prompt": "Explain DNS briefly.",
 "chosen": "DNS maps names to IP addresses by ...",
 "rejected": "I cannot help with that."}
```

Pitfalls:
- Reward hacking: the model exploits quirks of the reward model (verbosity, flattery).
- Preference data reflects annotator bias.
- Over-optimisation reduces diversity.

Interview tip: state why the KL term exists and that DPO trades the RL machinery for a supervised-style objective.

### Retrieval-augmented generation (RAG)
<!-- level: intermediate; ref: https://arxiv.org/abs/2005.11401 -->
RAG answers questions using documents fetched at request time instead of relying on model memory. Offline you split documents into chunks, embed them and store them in an index. Online you embed the query, retrieve the top-k similar chunks, put them into the prompt with instructions to answer from them, and generate with citations.

It keeps knowledge fresh without retraining, supports access control per document, and makes answers traceable. Quality depends on retrieval more than on the generator: if the right chunk is not retrieved, no prompt can save it.

```python
q_vec = embed(question)
hits = index.search(q_vec, k=5)
context = "\n\n".join(h.text for h in hits)
answer = llm(f"Answer from the context only.\n{context}\n\nQ: {question}")
```

Pitfalls:
- Evaluating only the final answer; measure retrieval recall separately.
- Stale indexes after source documents change.
- Ignoring permissions so users can retrieve documents they should not see.

Interview tip: describe debugging order: was the answer in the corpus, was it retrieved, was it ranked in the prompt, did the model use it.

### Chunking strategies
<!-- level: intermediate; ref: https://python.langchain.com/docs/concepts/text_splitters/ -->
Chunking splits documents into pieces small enough to embed precisely and retrieve selectively. Too large and each vector blurs several topics and wastes context; too small and a chunk loses the surrounding meaning. Common approaches: fixed size with overlap, recursive splitting on paragraphs then sentences, structure-aware splitting on headings, code functions or table rows, and semantic splitting where embedding similarity drops.

Practical defaults are a few hundred tokens with 10 to 20 percent overlap, but tune against retrieval metrics. Attach metadata (title, section, source, date, permissions) to every chunk and consider prepending the section heading to the chunk text. Parent-document retrieval indexes small chunks but returns the larger parent for context.

```python
splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=150)
chunks = splitter.split_documents(docs)
```

Pitfalls:
- Splitting mid-table or mid-code block.
- Dropping source metadata, which prevents citations and filtering.

Interview tip: say chunk size is a hyperparameter you tune with recall@k on real questions.

### Vector databases and approximate nearest neighbour search
<!-- level: advanced; ref: https://github.com/pgvector/pgvector -->
A vector database stores embeddings with metadata and answers "find the k nearest vectors" queries. Exact search compares the query with every vector, which is accurate but linear. Approximate nearest neighbour (ANN) indexes trade a little recall for large speedups: HNSW builds a layered proximity graph, IVF clusters vectors and searches only nearby clusters, and product quantisation compresses vectors. Tuning parameters (for HNSW, graph connectivity and search breadth) trade recall, latency and memory.

Options include dedicated engines and extensions such as pgvector for PostgreSQL, which keeps vectors next to relational data and transactions.

```sql
CREATE EXTENSION vector;
CREATE TABLE docs (id bigint, body text, embedding vector(768));
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);
SELECT id FROM docs ORDER BY embedding <=> $1 LIMIT 5;
```

Pitfalls:
- Index distance metric differing from the embedding model's intended metric.
- Heavy metadata filtering after ANN search returning fewer than k results.
- Measuring only latency, not recall against exact search.

Interview tip: justify a dedicated store versus pgvector by scale, filtering needs and operational burden.

### Hybrid search and reranking
<!-- level: advanced; ref: https://www.sbert.net/examples/applications/retrieve_rerank/README.html -->
Dense embeddings capture meaning but can miss exact tokens such as product codes, names or error numbers; keyword search (BM25) is the opposite. Hybrid search runs both and fuses the rankings, commonly with reciprocal rank fusion, where each document scores the sum of 1/(k + rank) across lists.

A reranker then improves precision: a cross-encoder reads the query and each candidate together and scores relevance more accurately than comparing independent vectors, but is too slow for the whole corpus. The usual pipeline retrieves 50 to 100 candidates cheaply, reranks them, and passes the best handful to the LLM.

```python
def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:
        for pos, doc in enumerate(ranking, 1):
            scores[doc] = scores.get(doc, 0) + 1 / (k + pos)
    return sorted(scores, key=scores.get, reverse=True)
```

Pitfalls:
- Reranking too few candidates to matter.
- Added latency not budgeted.

Interview tip: explain bi-encoder (fast, recall) versus cross-encoder (slow, precision) in two sentences.

## 10. Agents, Evaluation, MLOps and Responsible AI

### LLM agents and the tool loop
<!-- level: intermediate; ref: https://www.anthropic.com/engineering/building-effective-agents -->
An agent is an LLM running in a loop: it decides on an action, calls a tool, observes the result, and repeats until it can answer or hits a limit. Tools might be search, code execution, database queries or APIs. Patterns include ReAct (interleave reasoning and acting), planning then executing, and multi-agent setups where specialised agents hand off work.

Agents trade predictability for flexibility. Prefer a fixed workflow (a chain of steps with code-controlled branching) when the task is well understood, and use an agent only when the path genuinely depends on intermediate results.

```python
for step in range(MAX_STEPS):
    reply = llm(messages, tools=tools)
    if not reply.tool_calls:
        return reply.text
    for call in reply.tool_calls:
        messages.append(run_tool(call))
```

Pitfalls:
- No step or cost cap, allowing runaway loops.
- Tools with write access and no confirmation.
- Errors compounding across steps.

Interview tip: mention guardrails: iteration limits, least-privilege tools, human approval for irreversible actions, and tracing every step.

### Evaluating LLM applications
<!-- level: intermediate; ref: https://docs.anthropic.com/en/docs/test-and-evaluate/develop-tests -->
LLM outputs are open-ended, so evaluation needs several methods. Build a golden dataset of realistic inputs with expected answers or grading criteria, drawn from production traffic where possible. Use exact or programmatic checks where they apply (schema validity, regex, unit tests for generated code). Use LLM-as-judge with a clear rubric for qualities like helpfulness or faithfulness, and calibrate the judge against human labels. Keep humans in the loop for samples.

For RAG, measure retrieval (recall@k, MRR) separately from generation (faithfulness, answer relevance). Track results per change so every prompt, model or retrieval tweak is a measured experiment, and run the suite in CI.

```python
results = [grade(app(case.input), case.rubric) for case in dataset]
print(sum(r.passed for r in results) / len(results))
```

Pitfalls:
- Judge model bias toward longer or its own style of answers.
- Dataset leakage between prompt tuning and evaluation.
- Averages hiding failures on critical cases.

Interview tip: say you segment results by category and watch the worst slices, not only the mean.

### Model deployment and serving
<!-- level: intermediate; ref: https://kserve.github.io/website/latest/ -->
Serving turns a trained model into a reliable service. Online serving exposes a low-latency API (REST or gRPC) behind autoscaling; batch scoring runs the model over a dataset on a schedule; streaming and edge deployments handle continuous or on-device inference. Package the model, preprocessing code and dependencies together in a container, and make preprocessing identical to training to avoid training-serving skew.

Release safely with shadow deployment (run the new model silently and compare), canary rollout and A/B tests. For LLMs, latency has two parts: time to first token and tokens per second. Throughput improves with batching, quantisation and KV-cache reuse.

```text
request -> validate -> features -> model -> postprocess -> response
                       log inputs + prediction + model version
```

Pitfalls:
- Different feature code paths in training and serving.
- No rollback plan or model version in logs.
- Sizing on average rather than peak traffic.

Interview tip: define latency, throughput and cost targets before choosing batch versus online.

### Drift and monitoring
<!-- level: intermediate; ref: https://cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning -->
A deployed model degrades silently because the world changes. Data drift is a shift in input feature distributions; concept drift is a change in the relationship between inputs and the target; label or prior shift changes class proportions. Monitoring covers system health (latency, errors), data quality (nulls, ranges, schema), input distributions, prediction distributions, and, when labels arrive, real performance.

Distribution checks include the population stability index, KS test and divergence measures against a training or recent reference window. Because true labels are often delayed, proxy signals such as score distribution and downstream business metrics provide early warning. Alerts should trigger investigation or retraining, not automatic redeploy without checks.

```python
from scipy.stats import ks_2samp
stat, p = ks_2samp(train_feature, live_feature)
if p < 0.01: alert("feature drift")
```

Pitfalls:
- Alert fatigue from testing hundreds of features at tiny thresholds.
- Treating drift as proof of harm; confirm with performance.

Interview tip: separate "inputs changed" from "model is wrong" and explain how you get labels back.

### MLOps pipelines, registries and feature stores
<!-- level: intermediate; ref: https://mlflow.org/docs/latest/model-registry.html -->
MLOps applies DevOps discipline to machine learning, where code, data and model all change. A reproducible pipeline versions the dataset, code, hyperparameters and environment, then trains, evaluates against thresholds, and registers the model. A model registry stores versions with lineage, metrics and stage (staging, production) so deployments are auditable and reversible. A feature store provides the same feature definitions for offline training and online serving, which reduces training-serving skew and duplicated work.

Experiment tracking records parameters and metrics of each run so results can be compared and reproduced. CI/CD adds tests for data schemas, model quality gates and deployment checks.

```python
import mlflow
with mlflow.start_run():
    mlflow.log_params({"lr": 0.01})
    mlflow.log_metric("auc", 0.91)
    mlflow.sklearn.log_model(model, "model")
```

Pitfalls:
- Training from an unversioned data snapshot, making results irreproducible.
- Notebook-only workflows that cannot be rerun.

Interview tip: explain what you would need to recreate a model from six months ago.

### Quantisation and efficient inference
<!-- level: advanced; ref: https://huggingface.co/docs/transformers/quantization/overview -->
Quantisation stores weights, and sometimes activations, in fewer bits, for example 8-bit or 4-bit integers instead of 16-bit floats. Memory drops roughly in proportion, so larger models fit on a given GPU, and memory-bound decoding runs faster because less data is moved. Post-training methods such as GPTQ and AWQ need only a small calibration set; quantisation-aware training adapts the model during training for better quality.

Other inference optimisations include distillation (train a small student to mimic a large teacher), speculative decoding (a small draft model proposes tokens that the large model verifies in parallel), continuous batching, and paged KV-cache management.

```python
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
cfg = BitsAndBytesConfig(load_in_4bit=True)
model = AutoModelForCausalLM.from_pretrained(name, quantization_config=cfg)
```

Pitfalls:
- Quality loss on reasoning, maths or rare languages; evaluate on your own task.
- Assuming lower precision is always faster on your hardware.

Interview tip: link the technique to the bottleneck: memory bandwidth, memory capacity or compute.

### Bias, fairness and responsible AI
<!-- level: intermediate; ref: https://www.nist.gov/itl/ai-risk-management-framework -->
Models inherit and can amplify bias in data, labels and objectives. Sources include unrepresentative samples, historical decisions encoded as labels, proxy features correlated with protected attributes, and feedback loops where model decisions shape future data. Fairness has several competing definitions, such as demographic parity (equal positive rates), equal opportunity (equal true-positive rates) and calibration across groups, and they generally cannot all hold at once, so the choice is a policy decision for the context.

Practice includes documenting data and models (data sheets, model cards), evaluating metrics per subgroup, red-teaming, human oversight for high-stakes decisions, privacy protection, and a path for appeal. Regulation such as the EU AI Act sets obligations by risk category.

```python
for group, df in results.groupby("group"):
    print(group, recall_score(df.y_true, df.y_pred))
```

Pitfalls:
- Dropping the protected column and assuming fairness; proxies remain.
- Reporting only aggregate accuracy.

Interview tip: acknowledge fairness trade-offs and say who decides the acceptable one.

### Prompt injection and LLM security
<!-- level: advanced; ref: https://owasp.org/www-project-top-10-for-large-language-model-applications/ -->
Prompt injection is when text the model reads contains instructions that override the developer's intent. Direct injection comes from the user; indirect injection hides in retrieved web pages, emails, documents or tool outputs. Because instructions and data share one text channel, no prompt wording can fully prevent it.

Defence is architectural. Treat all model output and retrieved content as untrusted. Give the model least-privilege tools, scope credentials per user, require human confirmation for sensitive actions, and validate and sanitise tool arguments. Separate untrusted content handling from privileged actions, filter outputs that could exfiltrate data (for example rendered links or images with secrets in URLs), and log and monitor. Other risks include sensitive data disclosure, insecure output handling and denial of wallet through unbounded usage.

```text
Risky: agent reads inbox AND can send email AND can access files
Safer: read-only summariser; sending requires user approval
```

Pitfalls:
- Relying on "ignore malicious instructions" in the system prompt as the only control.
- Running model-generated code or SQL with production credentials.

Interview tip: describe the "lethal trifecta" idea: private data, untrusted content and an exfiltration path together make an exploitable system.
