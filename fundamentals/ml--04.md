## 7. Neural Networks and Transformers

### Neural networks and backpropagation
<!-- level: intermediate; ref: https://pytorch.org/tutorials/beginner/basics/autogradqs_tutorial.html -->
A neural network is a stack of layers, each computing a linear transform followed by a non-linear activation such as ReLU or GELU. Without the non-linearity the whole stack collapses into a single linear map. Training minimises a loss by gradient descent: the forward pass computes predictions and loss, and backpropagation applies the chain rule layer by layer in reverse to get the gradient of the loss with respect to every weight. An optimiser such as SGD with momentum or Adam then updates the weights using those gradients.

Frameworks build a computation graph during the forward pass so that gradients come for free (automatic differentiation).

```python
import torch
model = torch.nn.Sequential(torch.nn.Linear(10, 32), torch.nn.ReLU(), torch.nn.Linear(32, 1))
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
loss = torch.nn.functional.mse_loss(model(x), y)
opt.zero_grad(); loss.backward(); opt.step()
```

Pitfalls:
- Forgetting `zero_grad()` accumulates gradients across steps.
- Too high a learning rate gives diverging loss; too low looks like no learning.
- Vanishing or exploding gradients in deep nets are mitigated by residual connections, normalisation and sensible initialisation.

Interview tip: be able to explain backprop as "chain rule with cached intermediate values", not as magic.

### Self-attention
<!-- level: intermediate; ref: https://arxiv.org/abs/1706.03762 -->
Self-attention lets every token in a sequence build its representation as a weighted mix of all other tokens. Each token vector is projected into a query, a key and a value. The score between two tokens is the dot product of query and key, scaled by the square root of the key dimension, passed through softmax to give weights that sum to one. The output is the weighted sum of the values.

Unlike recurrent networks, all positions are processed in parallel, and any two tokens are connected in one step, which makes long-range dependencies easier to learn. The cost is that compute and memory grow quadratically with sequence length.

```python
scores = (Q @ K.transpose(-2, -1)) / d_k ** 0.5
scores = scores.masked_fill(causal_mask, float("-inf"))  # decoder-only models
out = scores.softmax(dim=-1) @ V
```

Multi-head attention runs several smaller attentions in parallel so different heads can capture different relations.

Pitfalls:
- Attention has no notion of order by itself; positional information must be injected.
- Attention weights are not a reliable explanation of model behaviour.

Interview tip: state the quadratic cost and name mitigations such as FlashAttention (an exact, memory-efficient kernel) and sliding-window or sparse variants.

### Transformer architecture
<!-- level: intermediate; ref: https://arxiv.org/abs/1706.03762 -->
A transformer block combines multi-head self-attention with a position-wise feed-forward network, each wrapped in a residual connection and layer normalisation. Blocks are stacked dozens of times. Positional information comes from sinusoidal encodings, learned embeddings, or rotary embeddings (RoPE), which most modern LLMs use.

There are three families. Encoder-only models (BERT) see the whole input bidirectionally and suit classification and embeddings. Decoder-only models (GPT-style, Llama, Claude) use causal masking and generate text one token at a time. Encoder-decoder models (T5) suit translation and summarisation.

During generation a KV cache stores the keys and values of already-processed tokens so each new token costs one step instead of recomputing the prefix. The cache grows with context length and batch size and is often the real memory bottleneck.

```text
x -> LayerNorm -> Attention -> + x -> LayerNorm -> FFN -> + (residual)
```

Pitfalls:
- Confusing the pre-norm layout used by most modern models with the original post-norm one.
- Ignoring KV-cache memory when sizing GPUs.

Interview tip: explain why decoder-only won for general LLMs: one simple objective, scales well, and handles many tasks via prompting.

### Tokenisation
<!-- level: basic; ref: https://huggingface.co/docs/transformers/tokenizer_summary -->
Models do not read characters or words; they read tokens, integer ids for sub-word pieces. Algorithms such as byte-pair encoding (BPE), WordPiece and SentencePiece learn a vocabulary of frequent fragments from a corpus, so common words are one token and rare words split into several. Byte-level BPE can encode any string.

Tokens matter because context limits, latency and API cost are all measured in tokens, and because tokenisation explains odd model behaviour: poor character counting, weak arithmetic on long numbers, and worse efficiency on non-English text or code that splits into many pieces.

```python
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("bert-base-uncased")
tok("unbelievably good")["input_ids"]
tok.tokenize("unbelievably")  # sub-word pieces
```

Pitfalls:
- Using one model's tokenizer to estimate another model's token counts.
- Truncating by characters instead of tokens.
- Changing the tokenizer after training, which breaks the embedding table.

Interview tip: mention that a rule of thumb for English is roughly four characters per token, but you should always count with the real tokenizer.

### Embeddings and similarity
<!-- level: intermediate; ref: https://developers.google.com/machine-learning/crash-course/embeddings -->
An embedding maps an item (word, sentence, image, user, product) to a dense vector of a few hundred to a few thousand floats so that similar items lie close together. Embeddings are learned: the training objective, for example contrastive learning on matching pairs, shapes what "similar" means.

Closeness is measured by cosine similarity, dot product or Euclidean distance. For normalised vectors cosine and dot product give the same ranking. Embeddings power semantic search, recommendations, clustering, deduplication and retrieval for RAG.

```python
import numpy as np
def cosine(a, b):
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))
```

Pitfalls:
- Mixing vectors from different embedding models or versions in one index; they live in unrelated spaces.
- Embedding very long text into one vector loses detail; chunk first.
- Assuming general-purpose embeddings capture domain jargon without evaluation.

Interview tip: say how you would evaluate an embedding model for your task, for example recall@k on a labelled query-document set, rather than trusting leaderboards.

### Transfer learning and pretrained models
<!-- level: basic; ref: https://huggingface.co/docs/transformers/training -->
Transfer learning reuses a model trained on a large general dataset as the starting point for a narrower task. Early layers learn broadly useful features (edges, syntax), so you only need to adapt the later ones. Options, from cheapest to most expensive: use the model as a frozen feature extractor, train only a new head, or fine-tune all or some layers with a small learning rate.

This matters because labelled data and compute are scarce for most teams. A pretrained backbone often reaches good accuracy with hundreds or thousands of examples instead of millions.

```python
from transformers import AutoModelForSequenceClassification
model = AutoModelForSequenceClassification.from_pretrained("distilbert-base-uncased", num_labels=3)
for p in model.distilbert.parameters():
    p.requires_grad = False  # train only the classification head
```

Pitfalls:
- A learning rate that is too high destroys pretrained knowledge (catastrophic forgetting).
- Domain mismatch between pretraining and target data limits gains.
- Licence terms of the pretrained weights.

Interview tip: describe the decision as a ladder: prompt first, then head-only, then parameter-efficient fine-tuning, then full fine-tuning.

## 8. Large Language Models and Prompting

### How LLMs are trained
<!-- level: intermediate; ref: https://arxiv.org/abs/2005.14165 -->
A large language model is trained in stages. Pretraining teaches next-token prediction over trillions of tokens of text and code with cross-entropy loss; this is where knowledge and fluency come from. Supervised fine-tuning on curated instruction and response pairs teaches the model to follow instructions. Preference tuning (RLHF, DPO and related methods) then steers it toward responses humans or reward models rate as helpful and safe.

At inference the model produces a probability distribution over the vocabulary for the next token, one token is chosen, appended to the input, and the loop repeats. Everything the model "knows" is encoded in weights and frozen at the training cutoff, which is why it cannot know recent events without retrieval or tools.

Pitfalls:
- Treating the model as a database: it generates plausible text, not verified facts.
- Assuming scale alone fixes reasoning or factuality problems.

Interview tip: be ready to separate pretraining, instruction tuning and preference tuning, and say what capability each stage adds.

### Context window and token budgeting
<!-- level: basic; ref: https://docs.anthropic.com/en/docs/build-with-claude/context-windows -->
The context window is the maximum number of tokens, input plus output, a model can attend to in one request. Everything the model should consider, such as system prompt, history, retrieved documents, tool results and the answer itself, must fit. Larger windows help, but cost and latency grow with input size, and models can use information in the middle of a very long context less reliably than at the edges.

Design with a budget: reserve space for the output, trim or summarise old turns, retrieve only the top relevant chunks, and keep stable content (system prompt, tool definitions) at the start so provider-side prompt caching can reuse it where supported.

```python
budget = MAX_CONTEXT - RESERVED_OUTPUT - len(system_tokens)
docs = take_until_budget(ranked_docs, budget)
```

Pitfalls:
- Stuffing everything in "because it fits"; irrelevant text lowers answer quality.
- Forgetting that conversation history is re-sent on every turn and billed again.

Interview tip: explain retrieval, summarisation and caching as three separate ways to deal with limited context.

### Sampling parameters
<!-- level: basic; ref: https://huggingface.co/docs/transformers/generation_strategies -->
Sampling decides how the next token is picked from the model's probability distribution. Greedy decoding always picks the most likely token: deterministic but can be repetitive. Temperature divides the logits before softmax; below 1 sharpens the distribution, above 1 flattens it. Top-k keeps only the k most likely tokens; top-p (nucleus) keeps the smallest set whose cumulative probability reaches p. Beam search keeps several candidate sequences and suits translation more than chat.

For extraction, classification and code, use low temperature. For brainstorming or creative text, raise it moderately. Adjust one control at a time, typically temperature or top-p, not both.

```python
out = model.generate(**inputs, do_sample=True, temperature=0.7, top_p=0.9, max_new_tokens=200)
```

Pitfalls:
- Expecting temperature 0 to be perfectly reproducible; batching and hardware nondeterminism can still change outputs.
- Some hosted reasoning models fix or restrict these parameters.

Interview tip: tie each parameter to a trade-off between determinism, diversity and risk of incoherence.

### Prompt engineering
<!-- level: basic; ref: https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview -->
Prompt engineering is writing the input so the model reliably produces the output you need. Effective prompts state the task, the audience and the output format explicitly, supply relevant context, and give a few examples (few-shot) when format or style matters. Separating instructions from data with clear delimiters, and asking the model to reason step by step for multi-step problems, both improve accuracy. Role framing and stating what to do (rather than only what to avoid) help.

Treat prompts as code: version them, test them against a fixed evaluation set, and change one thing at a time.

```text
You are a support triage assistant.
Classify the ticket into: billing, bug, feature_request.
Return JSON: {"category": "...", "confidence": 0-1}
<ticket>{{ticket_text}}</ticket>
```

Pitfalls:
- Tuning a prompt on three examples and shipping it.
- Contradictory instructions in long prompts.
- Putting untrusted user text inside instructions without delimiting it.

Interview tip: describe how you would evaluate a prompt change objectively with a regression set, not by eyeballing outputs.

### Structured output and tool calling
<!-- level: intermediate; ref: https://docs.anthropic.com/en/docs/build-with-claude/tool-use/overview -->
Applications need machine-readable output, not prose. Tool calling (function calling) lets you describe functions with a name, description and JSON schema; the model replies with a request to call a tool and its arguments, your code executes it, and you send the result back for the model to continue. Some providers also support schema-constrained decoding so output is guaranteed to parse.

The model never executes anything itself; your application validates arguments, runs the tool and decides what is allowed.

```json
{
  "name": "get_order_status",
  "description": "Look up an order by id",
  "input_schema": {"type": "object",
    "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}
}
```

Pitfalls:
- Trusting model-generated arguments without validation (injection, wrong ids).
- Vague tool descriptions, which cause wrong tool choice.
- Giving broad powerful tools when a narrow one would do.

Interview tip: always mention validating output against the schema and having a retry or fallback path when parsing fails.

### Hallucination and grounding
<!-- level: intermediate; ref: https://arxiv.org/abs/2311.05232 -->
A hallucination is fluent output that is unsupported or false. It happens because the model optimises for plausible continuation, not truth, and has no built-in way to say what it does not know. Rates rise for obscure facts, precise numbers, citations and questions with a false premise.

Mitigations work at several layers. Ground answers in retrieved or supplied documents and instruct the model to answer only from them. Require citations to source passages and check that they exist. Allow "I don't know" explicitly. Use tools for facts a model should not recall, such as calculations and live data. Lower temperature for factual tasks, and verify with a second pass or a rule-based checker.

```text
Answer using only the context. Quote the supporting sentence.
If the context lacks the answer, reply "Not found in the provided documents."
```

Pitfalls:
- Assuming RAG removes hallucination; the model can still ignore or misread the context.
- Measuring only fluency, not factual accuracy.

Interview tip: say that you measure groundedness (are claims supported by the retrieved text) separately from answer relevance.
